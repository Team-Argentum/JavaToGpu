Дорожная карта новой версии проекта (`com.sixik.gpu`). Документ рассчитан на то, чтобы **человек или нейросеть, не
знавшие контекста, сразу поняли, что строится, по каким правилам и что делать дальше.**

Состояние на 2026-11-07: **M0, M1 и M2 выполнены, следующая веха — M3.**

## 1. Что строим

**В одном абзаце.** Пользователь пишет GPU-код на Java (строго подмножество, не произвольный код); библиотека на этапе
сборки превращает его в компактный бинарный IR, а в рантайме (JIT) генерирует OpenCL C под конкретное устройство,
компилирует, кэширует и запускает. Если GPU нет — тот же метод выполняется на JVM. Архитектура рассчитана на будущий
перенос ядра на Rust (AnyToGpu) без переписывания дизайна.

**Ключевая боль, ради которой всё затеяно:** адаптация кода под разные видеокарты (AMD / NVIDIA / Intel) и распределение
работы между несколькими, в т.ч. разнородными GPU. Это **будущие планы** (разд. 8), в v1 закладываются только швы.

### Цели v1

| ID | Цель                                                                                                                 |
|----|----------------------------------------------------------------------------------------------------------------------|
| G1 | Метод с `@Kernel` на Java-подмножестве работает на OpenCL-устройстве через обычный вызов `K.f(a, b)`                 |
| G2 | Единственный канонический, сериализуемый, детерминированный IR (контракт Java↔Rust)                                  |
| G3 | Строгая диагностика на этапе компиляции (`GPU####`, позиция в исходнике, подсказка)                                  |
| G4 | Корректность проверяется без железа: IR-интерпретатор + golden-файлы + JVM-эталон                                    |
| G5 | JVM-fallback и `@GPUTest`: тот же метод и тесты работают без GPU                                                     |
| G6 | Простая модульная структура с проверяемыми границами; никакого over-engineering                                      |
| G7 | Возможности v1: скаляры, массивы, векторы, `@Struct`, pointer-типы, local memory, `barrier`, atomics, helper-функции |

### Не-цели v1 (сознательно НЕ делаем)

Оптимизатор (e-graph), CUDA/SPIR-V/ROCm-эмиттеры, ASM-фронтенд, images/samplers, async-API, multi-GPU,
Benchmark/AutoTune, вендорная адаптация кодгена, `@GpuNative`, разбиение одного запуска между картами. В языке: объекты
и куча, виртуальные вызовы, исключения, рекурсия, мониторы, labeled `break/continue`, `try/finally`, `assert`, строки.

## 2. Нерушимые принципы (проверьте себя перед каждым коммитом)

1. **Данные плоские (DOD).** IR и все таблицы ядра — SoA на примитивных массивах (`int[] op, type, a, b, c` + боковые
   таблицы). Ссылки — целочисленные id, не объекты. Строки интернируются. Никаких `Object`-графов, `Map<String,String>`
   как модели, reflection, иерархий узлов.
2. **Логика — статические функции над данными.** Запрещены
   `Registry / Factory / Provider / Service / Catalog / Contributor / Hook`-паттерны в ядре. Разрешены ровно три точки
   расширения: `Backend`, `OptimizerPass`, `EventListener` (разд. 10 архитектуры).
3. **Нет глобального изменяемого состояния в ядре.** Контекст (`GpuContext`) — явный объект. Единственное
   «ambient»-место — тонкий хост-фасад пользователя (ленивый default-контекст + scoped override).
4. **Ошибки — значения.** Ядро (`ir`, `codegen-opencl`, `ir-interpreter`, `runtime`-core) возвращает `Result`/список
   `Diagnostic` (код + позиция + сообщение + подсказка). Исключения — только на публичной границе (`GpuException` с
   полным отчётом) и во фронтенде для javac `Messager`.
5. **Детерминизм.** Один и тот же вход → побайтово тот же IR, хэш и OpenCL C. Нет зависимости от порядка `HashMap`,
   `String.hashCode`, времени, пути.
6. **Один канонический IR.** Запрещены текстовый IR, обратный парсинг IR в исходник, параллельные представления.
   Текстовый дамп (в `tools`) — только для людей и golden-тестов, в IR не парсится обратно.
7. **IR vendor-neutral и backend-neutral.** Вендорная/бэкендовая специализация — только на выходе, в кодгене (
   `emit(IrModule, Target)`).
8. **Нет кастов в IR и в исходнике ради типов.** Знак — метка типа; опкоды полиморфны; неявных приведений нет; `convert`
   только явный. Касты к `unsigned` допустимы лишь внутри сгенерированного C (чтобы дать Java-семантику).
9. **Java-семантика целых и `float→int` гарантирована контрактом IR** (оборот знаковых, маскирование сдвигов, насыщение,
   NaN→0); деление на ноль — «не определено, без падения».
10. **JVM ≡ GPU по конструкции.** Подмножество языка и валидатор исключают расхождения (векторы immutable; `@Struct` без
    aliasing). Float сравнивается «в ULP» из таблицы builtins, точного равенства не обещаем.
11. **Платформа:** Java 25, FFM (`java.lang.foreign`) для OpenCL, **без LWJGL** и сторонних нативов. ASM — только в
    `weaver`.
12. **Границы модулей проверяются сборкой.** Не обходите `verifyModuleBoundaries` — меняйте граф осознанно (и запись в
    `REWORK_ARCHITECTURE.md`, разд. 11).
13. **Единый источник истины.** Builtins — один декларативный файл; `Gpu.java`, типы и таблицы **генерируются**, руками
    не правятся.
14. **Каждый новый узел IR / правило / публичный метод — с тестом**, и узел IR сразу в трёх местах: валидатор,
    интерпретатор, кодген.

## 3. Архитектура кратко

```
[Сборка пользователя]   @Kernel Java  --frontend-java (javac Tree API)-->  IR (бинарный, колонками) в ресурсах
                                       --weaver (ASM)-->  тело метода → делегат хост-фасаду; оригинал → <name>$jvm

[Выполнение]            вызов K.f(a,b) → хост-фасад → GpuContext
                        IR → (optimize: identity в v1) → codegen-opencl: emit(IrModule, Target) → OpenCL C
                        → компиляция драйвером → кэш (память + диск) → запуск → результат
                        нет устройства → JVM-fallback поверх <name>$jvm
```

## 5. Глоссарий

- **IR / IrModule** — канонический бинарный образ GPU-программы: таблицы типов, узлов, функций, строк, констант + секция
  `debug`.
- **kernelId** — `hash(IR без debug)`.
- **Узел** — строка таблицы `nodes` (`op,type,a,b,c`); id = индекс; операнды всегда с меньшим id.
- **Открытый узел** — читает локаль или память (`local_get`, `load`, …); у него ровно один родитель. **Закрытый** —
  константа/параметр/чистая арифметика над закрытыми; им можно делиться.
- **Target** — `{backend, vendor, deviceClass, features, subGroupSize, computeUnits, …}` из `DeviceInfo`; вход кодгена и
  часть ключа кэша.
- **DeviceInfo** — vendor, name, driver, features, sub-group size, compute units, memory.
- **required_features** — битовая маска возможностей (fp64, int64-atomics, fp16…), считает валидатор IR; проверяется до
  компиляции.
- **uses_group_sync** — функция использует `barrier` или local memory (транзитивно); такие ядра не уходят в
  JVM-fallback.
- **`<name>$jvm`** — оригинальное тело `@Kernel`-метода (один work-item), сохранённое weaver'ом: JVM-fallback и эталон
  тестов.
- **KernelSample** — генератор аргументов + опциональные ожидаемые результаты; общий для `@GPUTest` (v1) и AutoTune (
  позже).
- **KernelGroup** — (зарезервировано) варианты одного ядра с одной ABI.
- **golden-файлы** — эталонные текстовые дампы IR и OpenCL C; будущая конформанс-сюита для Rust-версии.

## 7. Вехи v1

Стратегия: **тонкий вертикальный срез** (M1–M7: baseline-ядро от исходника до запуска), затем **ширина** (M8–M13: по
одной возможности, каждая — расширение IR → интерпретатор → кодген → рантайм → тесты). Всегда есть работающая сборка.

Baseline-подмножество среза: скаляры, массивы, `if/for/while/do-while/switch`, арифметика/сравнения/логика/тернарный,
helper-вызовы, builtins, `FloatPtr` — позже (M9).

### M0 — Сброс `[x]`

Тег `legacy-alpha5`; старый код удалён; скелет из 10 модулей; Gradle 9.8.1, JDK 25, JUnit 6.1.3, ASM 9.11.1;
`verifyModuleBoundaries` (проверено негативными тестами). Коммит `5ce86b90`.

### M1 — Модуль `ir` `[x]`

**Цель:** канонический IR, валидатор и сериализация — без единой зависимости. Фундамент всего остального.

**Сделано** (`ir/src/main/java/com/sixik/gpu/ir`):

- Таблица типов (`Types`, `AddressSpace`): фиксированные id скаляров `0..11` (+`VOID`), `12..15` зарезервированы;
  динамические `Vec`, `Ptr`, `Array`, `Struct` (с `align`) с дедупликацией, struct номинальны.
- SoA-таблицы (`IrModule`): `nodes` (`op,type,a,b,c`), пул списков, 64-битные константы (≤32 бит и `f32` — прямо в
  колонке `a`), семантические строки, таблица функций (18 колонок: kind, параметры, локали, `reqd_wg`, `inline`, `opt`,
  `required`, `body_kind`, `fallback`, `tune_*`). Каталог опкодов `Op` (≈55) и единая схема операндов `Operands`.
- `IrBuilder`: типизированные методы со своим выводом типов, детерминированная нумерация (операнды раньше узла),
  отладочные имена и позиции (`DebugInfo`).
- `Validator`: **все правила 5.12** (`IR-S/T/V/E/C/M/F/B`) + вычисление `required_features`, `uses_group_sync`, режимов
  доступа параметров, эффектов; возвращает `Diagnostic`, **не бросает исключений даже на мусорных данных**.
- `IrBinary`: колоночный формат `"GIR\0"`, секции `TYPE STRS CNST NODE LIST FUNC DBUG`; `hash`/`kernelId` (SHA-256) без
  `DBUG`; чтение возвращает `Result` (`IR-S05` версия, `IR-S06` повреждение).
- `AbiLayout` (O4): size/align/offset по правилам OpenCL C, `float3` = 16 байт.
- `Builtins` (O1, часть): `builtins/builtins.def` в корне репозитория упаковывается в ресурсы `ir` и читается в
  рантайме;
  15 builtins (индексы, математика, `assumeUniform`, `atomicAdd`); сигнатуры проверяются по классам `genf/geni/genn`.
- `tools`: `IrDump` — текстовый дамп (с/без отладки) + golden-тесты. `ir`: `testFixtures` (`Fixtures.computeSine()`,
  `Fixtures.rich()`) для тестов следующих модулей. JMH: `gradle/jmh.gradle`, `ir/src/jmh`.

**Критерии приёмки:**

- [x] Тест на каждое правило `IR-S/T/V/E/C/M/F/B` — 107 тестов валидатора; мутационная проверка: отключение правила
  роняет ровно свой тест.
- [x] Round-trip `serialize → deserialize` совпадает побайтово; одинаковая последовательность builder'а → одинаковые
  байты
  и hash.
- [x] Hash не меняется при изменении только `debug`; меняется при изменении константы и атрибута функции.
- [x] Golden: `computeSine` из `REWORK_ARCHITECTURE.md` 5.11 воспроизводится (15 узлов, 300 байт, `t16`/`t17`).
- [x] `ir` без зависимостей и запрещённых импортов (`verifyModuleBoundaries`); JMH для build/validate/read/write/hash.
- [x] Фазз: 2,1 млн итераций (побайтовых и «семантических») — читатель и валидатор не падают. Фазз нашёл и помог
  исправить два реальных дефекта валидатора (каскад повреждённых операндов).

**Измерения (JMH, 217 узлов, 3 функции):** build 4,1 мкс · validate 17,7 мкс · write 4,3 мкс · read 0,8 мкс · hash 5,9
мкс ·
холодный путь «read → validate → kernelId» 25,5 мкс.

**Решения, принятые в M1** (подробности — `REWORK_ARCHITECTURE.md`, 5.13): O1 — builtins читаются рантаймом из ресурса
(генератор нужен только `api` в M2); O4 — ABI живёт в `ir`; O7 — таблица «операция × тип» и коды
`IR-S06/S07/T09/T10/V04`
зафиксированы; правило «открытый узел имеет одного родителя» означает, что фронтенд для `a[i] += 1` создаёт **два**
узла `elem_ptr`.

**Не входит:** images, оптимизатор, исполнение (M4), кодген (M5).

### M2 — Модуль `api` `[x]`

**Цель:** публичный язык GPU-кода.

**Сделано** (`api/src`):

- Аннотации `@Kernel(inline, optLevel, workgroup, required, fallback)`, `@DeviceFunction`, `@Struct(alignment)`,
  `@Global(constant)`, `@Local`, `@Constant`, `@WorkGroup(x,y,z)` (Retention `CLASS` — их читает weaver) и `InlinePolicy`.
- **Генератор** (`src/generator`, задача `generateApi`, вывод в `build/generated`): из `builtins/builtins.def` строит
  `Gpu` (скаляры `float/double/int/long` + покомпонентные векторные перегрузки, Javadoc из `doc`, JVM-реализации из `jvm`),
  20 векторных типов `Float|Double|Int|Long × {2,3,4,8,16}` (неизменяемые) и классы-ссылки `FloatPtr/DoublePtr/IntPtr/LongPtr`.
  Таблица расширена директивами `doc/jvm/vectors/pointers` и флагом `ulp64=` (`ir` их пропускает; `Builtins.ulp64`).
- `WorkItem` / `WorkItemContext` (O6): положение work-item для JVM-реализаций `getGlobalId` и др., `ScopedValue`, плоские `int[3]`.
- Тесты `api`: 54 теста (генератор позитивно/негативно, builtins на крайних значениях, ULP-сверка с независимыми эталонами,
  контекст work-item, типы, аннотации, `ConceptSample` — образец концепта, выполняемый на JVM). JMH: `ApiBenchmarks`.

**Критерии приёмки:**

- [x] `Gpu.java` и типы не правятся руками: генерируются в сборке (коммитить нечего, расхождение невозможно);
- [x] JVM-реализации совпадают с таблицей допусков на крайних значениях (`GpuUlpToleranceTest`; мутационная проверка: порча
  `sin`/`sqrt` в таблице роняет тесты f32 и f64); builtin с допуском без эталона в тесте роняет тест;
- [x] синтаксис из `OldCodeConcept` компилируется и выполняется на JVM (без `@GpuNative/@GpuFallback/@AutoTune` — не v1);
- [x] ни одной внешней зависимости (`verifyModuleBoundaries`; генератор и JMH не входят в jar).

**Измерения (JMH, короткий прогон):** один work-item JVM-fallback ≈ 14 нс против ≈ 6,4 нс прямого цикла (≈ 8 нс — цена контекста),
привязка контекста `WorkItem.run` ≈ 15 нс на запуск.

**Решения, принятые в M2** (подробности — `REWORK_ARCHITECTURE.md`, 5.14): O1 закрыт (один файл — две стороны); O6 закрыт
(`ScopedValue`); `atomicAdd` без Java-представления до M9/M10; **float `max/min` на JVM = `Math.max/min` — кодген (M5) обязан
дать ту же семантику (NaN, `±0`), иначе OpenCL `fmax/fmin` разойдётся с JVM**; допуски ULP сверить с первоисточником
спецификации в M5; `required` — имена `Features` IR (`"SIMD"` из концепта — диагностика в M3).

**Не входит:** операции над векторами (M8), pointer-типы `Global*/Local*/Constant*Ptr` (M9), `barrier` и atomics в Java-API (M10).
**Опирается на:** 3.A, 3.B, 5.7, 8.3.

### M3 — Модуль `frontend-java` `[ ]`

**Цель:** `@Kernel`-метод → IR на этапе `javac`.
**Объём:** annotation processor на javac Tree API (`com.sun.source` + `Trees`, типы разрешены javac); разбор
baseline-подмножества; **нормализация эффектов** (инварианты `E01/E02`: `f(x++, g())` раскладывается по локалям в
Java-порядке; compound-присваивания и `++` разворачиваются); `&&`/`||` → ленивый `select`; атрибуты из аннотаций →
атрибуты функции IR; subset-валидатор с диагностиками `GPU####` через `Messager` (точная позиция, подсказка); сбор
helper-функций транзитивным замыканием, в т.ч. из других классов/библиотек; запись IR-ресурса (O5); оригинальный метод
остаётся нетронутым (его потом подменит weaver).
**Критерии приёмки:** 
- [ ] компиляция образцов через `javax.tools.JavaCompiler` in-process и сравнение с golden-дампом
IR;
- [ ] для каждого кода `GPU####` — негативный тест (исключение, объект, labeled break, рекурсия, `try`,
`synchronized`, `assert`, строка, …);
- [ ] результат IR проходит валидатор `ir`;
- [ ] определён и проверен обход прокси`ProcessingEnvironment` (Gradle/IDE).
**Риск:** javac Tree API работает только с javac (ECJ не поддерживается) — осознанно.
**Опирается на:** 3.A, 3.3, 5.4, 5.8, 5.12.

### M4 — Модуль `ir-interpreter` `[ ]`

**Цель:** эталонная семантика IR на CPU.
**Объём:** выполнение по виртуальному NDRange 1D/2D/3D; Java-семантика целых (оборот, маска сдвигов), насыщающий
`float→int`, ленивый `select`; builtins по таблице; `barrier`/local — в M10.
**Критерии приёмки:** [ ] **дифференциальные тесты**: на наборе образцов результат интерпретатора = результат прямого
вызова оригинального Java-метода по work-item'ам (точно для целых/логики, в ULP для float); [ ] крайние значения (
`MIN/MAX`, `NaN`, сдвиги ≥ ширины); [ ] нет зависимостей кроме `ir`.
**Опирается на:** 5.10, 8.3, 13.

### M5 — Модуль `codegen-opencl` `[ ]`

**Цель:** `emit(IrModule, Target) → Artifact` (текст OpenCL C + имена entry + раскрытая сигнатура аргументов).
**Объём:** читаемый C (имена из `debug` + `#line` в debug-режиме; в release — без них, текст стабилен); `Array` →
`__global T* a, int a_len`; Java-семантика целых (арифметика через `unsigned` внутри C, маска сдвигов); насыщающий
`float→int` (`convert_*_sat` + NaN, проверить по спецификации/драйверам); `#pragma OPENCL FP_CONTRACT OFF`, `fastMath`
по опции; `#pragma OPENCL EXTENSION …` по `required_features`; `select` → `?:`; `load(elem_ptr(a,i))` → `a[i]`; `Target`
уже в сигнатуре и в имени golden (вендорных правил в v1 нет).
**Критерии приёмки:** [ ] golden-файлы OpenCL C для всех образцов, отдельно release и debug; [ ] детерминизм (повторный
`emit` = те же байты); [ ] ни `java.nio.file`, ни FFM; [ ] (device-тест, M6) сгенерированный C компилируется реальным
драйвером.
**Опирается на:** 8, 8.A.

### M6 — Модуль `runtime`, ядро запуска `[ ]`

**Цель:** найти устройство, скомпилировать, залить буферы, запустить, забрать результат — синхронно.
**Объём:** `DeviceApi` — тонкий слой над `libOpenCL` через FFM (≈40 функций:
платформы/устройства/контекст/очередь/программа/kernel/буферы/NDRange/`finish`/release; загрузка `OpenCL.dll` /
`libOpenCL.so.1` / macOS framework; отсутствие библиотеки = «устройств нет»); `DeviceInfo`; `GpuContext` (builder,
потокобезопасный; v1 — ровно одно активное устройство); `GpuBuffer` (device-resident); массивы как сахар с
загрузкой/выгрузкой по режимам доступа из IR; компиляция с разбором build log в диагностики; кэш в памяти;
`EventListener`; ошибки: `Result` внутри, `GpuException` на границе. `DeviceApi` за интерфейсом + фейковая реализация
для тестов без железа.
**Критерии приёмки:** [ ] unit-тесты на фейковом `DeviceApi` (без железа); [ ] `@Tag("device")` тест: `computeSine` на
реальном OpenCL; [ ] FFM-доступ без LWJGL; [ ] отсутствие драйвера не роняет старт.
**Опирается на:** 9, 9.1, 9.2, 9.5. **Legacy (идеи):** `OpenClGpuRuntimeBackend`, `OpenClRuntimeSession`,
`OpenClArgumentMarshaller`, `OpenClValuePacker`.

### M7 — `weaver` + `gradle-plugin` + хост-фасад: первое ядро end-to-end `[ ]`

**Цель:** обычный вызов `K.f(a, b)` запускается на GPU.
**Объём:** `weaver` (ASM, чистая функция над `ClassNode`): тело `@Kernel`-метода → `<name>$jvm`, метод становится
делегатом хост-фасаду (`kernelId`, аргументы); `gradle-plugin`: подключает зависимости и processor, weave-шаг после
`compileJava`, `--enable-native-access=ALL-UNNAMED` для `test/run`; хост-фасад в `runtime` (имя — **O2**): ленивый
default-контекст, scoped override `use(ctx)`, shutdown hook, запуск с `launch1D/2D/3D`-override (дефолт — по первичному
массиву); IR-ресурс находится по `kernelId`.
**Критерии приёмки:** [ ] TestKit-проверка плагина на тестовом проекте; [ ] байткод-тест weaver'а (оригинал сохранён как
`$jvm`, делегат корректен); [ ] E2E `@Tag("device")`: `computeSine` из README запускается обычным вызовом; [ ] E2E без
железа (weave + IR-ресурс присутствуют).
**Опирается на:** 3.4, 3.6, 3.7. **Открыто:** O2, O5.

### M8 — Векторы + `@Struct` + ABI `[ ]`

Векторные типы и ops в IR/интерпретаторе/кодгене (`splat extract insert shuffle build`); immutable `FloatN`;
`@Struct(alignment)` как value-тип; no-aliasing правила `@Struct` во фронтенде (3.2); хост-представление struct (**O3**:
предложение — генерируемые аксессоры над `GpuBuffer` + сахар для массивов объектов через сгенерированный упаковщик, без
reflection); `float3` = 16 байт.
**Критерии:** [ ] дифференциальные тесты векторов/struct; [ ] golden C; [ ] device-тест массива struct.
**Legacy (знания):** `OpenClStructLayout`, `OpenClVectorLayout`, `OpenClValueLayout`, `docs/OpenCL-Data-Model.md`.

### M9 — Pointer-типы и address spaces `[ ]`

`Ptr(space,pointee)`, `Global*/Local*/Constant*Ptr`, `FloatPtr` (`local_addr`), `@Global(constant=true)` (массив →
`__constant`, проверка `CL_DEVICE_MAX_CONSTANT_BUFFER_SIZE`; скаляр → по значению), правило `IR-M01/M04`.
**Критерии:** [ ] тесты семантики по ссылке (JVM ≡ GPU); [ ] запись в `constant` отклоняется.

### M10 — Local memory, `barrier`, atomics `[ ]`

`local_array_decl`, `barrier`, `atomic_*` (через `elem_ptr`), `uses_group_sync`; `IR-B01` (taint-анализ расходящегося
`barrier`: WARNING, `strictBarriers` → ошибка; `Gpu.assumeUniform`); эмуляция групп и барьера в интерпретаторе.
**Критерии:** [ ] редукция/тайлинг-примеры в интерпретаторе и на устройстве; [ ] тесты на `IR-B01`.

### M11 — Prepared launcher и `GpuBuffer` `[ ]`

`prepare(kernel, args…) → PreparedLauncher`: переиспользуемые буферы, повторные запуски без пере-подготовки; одна
реализация (не три вложенных); static-аргументы выражаются владением буфером, не масками.
**Критерии:** [ ] JMH накладных расходов запуска; [ ] тесты владения/освобождения буферов.

### M12 — Дисковый кэш, политика устройства, Timings, варианты по `required` `[ ]`

Диск-кэш (user-cache dir, ключ = hash IR без debug + версия кодгена + устройство + опции, атомарная запись tmp+rename,
повреждённый файл = промах, LRU); `DevicePolicy` (фильтры: тип/vendor/память/features; override через builder и
`JAVATOGPU_DEVICE`; детерминированный порядок); Timings (upload/kernel/readback, счётчики кэша) через `EventListener` (
события несут id устройства); выбор варианта метода по `required` (директива `fallback`-вариант, без измерений);
`inline/optLevel` — информативные атрибуты.
**Критерии:** [ ] тесты кэша (попадание/промах/повреждение/инвалидация версией кодгена); [ ] политика на фейковых
устройствах.

### M13 — JVM-fallback и `test-support` `[ ]`

JVM-fallback: последовательный цикл по global id поверх `<name>$jvm` (контекст work-item — O6); `uses_group_sync`-ядра →
ошибка «нужно устройство»; политика `fallback = ALLOWED` (дефолт, одно WARNING-событие с причиной и build log) /
`NEVER`. `test-support`: `@GPUTest`, `GpuAssert.sameResult(K.class, "f", args…)` — `$jvm` → IR-интерпретатор → GPU,
сравнение (целые/логика точно, float в ULP), `KernelSample` (генератор + опц. ожидаемое; JSON-загрузчик как один из
источников).
**Критерии:** [ ] все образцы M3–M10 имеют `@GPUTest`; [ ] fallback-тесты без железа; [ ] device-тесты по тегу.

### M14 — Документация и alpha `[ ]`

Одна пользовательская (быстрый старт, подмножество языка, диагностики `GPU####`, fallback, кэш, ограничения) и одна
архитектурная документация; публикация alpha **v1** (O8: координаты); актуализация README и этого файла.

## 12. Быстрый старт для исполнителя (в т.ч. нейросети)

1. Прочитайте разд. 0–2 этого файла и разделы 5, 5.10–5.12 в `REWORK_ARCHITECTURE.md`.
2. Возьмите первую веху со статусом `[ ]` (сейчас **M3**). Работайте только в модулях этой вехи.
3. Перед кодом выпишите узлы/правила, которые затрагиваете, и где они должны появиться (валидатор + интерпретатор +
   кодген).
4. Пишите тест раньше или вместе с кодом; golden обновляйте осознанно.
5. `./gradlew build` → зелёный. Отметьте критерии приёмки вехи и обновите статусы здесь.
6. Если нужное решение не записано или противоречит принципам — **не придумывайте молча**: добавьте вопрос в
   `REWORK_ARCHITECTURE.md` (разд. 15) и сообщите владельцу.
