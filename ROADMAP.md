### F1. Remaining blockers for full large-workload Java-source parity

The current large-workload dogfooding target is now mostly aligned with existing JavaToGpu concepts, but a full source-level Java port still needs a few focused pieces:

- [x] Add 3D runtime launch support end-to-end.
  The reference kernels use `get_global_id(2)` / `get_global_size(2)` and 3D NDRange layouts. `GpuExecutionConfig` now supports `globalZ` / `localZ`, the OpenCL backend can enqueue 3D NDRanges, generated launchers expose explicit config and 3D work-size overloads, and targeted regression coverage exercises the 3D runtime path.
- [x] Add or formalize the Java authoring path for union-style packed views.
  Some source workloads use C `union` overlays inside packed structs such as weighted lookup nodes and compact search-tree nodes. The source-level policy remains no general Java union support; the practical path is now an explicit packed/blob overlay pattern using byte-root pointer views and `read*At(byteOffset)` helpers, with overlay regression coverage for reading alternate `uint32_t` / `int16_t` views from the same packed node layout.
- [x] Improve generic root-blob pointer ergonomics for this style of code.
  Large packed-data kernels often use `global const void *`, `global void *`, pointer-shift helpers, typed reinterpret casts, `restrict`, and `const` combinations. Existing byte-root typed views now have direct `read*At(byteOffset)` and `*PtrAt(byteOffset)` helpers, so root-blob schemas can express offset-driven typed views without repeating `root.add(offset).asTypePtr()` boilerplate for every field.
- [x] Define the source-level policy for preprocessor/debug/trap constructs.
  The file relies on `#ifdef` / `#define` feature gates, `DEBUG`, `DF_COMPILE_*`, `printf`, and `__builtin_trap()`. The Java frontend policy is now explicit: preprocessor feature gates and debug printing remain build/configuration or low-level concerns, while source-level fail-fast paths use `GPU.trap()` and `GPU.unreachable()` as deliberate Java-side replacements for `__builtin_trap()` / `__builtin_unreachable()`.
- [x] Validate kernel attributes together with 3D launch semantics.
  Attribute support exists, and the reference file includes launch-sensitive attributes such as `reqd_work_group_size(8, 8, 1)`. Regression coverage now verifies that this attribute is preserved in generated OpenCL, generated launchers expose explicit 3D config entry points, and runtime invocation can carry matching explicit local sizes such as `8 x 8 x 1`.
- [x] Add a focused Java dogfooding slice for large packed/root-blob kernels.
  The focused source-level dogfooding slice now covers a representative 3D packed lookup kernel shape: 3D NDRange launch, `reqd_work_group_size(8, 8, 1)`, packed/root-blob offset views, typed reinterpret helpers, and CPU-vs-GPU validation on the available NVIDIA OpenCL stack. The serious workload report now tracks this as a dedicated 3D packed/root-blob workload artifact.

## I. Future Compiler Intelligence

These are major post-production-core architecture tracks. They should not block the current A1/A2 runtime-validation push, but they define the next generation of the compiler once the runtime is operationally stable.

### I1. General ASM ingestion frontier

- [ ] Build an improved ASM parser/frontend that can ingest arbitrary JVM bytecode shapes instead of requiring GPU-friendly ASM.
  The long-term target is to accept normal Java compiler output and progressively classify methods into supported, transformable, or rejected regions with useful diagnostics. This likely needs CFG reconstruction, stack-state simulation, local-variable/type recovery, exception/monitor/control-flow detection, and a lowering boundary that can isolate GPU-safe regions without forcing source authors to hand-shape bytecode for the GPU pipeline.
- [ ] Add diagnostics for non-GPU-safe bytecode patterns discovered by the general ASM frontend.
  Arbitrary ASM should fail with concrete reasons and rewrite hints rather than opaque frontend errors, especially for object allocation, virtual dispatch, exceptions, synchronization, recursion, unsupported library calls, and heap/object graph access.

### I2. IR validation and optimization pipeline

I2 is closed for the current scope: the read-only IR Validator foundation is ready to be exercised on real examples. Deeper production optimizer/rewrite work remains intentionally out of I2 and is tracked as post-I2 frontier work instead of blocking validator dogfooding.

  `GpuIrOptimizationValidationPipeline` now aggregates safety validation, CSE planning preview, auto-vectorization preview, dry-run validation, resolved rewrite operations, optimizer-gate summaries, and CI artifact fields.

### I3. Production IR pipeline and runtime backend optimization

#### I3.6 Runtime-equivalence and promotion gates

- [x] Add pre/post runtime-equivalence execution for selected optimized IR.
  Runtime backends now have an opt-in `GpuRuntimeEquivalenceExecutor` / `GpuRuntimeEquivalenceRequest` hook that can compare compile stages before promotion. - [x] Add rollback-on-failure at runtime.
  Runtime compile snapshots now include `fallback.properties` with fallback decision, original/optimized selection flags, and diagnostics. #### I3.7 Public extension hooks and third-party integration SPI

- [x] Define a stable extension registry foundation for compiler/runtime hooks.
  `GpuExtension`, `GpuExtensionCapability`, `GpuExtensionDescriptor`, and `GpuExtensionRegistry` now provide stable id/version/capability/order metadata, deterministic descriptor ordering, duplicate-id rejection, and audit field maps. `GpuRuntimeIrOptimizationPass` and `GpuIrValidationProvider` participate in the common contract without losing their functional-interface shape; explicit lists preserve caller order, while `ServiceLoader` paths use deterministic ordering. Persisting the exported metadata in `IrGpu` and runtime/build artifacts remains tracked separately below.
- [x] Split extension hooks by pipeline phase and permission level.
  `GpuExtensionPhase` now identifies validation, diagnostics, runtime IR optimization, backend lowering, device selection, runtime equivalence, production promotion, and artifact emission. `GpuExtensionPermission` separates `READ_ONLY`, `MUTATION_PROPOSAL`, and `PRODUCTION_AFFECTING` authority. Pipeline registries enforce phase, maximum permission, and required capability before execution: IR validators are read-only, optimizer passes are limited to mutation proposals, and production-affecting optimizer extensions are rejected until a dedicated authorization contract exists.
- [x] Add production-affecting extension authorization.
  `GpuProductionExtensionAuthorizationDecision` now evaluates the existing production optimizer gate, accepted proof artifacts, runtime-equivalence evidence, fallback state, rollback support, valid production-promotion decision, mutation allowance, and explicit operator acceptance. Authorizations are bound to extension id/version, backend, device vendor/label, optimization profile, and original `IrGpu` identity. `GpuRuntimeIrOptimizerRegistry` skips production-affecting passes in production profiles unless a matching accepted authorization is installed; review profiles remain available for collecting evidence, and stale authorization cannot be reused for another kernel or runtime context.
- [x] Add extension safety contracts and fail-closed behavior.
  `GpuExtensionExecutionReport`, `GpuExtensionExecutionOutcome`, `GpuExtensionFailurePolicy`, and `GpuExtensionExecutionException` now provide a shared audit surface for extension invocation. Advisory optimizer failures are isolated as `FAILED_CONTINUED`, represented as non-mutating skipped passes, and do not block later passes or force aggregate rollback. Production-profile optimizer failures are `FAILED_CLOSED`, stop the pipeline, and remain rollback-required. Diagnostic IR validation isolates unexpected provider failures and continues, while strict modes stop immediately; existing compiler-domain failures such as `GpuIrPassException` preserve their public exception type instead of being hidden by the generic wrapper.
- [x] Allow third-party validators to extend the existing IR Validator model.
  `GpuIrValidationProvider` remains a ServiceLoader SPI, while `GpuIrValidationReportEntry` now carries provider alias, extension id/version, rule id, severity, source anchor, method identity, entry-point state, and arbitrary provider fields. `GpuIrValidationRunner` automatically enriches legacy four-field entries with the actual provider metadata and Java/ASM source anchor, so downstream validators do not need to duplicate compiler location logic. `GpuCompilerProcessor` persists the enriched fields in the existing validation properties artifact without breaking the established provider alias contract. The built-in optional `ir-validation` provider now exposes stable id `javatogpu.ir-validation`, version `1`, aggregate rule id, and derived INFO/WARNING/ERROR severity.
- [x] Allow third-party optimizer and peephole passes without core forks.

Rule reports preserve rule id/version, extension id/version, method, candidate/proposal counts, proof status, diagnostics, and custom fields. The built-in matcher set now shares `GpuRuntimeIrTypedNodeGraph` for read-only typed-node traversal, emits `GpuRuntimeIrPeepholeReplacementPlanValidation` evidence, and produces mutation-free `GpuRuntimeIrPeepholeRewriteSketch` records so future structural rewrites have a fail-closed graph/plan/sketch boundary before any rewrite builder exists. Drift artifacts, workload gates, OpenCL validation reports/history, and production-promotion explainability now surface plan-validation and rewrite-sketch counts/first blockers as evidence-only telemetry. The current pass remains diagnostic/proposal-only: rules cannot bypass fast-math policy, proof requirements, production authorization, rollback, runtime-equivalence, or final IR selection gates.
- [x] Add optional approval-bound IR optimizer modules.
  `ir-optimizer` and `ir-vendor-optimizer` now exist as optional modules that keep `GpuIrValidationProvider` strictly read-only and expose optimization only through separate `MUTATION_PROPOSAL` provider contracts. The backend-neutral runtime bridge records proposal/provider evidence without loading vendor providers by default, while vendor-specific providers must opt into `GpuIrVendorOptimizationProposalProvider` / `GpuIrVendorOptimizationProposalRegistry`. Optimizer proposal evidence now includes approval-template status: real immutable rewrites can emit pending templates under `META-INF/javatogpu/ir-optimization-approvals/`, while preview/no-change proposals record `not-applicable` blockers. Approval artifacts are bound to optimizer id/version, original and optimized `IrGpu` identities, backend target, optimization profile, proof verdict, and rollback requirement; they remain manual-review-only and do not authorize production mutation or selected-IR replacement by themselves. Runtime OpenCL validation now surfaces this evidence through `runtime-ir-optimizer-evidence.properties` and the `Runtime IR Optimizer Evidence` report section, including approval-template pending/not-applicable counts.
- [x] Add the third-party backend/device policy foundation.
  `GpuRuntimeDevicePolicy` extensions can contribute deterministic ranking adjustments, candidate rejection, capability facts, vendor quirks, compile-option validation, and diagnostics without taking ownership of final device selection. `GpuRuntimeDevicePolicyRegistry` loads the built-in backend-compatibility policy plus ServiceLoader extensions, rejects duplicate policy/extension ids, validates the device-selection phase/capability/read-only permission contract, isolates advisory failures, fails closed in production profiles, and keeps final scoring, rejection precedence, tie-breaking, and blocker selection in core. `GpuBackendLowerer` now participates in the shared extension metadata contract through stable backend-lowerer id/version/capability/phase/permission fields.
- [x] Add third-party backend compiler feedback providers.
  `GpuBackendCompilerFeedbackProvider` extensions can parse vendor/toolchain-specific resource diagnostics after backend compilation without mutating IR or compile decisions. The registry loads providers through ServiceLoader, runs backend-specific providers before the built-in generic fallback through extension ordering, validates the `BACKEND_COMPILER_FEEDBACK` / `COMPILER_FEEDBACK` / `READ_ONLY` contract, rejects duplicate ids, isolates parser failures, and persists execution outcomes beside the selected resource metrics.
- [x] Connect OpenCL device policy modules to physical discovery and context creation.
  `OpenClRuntimeSession` now enumerates every OpenCL platform/device through Packager, queries capability/vendor/driver metadata before context creation, classifies CPU/iGPU/dGPU from device type and unified-memory support, assigns a runtime-unique candidate id, evaluates `GpuRuntimeDevicePolicyRegistry`, maps the selected profile back to the exact native device, and only then creates the OpenCL context/queue. Core scoring gives device class precedence so a supported dGPU outranks an iGPU by default even when the iGPU reports more compute units. Compile requests reuse the selected profile, including device id/class/global memory/unified-memory facts.
- [x] Add request-specific OpenCL selection and explicit device overrides.
  `GpuRuntimeCompileOptions` now carries backend-neutral `GpuRuntimeDeviceOverride` selectors for runtime device id, vendor, device label, and device class. `GpuRuntimeExplicitDeviceOverridePolicy` applies them as required fail-closed constraints before native context creation. The first OpenCL session is selected with the concrete kernel descriptor and compile options rather than default options only; later invocations re-evaluate all policies against the original candidate set.   Future CUDA/Vulkan/Metal discovery should reuse the same pre-context and request-specific selection boundary. Future backend-specific artifacts still need the same normalized participation model. This keeps generated artifacts auditable when a project depends on company-specific plugins or third-party GPU libraries.

- [x] Add backend-lowerer/module identity to runtime compile cache keys.

- [x] Make cache keys aware of stable `IrGpu` artifact identity.

- [x] Add explicit backend artifact and lowerer version fields to cache keys.
  Cache identity now carries both backend artifact format version and backend lowerer version explicitly, so future source/binary artifact upgrades can invalidate compiled kernels without relying only on full artifact equality.
- [x] Store original and optimized artifacts separately.
  Runtime compile artifacts now keep a backend-neutral snapshot with original `IrGpu`, optimized `IrGpu`, explicit selected `IrGpu` handoff state, lowered backend module, compile log placeholder, and runtime validation evidence placeholder attached to compiled kernels. Snapshot mutators refresh the stored runtime selection when fallback, equivalence, optimizer report, or compile provenance changes, so dump artifacts and backend lowering consume the same source-of-truth decision.

### I4. Optional IR optimizer module split

Goal: turn the current read-only IR Validator evidence model into a clean optional optimization architecture without making validation mutable, forcing optimizer dependencies on normal users, or coupling backend-neutral rewrites to one vendor stack.

Current rule: `ir-validation` remains strictly read-only. Optimizer modules may inspect validation evidence, run pre/post validation, and emit proposal/equivalence artifacts, but they must not mutate the original `IrGpu` artifact in place or silently replace the selected runtime IR without explicit opt-in policy and fail-closed evidence.

- [x] Define the module boundary for optional IR optimization.
  Keep `processor` as the owner of the canonical `IrGpu` model, artifact identity, runtime compile request, backend lowering handoff, and no-op default behavior. Keep `ir-validation` as the optional read-only validator module. Add `ir-optimizer` for backend-neutral transform contracts and general optimization passes. Keep vendor/device-specific optimization implementations out of that core module by default.
- [x] Split backend-neutral optimizer contracts from runtime-local prototype APIs.
  `ir-optimizer` now exposes backend-neutral proposal contracts through `GpuIrOptimizationProposalProvider`, immutable proposal/request/report types, the validation sandwich, approval-template helpers, vendor-provider SPI, and `GpuIrOptimizationProposalRegistry`. The registry owns ServiceLoader loading, deterministic ordering, duplicate-id rejection, and backend-neutral provider discovery, while `GpuIrProposalRuntimeBridgePass` remains a thin runtime-local adapter to the existing `GpuRuntimeIrOptimizationPass` path. This preserves current runtime behavior when no optimizer module is present and keeps future optimizer authors on the optional proposal API instead of depending on runtime-local prototype registry details.
- [x] Add an immutable IR rewrite contract.
  `GpuIrOptimizationProposal` now enforces the immutable rewrite boundary directly: `PROPOSED` decisions must carry a distinct optimized artifact instance with a different stable `IrGpu` identity, while unchanged or preview-only work must use `NO_CHANGE` / proposal evidence instead. Proposal requests carry the original artifact plus policy/context, and proposals preserve optimizer id/version, diagnostics, proof metadata, rollback reason, original identity, and optimized identity. This keeps validation, diffing, cache identity, approval templates, and production gates comparing original versus optimized artifacts instead of trusting in-place mutation.
- [x] Add the validation sandwich as the default optimizer safety model.
  `GpuIrOptimizationSandwichRunner` now enforces the default optimizer safety flow: validate the original artifact, run one immutable proposal provider, validate the optimized artifact when present, then either keep the original, emit proposal-only evidence, select the optimized artifact only when mutation is explicitly allowed, or roll back on invalid optimized IR. The report records original/optimized validation results, final status, selected artifact, diagnostics, and rollback requirement. Existing tests cover no-change proposals, proposal-only mode, explicit mutation selection, invalid optimized rollback, invalid original short-circuiting, malformed proposal rejection, and ServiceLoader discovery.
- [x] Define backend-neutral optimizer policy controls.
  `GpuIrOptimizationPolicy` now provides the backend-neutral optimizer control surface for optimizer profile, optimization level, proposal-only mode, mutation permission, fast-math permission, vendor adaptation, register-pressure splitting, rollback requirement, and proof requirement. `GpuIrOptimizationProposalRequest` preserves its existing constructors while exposing the normalized policy view and serializing policy fields into context metadata, so proposal providers and runtime adapters can consume one shared policy contract without depending on OpenCL-only flags or runtime-local prototype details.
- [x] Add first backend-neutral optimizer families only after the contract is stable.
  `GpuIrTextCanonicalizationProposalProvider` handles semantics-neutral transitional text normalization, and `GpuIrHelperDependencyDeduplicationProposalProvider` now performs the first backend-neutral metadata cleanup by removing duplicate helper dependencies while preserving first-occurrence order and leaving body/typed/backend output data unchanged. More aggressive families such as constant folding, dead-code cleanup, safe local CSE, private-array scalarization, and typed-body peephole rewrites remain future proposal-only candidates until pre/post validation plus runtime-equivalence evidence are available.
  `GpuIrConstantFoldingPreviewProposalProvider` now adds the first constant-folding proof surface by scanning typed IR for simple plain-decimal literal binary expressions and recording candidate, operator, numeric-kind, first-fold, skipped-blocker, policy, proof, and safety evidence without proposing a rewrite. It explicitly records divide-by-zero, non-even division, unsupported operator, non-literal operand, and non-plain literal blockers, plus `runtimeEquivalenceRequiredBeforeRewrite`, `approvalRequiredBeforeRewrite`, and unresolved integer-overflow / floating-rounding proof flags so the future rewrite path cannot graduate without stronger evidence.
  OpenCL runtime validation now aggregates that preview evidence into `constantFoldingPreview.*` fields in `runtime-ir-optimizer-evidence.properties` and surfaces pass, candidate, and skipped-blocker counts in the `Runtime IR Optimizer Evidence` report section, making constant-folding readiness visible without enabling optimized IR selection.
  `GpuIrSafeLocalCsePreviewProposalProvider` now adds the matching safe-local-CSE proof surface by scanning typed IR for repeated local expressions and recording expression, candidate-expression, duplicate-expression, equivalence-class, blocker, policy, proof, and safety evidence without proposing a rewrite. It explicitly records unsupported-operator, impure-operand, and control-flow-boundary blockers plus required runtime-equivalence/approval gates and unresolved dominance / side-effect-freedom proof flags, so CSE readiness can be measured without enabling optimized IR selection.
  OpenCL runtime validation now aggregates that preview evidence into `safeLocalCsePreview.*` fields in `runtime-ir-optimizer-evidence.properties` and surfaces pass, candidate-expression, duplicate-expression, and blocker counts in the `Runtime IR Optimizer Evidence` report section.
  `GpuIrTypedDeadCodePreviewProposalProvider` now adds the first typed dead-code proof surface by walking typed-body roots and recording node, reachable-node, unreachable-node, unreachable-kind, blocker, policy, proof, and safety evidence without proposing a rewrite. It explicitly records missing-root, missing-child-reference, and side-effecting-unreachable-node blockers plus required runtime-equivalence/approval gates and unresolved side-effect-freedom proof flags, so dead-code cleanup readiness can be measured without enabling optimized IR selection.
  OpenCL runtime validation now aggregates that preview evidence into `typedDeadCodePreview.*` fields in `runtime-ir-optimizer-evidence.properties` and surfaces pass, unreachable-node, and blocker counts in the `Runtime IR Optimizer Evidence` report section.
  The same runtime evidence now includes `previewReadiness.*` aggregate fields over constant folding, safe-local CSE, and typed dead-code cleanup. The aggregate records overall status, recorded/candidate/blocked family counts, and a per-family status summary (`not-recorded`, `no-candidates`, `candidates-recorded`, `blocked-by-proof`, or `ready-for-runtime-equivalence-review`) so CI can track optimizer-family readiness without enabling production mutation or selected-IR replacement.
  `runtimeEquivalenceReview.*` now sits above `previewReadiness.*` as a fail-closed review gate. It records whether preview families are eligible for runtime-equivalence review, whether review evidence is required, the first blocker, the family summary, and explicitly disabled production mutation / selected-IR replacement so review readiness cannot be confused with production optimization enablement.
  `reviewPackage.*` now sits above runtime-equivalence review as the manual-review bundle boundary. It records package status, requirement/completeness, first blocker, proposal-pass count, pending approval count, original/optimized IR and proof-summary requirements, and repeats manual-review-only plus disabled production mutation / selected-IR replacement guardrails so review packaging remains evidence-only.
  `validateOpenClRuntimeIrOptimizerEvidence` now validates those raw runtime evidence files in the OpenCL operational/NVIDIA routines, failing CI if review-package guardrails disappear, if production mutation or selected-IR replacement becomes enabled, or if a required package is marked complete/missing a blocker before an activation design exists.
- [x] Keep vendor optimization as a separate optional provider layer.
  `ir-vendor-optimizer` now exists as a separate optional module skeleton. It contributes vendor proposals only through `GpuIrVendorOptimizationProposalProvider` and `GpuIrVendorOptimizationProposalRegistry`, while the default runtime bridge keeps loading only backend-neutral proposal providers. Future vendor modules may consume target device profile, backend compiler feedback, resource metrics, driver quirks, launch advisories, and promotion evidence, but missing modules, missing matching device evidence, or disabled vendor adaptation must leave backend-neutral IR selection unchanged.
- [x] Gate production optimizer selection through approval-bound artifacts.
  `GpuIrOptimizationApprovalManifest` now writes and validates a review-only approval template for one immutable optimizer proposal. It is bound to optimizer id/version, original and optimized `IrGpu` identities, backend target, optimization profile, optional device vendor/label context, proof source/verdict, and rollback requirement, and is intended for `META-INF/javatogpu/ir-optimization-approvals/`. A valid manifest remains manual-review-only and does not select optimized IR or grant production mutation by itself; missing, stale, or mismatched approval keeps selection external and fail-closed.
  `GpuIrOptimizationApprovalTemplateFormatter` now bridges proposal evidence to pending approval templates and explicitly returns `not-applicable` for preview/no-change proposals, making the approval boundary visible before applied rewrites exist.
- [x] Publish docs for optimizer authors and users before enabling real rewrites.
  `docs/IR-Optimizer.md` now documents the validator/optimizer/vendor split, proposal-only runtime bridge behavior, backend-neutral and vendor ServiceLoader packaging, approval-template artifacts, approval manifest resource path, and safe default behavior. Runtime and validation docs now point operators to `runtime-ir-optimizer-evidence.properties` and explain that optimizer evidence is report-only: projects that do not add optimizer modules keep the current no-op runtime path, and approval templates do not enable production mutation or selected-IR replacement by themselves.

## Recommended Execution Order

If the goal is to move forward pragmatically from the current state, the best order is now:

1. `A1/A2 NVIDIA/AMD interim operational validation`
   Keep repeating `:processor:openClOperationalRoutine --rerun-tasks` on the available RTX 3060, RTX 5070, and RX 7800 XT stacks until Intel hardware exists, preserving validation history, workload summaries, long-running summaries, and benchmark output.
2. `A3/A4 Diagnostics and runtime-stability fixes from real failures`
   Treat any repeated NVIDIA/AMD failure, skipped workload, resource leak, or diagnostic gap as the next concrete implementation target.
3. `I3 Production IR pipeline foundation`
   Start with the non-mutating foundation: canonical `IrGpu` artifact, dual output beside current OpenCL source, OpenCL-from-`IrGpu` parity, runtime compile request/options, backend-lowering boundary, and source/ASM frontends feeding the same IR storage path. Keep runtime optimization profile `off` by default.
4. `I4 Optional IR optimizer module split`
   Before implementing real optimizer transforms, freeze the module boundary: validator stays read-only, backend-neutral optimizer contracts live behind optional dependencies, vendor optimizers are separate providers, and all mutation remains proposal/opt-in/fail-closed until proof and rollback are present.
5. `A1 Intel runner bring-up when hardware exists`
   The remaining cross-vendor production gate stays open until an Intel OpenCL stack can run the same bucket set.
6. `Improved ASM parser/frontend`
   Broader ASM ingestion should lower into `IrGpu` first, then reuse the same runtime compile request, validation, backend lowering, and future optimizer path instead of growing a separate pipeline. The first broader-ASM diagnostics layer is already in place through `asmFailure.*` metadata and public preflight APIs.
7. `I3/I4 prototype runtime optimization`
   After `IrGpu` storage and OpenCL parity are stable, add opt-in prototype optimization with rollback, pre/post runtime-equivalence artifacts, and NVIDIA/AMD evidence first. Keep production mutation disabled until A1/A2 confidence and the future Intel gate are satisfied.
8. `H Lower-priority backend/optimization work`

JavaToGpu is already beyond the "toy compiler" stage.

The broad repetitive intrinsic-family generation detour is now closed for current priorities, so the active focus returns to production-core/runtime validation rather than expanding optional API symmetry.
