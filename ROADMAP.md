### A6. OpenCL practical 90% release track

Goal: make the OpenCL path feel complete for most practical alpha users before the next public release without painting the runtime into an OpenCL-only corner. This track prioritizes backend-neutral runtime selection, user-facing runtime control, debuggability, examples, and polished common workflows over broad low-level OpenCL API symmetry. OpenCL is the first complete adapter; CUDA, Vulkan/SPIR-V, and Metal should plug into the same selection and evidence model later.

- [ ] Add a backend-neutral runtime backend selection orchestrator.
  Build the public selection layer above individual backend adapters: discover available backend families, evaluate user policy and method/device constraints, rank backend candidates, select a backend + device pair, and fall back predictably when a backend is unavailable. The initial production implementation may only have OpenCL as a real backend, while CUDA/Vulkan/Metal adapters can report explicit unsupported diagnostics through the same contract.
- [ ] Add user-facing backend selection controls.
  Expose controls for forcing a backend target, setting backend preference order, requiring backend features, selecting fallback behavior, and keeping selection deterministic. This should build on `GpuBackendTarget`, `GpuRuntimeBackendPolicy`, backend lowerers, and runtime device-selection artifacts rather than adding OpenCL-only flags.
- [ ] Add user-facing OpenCL device selection controls as the first adapter implementation.
  Expose backend-neutral controls for forcing a device, preferring a vendor/device class, excluding CPU OpenCL or iGPU devices, and configuring startup self-tests. These controls should reuse the existing runtime device-selection/profile machinery, be recorded in compile provenance and runtime artifacts, and avoid enabling automatic Multi-GPU partitioning by default.
- [ ] Add backend/device discovery and selection explanation APIs.
  Provide a small API/CLI/example that lists available backend adapters, detected platforms/devices for each backend, capability facts, self-test state, rejection reasons, ranking adjustments, fallback decisions, and the final selected backend/device. The goal is for users to answer "why this backend and GPU?" without opening raw validation artifacts.
- [ ] Add method-level GPU test-vector metadata for backend/device selection evidence.
  Introduce a future annotation surface such as `@GPUTest` / `@GPUTestCase` that binds representative input arguments and expected output arguments to a specific `@GPU` method. These vectors should let the runtime validate a candidate backend/device against the actual kernel shape, collect per-method correctness and optional timing evidence, and feed backend/device ranking without requiring users to hand-write separate selection probes for every workload.
- [ ] Define the `@GPUTest` authoring and serialization contract.
  Keep the first form deliberately narrow: primitive scalars, primitive arrays, vector arrays, simple structs, tolerance metadata for floating outputs, named fixtures for larger data, and explicit output-argument matching. Avoid arbitrary Java object graphs or hidden side effects. Persist test-vector identities and results in `IrGpu` metadata, runtime selection artifacts, lifecycle journals, and validation reports so a chosen backend/device can be audited later.
- [ ] Use method-specific GPU tests as opt-in selection probes.
  Backend selection should first use cheap capability/profile/self-test evidence, then optionally compile and run `@GPUTest` probes when the user requests stronger placement confidence. Failing probes reject that backend/device for the method; passing probes can improve confidence or ranking. Probe execution must be bounded, cacheable by method/backend/device/driver identity, and safe to skip in low-latency startup modes.
- [ ] Add an optional compile/runtime lifecycle journal end-to-end.
  Record descriptor loading, `IrGpu` loading, validation, optimizer-provider discovery, proposal execution, runtime-equivalence/review-package state, backend source selection, OpenCL build, fallback/rollback, invocation, and shutdown. The journal must stay opt-in, ServiceLoader-friendly, and safe for normal applications.
- [ ] Polish common image host-helper workflows.
  Keep the existing kernel image coverage, but improve the user-facing host API and examples for the common 2D/3D float/int/uint/RGBA8 workflows, including create/upload/readback helpers, format diagnostics, and vendor-validation coverage. Unsupported image families should remain explicitly documented rather than partially hidden behind confusing helpers.
- [ ] Add a friendlier launch configuration layer.
  Wrap the existing 1D/2D/3D `GpuExecutionConfig` support in a more discoverable public API and examples for global sizes, local sizes, work-group attributes, generated launcher helpers, and common validation failures such as oversized local groups or non-preferred multiples.
- [ ] Evaluate a narrow `@GPU` return-value convenience layer.
  Keep real entry-point lowering output-buffer based, but explore a small source/API convenience for scalar or single-output kernels that lowers to an explicit output holder/buffer. Do not generalize this into arbitrary non-`void` GPU entry semantics until helper reuse, launcher ABI, and diagnostics stay simple.
- [ ] Add a practical OpenCL release example suite.
  Build a curated examples-app path that covers arrays, scalar parameters, vectors, structs, packed/root-blob views, images/samplers, device selection, lifecycle journal, optimizer artifact dumps, and CPU-reference checks. This should become the user-facing proof that the common OpenCL path is coherent.
- [ ] Keep Intel OpenCL bring-up as the remaining 90% confidence gate.
  NVIDIA and AMD are the active alpha confidence lanes. Intel should remain a separate hardware-runner track; once hardware exists, run the same operational routine and record quirks before claiming broad cross-vendor OpenCL confidence.
- [ ] Avoid expanding OpenCL surface symmetry without workload evidence.
  New builtins, image families, vector widths, or low-level qualifiers should be added when a real workload, example, or diagnostic gap requires them. The next release should feel better because common paths are easier to use and debug, not because every OpenCL C corner has a Java facade.

### F1. Remaining blockers for full large-workload Java-source parity

The current large-workload dogfooding target is now mostly aligned with existing JavaToGpu concepts, but a full source-level Java port still needs a few focused pieces:

- [x] Add 3D runtime launch support end-to-end.
  The reference kernels use `get_global_id(2)` / `get_global_size(2)` and 3D NDRange layouts. `GpuExecutionConfig` now supports `globalZ` / `localZ`, the OpenCL backend can enqueue 3D NDRanges, generated launchers expose explicit config and 3D work-size overloads, and targeted regression coverage exercises the 3D runtime path.
- [x] Add or formalize the Java authoring path for union-style packed views.
  Some source workloads use C `union` overlays inside packed structs such as weighted lookup nodes and compact search-tree nodes. The source-level policy remains no general Java union support; the practical path is now an explicit packed/blob overlay pattern using byte-root pointer views and `read*At(byteOffset)` helpers, with overlay regression coverage for reading alternate `uint32_t` / `int16_t` views from the same packed node layout.
- [x] Improve generic root-blob pointer ergonomics for this style of code.
  Large packed-data kernels often use `global const void *`, `global void *`, pointer-shift helpers, typed reinterpret casts, `restrict`, and `const` combinations. Existing byte-root typed views now have direct `read*At(byteOffset)` and `*PtrAt(byteOffset)` helpers, so root-blob schemas can express offset-driven typed views without repeating `root.add(offset).asTypePtr()` boilerplate for every field.
- [x] Define the source-level policy for preprocessor/debug/trap constructs.
  The file relies on `#ifdef` / `#define` feature gates, `DEBUG`, `DF_COMPILE_*`, `printf`, and `__builtin_trap()`. The Java frontend policy is now explicit: preprocessor feature gates and debug printing remain build/configuration or low-level concerns, while source-level fail-fast paths use `GPU.trap()` and `GPU.unreachable()` as deliberate Java-side replacements for `__builtin_trap()` / `__builtin_unreachable()`.
- [x] Validate kernel attributes together with 3D launch semantics.
  Attribute support exists, and the reference file includes launch-sensitive attributes such as `reqd_work_group_size(8, 8, 1)`. NVIDIA can initially prefer scalar-friendly OpenCL/CUDA lowering, AMD/Intel dGPU can opt into vector-friendly rewrites when runtime evidence supports it, and iGPU targets can apply memory-coherency / shared-memory policies that account for unified memory and lower transfer overhead. - [x] Add explicit OpenCL device discovery and selection policy.
  OpenCL now enumerates all platforms/devices before context creation, classifies dGPU/iGPU/CPU candidates, applies deterministic scoring and extension policies, supports explicit backend-neutral overrides, and emits `runtime-device-selection.properties`.   `@GPUDeviceConstraint` declares supported backends, vendor families, device classes, and required features. Java and ASM compilation paths normalize the annotation into per-method `IrGpuMethodDeviceConstraint` metadata. Runtime device selection loads the IrGpu artifact before OpenCL context creation and rejects incompatible candidates through `GpuRuntimeMethodDeviceConstraintPolicy`; no compatible device produces `GpuRuntimeDeviceSelectionException` instead of compiling unsupported code.
- [x] Add deterministic fallback method variants.
  `@GPUFallbackVariant` now declares a logical group, stable variant id, priority, and compatibility note. Generated launchers carry variants compiled in the same annotation-processing run, while the runtime registry adds variants exported by dependency modules. OpenCL selects a compatible `descriptor + device` pair before ABI marshalling or context creation. Device policy, `@GPUDeviceConstraint`, required features, backend support, and explicit device overrides remain hard constraints. Selection prefers the best compatible device score first, then variant priority, then stable variant/resource identities, and records selected/skipped variant diagnostics in runtime device-selection evidence. Variants must expose the same parameter type/access ABI. Active OpenCL sessions only consider the already selected device and never switch hardware silently.
- [x] Add cross-module fallback variant discovery.
  The annotation processor generates one `GpuRuntimeMethodVariantProvider` per fallback owner plus the standard `META-INF/services` registration. `GpuRuntimeMethodVariantRegistry` loads providers through the generated launcher's classloader, validates provider identities and variant registrations, merges dependency variants with launcher-local descriptors, sorts them deterministically, and fails closed on conflicting `groupId + variantId` registrations. External kernel source and `IrGpu` metadata remain lazy classpath resources. Classpath and automatic-module packaging are covered; strict JPMS named modules may still require an explicit `provides GpuRuntimeMethodVariantProvider with ...` bridge because annotation processors cannot safely rewrite `module-info.java`.
- [ ] Add backend-neutral GPU annotation facade before CUDA/Vulkan/Metal expansion.
  The public source API should avoid making OpenCL-specific annotations the primary way to describe portable GPU intent. Introduce backend-neutral annotations for common concepts such as kernel entry (`@GpuKernel` or a future alias of `@GPU`), global/constant/local memory spaces, required or preferred work-group size, unroll policy, fast-math policy, backend/device constraints, and optional fallback variants. Backend-specific lowerers should translate those neutral annotations into OpenCL attributes/qualifiers, CUDA launch metadata, Vulkan/SPIR-V execution modes, or Metal attributes where possible, and emit a clear diagnostic when a neutral concept has no safe mapping for the selected backend.
- [ ] Freeze the public `GPU` facade as the single OpenCL-style source dialect.
  Public source-level APIs such as `net.sixik.ga_utils.javatogpu.api.GPU` should intentionally keep OpenCL-style syntax and naming for intrinsics, work-item queries, vector helpers, memory concepts, and math functions. Future CUDA, Vulkan/SPIR-V, and Metal support should be implemented as backend lowerers and runtime planners behind the same source dialect, not as parallel CUDA-style, Vulkan-style, or Metal-style Java APIs. This keeps user code, docs, examples, diagnostics, and IR metadata consistent while still allowing backend-specific lowering and optimization internally.
- [ ] Keep backend-specific attributes and qualifiers as explicit escape hatches.
  Existing low-level surfaces such as `@OpenCLAttributes` and `@OpenCLQualifiers` should remain available for expert OpenCL-only code, but they must be modeled as backend-specific metadata rather than portable intent. The compiler should reject or ignore them fail-closed when compiling for CUDA/Vulkan/Metal unless the method is explicitly constrained to OpenCL, and diagnostics should suggest the backend-neutral replacement when one exists, for example a neutral work-group-size annotation instead of raw `reqd_work_group_size(...)` or a neutral memory-space annotation instead of backend-only pointer qualifiers.
- [x] Persist backend-neutral annotation intent in `IrGpu` storage for portable attribute metadata.
  `kernel.irgpu.properties` now carries normalized `attributeMetadata.*` records for modeled portable concepts such as required/preferred work-group size, vector type hints, packed/aligned layout metadata, and always-inline helper intent. Java source parsing, frontend OpenCL emission, runtime `IrGpu` source assembly, and validator checks all project this metadata through `OpenClAttributeProjection`, while legacy `openClAttribute.*`, `@OpenCLAttributes`, and `@GPUAttribute` remain compatibility/escape-hatch surfaces. Remaining future work is to extend the same normalized model to any additional annotation intent such as unroll policy or backend-specific raw selector metadata.
- [x] Persist method device constraints in `IrGpu` storage.
  `kernel.irgpu.properties` now carries `methodDeviceConstraint.*` records with method/emitted names, supported backends, supported vendors, supported device classes, required features, and metadata source. Serializer/parser round trips preserve the contract, and Java plus ASM paths use the same normalized model.
- [x] Persist fallback groups and native-code compatibility notes in `IrGpu` storage.
  `kernel.irgpu.properties` now carries `methodFallbackVariant.*` records with method/emitted names, group id, variant id, priority, compatibility note, and metadata source. Serializer/parser round trips preserve the contract, Java and structured-ASM paths share the normalized frontend model, and runtime variant planning consumes it alongside `methodDeviceConstraint.*`. Device/vendor/backend exclusions and capability predicates remain normalized through `@GPUDeviceConstraint` rather than duplicated in fallback metadata.
- [x] Add user-catchable GPU runtime failure hierarchy.

### I4.2 IR-Optimizer v2 core: e-graphs and equality saturation

Goal: move the long-term optimizer core from isolated hand-written peephole conditions to an algebraic optimizer that can reason over many equivalent expression forms at once, then choose the best safe form for the selected backend and policy.

Current rule: keep the existing alpha materializers useful and conservative. The v2 core must plug into the same optional proposal/review/apply pipeline, produce `optimized.*` review artifacts first, and stay fail-closed behind validation, runtime-equivalence, rollback, approval, and production-promotion gates.

- [ ] Define the v2 optimizer boundary as a backend-neutral algebraic expression optimizer.
  The first v2 scope should cover pure expression regions only: local initializers, assignment RHS expressions, return expressions, ternary mask expressions, and intrinsic/math trees with no memory writes, atomics, barriers, volatile effects, or control-flow rewrites. Loops and memory-sensitive transformations should stay outside the first equality-saturation core unless represented as explicitly proven regions.
- [ ] Add typed-IR region extraction for e-graph input.
  Build a deterministic extractor from reachable `ir-tree-v1` nodes into small pure expression regions, carrying node ids, source method/body identity, type information, numeric kind, purity/effect classification, fast-math policy, device/backend context, and original text anchors. Unsupported nodes should become explicit blockers rather than partial rewrites.
- [ ] Introduce an optimizer expression language and rewrite-rule catalog.
  Model literals, variables, arithmetic, comparisons, select/ternary masks, OpenCL-style intrinsics, vector constructors, and safe casts in a compact internal expression form. Seed the catalog with the existing alpha families: constant identities, constant folding candidates, `mad/fma`, `clamp`, `step`, `mix`, safe CSE shapes, and later dot/vector patterns. Every rule must declare semantic guards such as strict-float, fast-math-required, integer-overflow behavior, NaN/equality behavior, and backend availability.
- [ ] Implement the first bounded e-graph saturation engine.
  Add deterministic equality-saturation passes with hard budgets for nodes, e-classes, iterations, time, and per-method work. Saturation must report why it stopped (`fixed-point`, `budget`, `unsupported-node`, `policy-gate`, `proof-blocker`) and must never mutate the original `IrGpu` while exploring alternatives.
- [ ] Add a backend-aware cost model and extractor.
  Choose the best expression from an e-class using a cost model that can prefer `clamp` over `min(max(...))`, `mad` over `mul+add` only when policy permits, `mix` over expanded interpolation when safe, and scalar/vector forms based on backend/device hints. The cost model should be explainable and conservative: if two choices have unclear semantics or proof, keep the original shape.
- [ ] Emit an equality-saturation journal and review evidence.
  Extend optimizer evidence with e-graph-specific fields: region count, e-class/e-node counts, applied rule counts, saturation stop reason, selected extraction cost, rejected lower-cost blockers, semantic guard decisions, and before/after expression summaries. This should feed the future compile lifecycle journal without changing default runtime behavior.
- [ ] Lower selected e-graph expressions back through the immutable proposal pipeline.
  Convert the chosen expression back into typed IR and `ir-text-v1` using the shared graph-patch/materialization boundary, allocate deterministic node ids, regenerate review backend source, validate the transformed artifact, and preserve rollback to the original artifact on any mismatch. The selected runtime IR must remain original unless experimental apply or future production gates explicitly allow mutation.
- [ ] Migrate existing peephole families onto the v2 core gradually.
  Keep alpha materializers as regression or fallback implementations while moving `mad/fma`, `clamp`, `step`, `mix`, constant folding, and safe local CSE into the e-graph rule catalog. Close each migration only when the v2 output matches or improves the current review artifacts and emits equal or stronger evidence.
- [ ] Keep vendor optimization as an overlay, not a hidden mutator.
  Vendor/device-specific optimizer modules should be able to contribute extra rewrite rules, backend availability metadata, and cost-model weights, but they must still use the same e-graph proof/evidence path, proposal contract, approval manifests, and fail-closed runtime selection gates.
- [ ] Add v2 regression fixtures from real generated kernels.
  Build fixtures that prove equality saturation handles equivalent generated forms without ordering-sensitive pass bugs: expanded `mix`, `mad`-lowered interpolation, strict/inclusive `step`, nested clamp trees, repeated common subexpressions, constant/identity chains, and future vector/load patterns. Include negative fixtures for unsafe float reassociation, side effects, unsupported memory access, and budget exhaustion.

## Recommended Execution Order

If the goal is to move forward pragmatically from the current state, the best order is now:

1. `A6 OpenCL practical 90% release track`
   Start with a backend-neutral runtime selection orchestrator and public backend-selection controls, then implement OpenCL device controls as the first real adapter and add backend/device-selection explanation. Add method-level `@GPUTest` vectors as opt-in correctness/performance probes so selection can eventually be based on the actual kernel, not only device capability metadata. After that, add the compile/runtime lifecycle journal, friendly launch helpers, image-host helper polish, and a curated examples-app release suite. This should make the current OpenCL backend feel coherent for normal alpha users while keeping CUDA/Vulkan/Metal pluggable later.
2. `A1/A2 NVIDIA/AMD interim operational validation`
   Keep repeating `:processor:openClOperationalRoutine --rerun-tasks` on the available RTX 3060, RTX 5070, and RX 7800 XT stacks while A6 changes land, preserving validation history, workload summaries, long-running summaries, benchmark output, and device-specific quirks. Intel remains the remaining hardware confidence gate.
3. `A3/A4 Diagnostics and runtime-stability fixes from real failures`
   Treat any repeated NVIDIA/AMD failure, skipped workload, resource leak, confusing device-selection result, image helper failure, launch-shape issue, or lifecycle-journal gap as the next concrete implementation target.
4. `I3 Production IR pipeline foundation`
   Start with the non-mutating foundation: canonical `IrGpu` artifact, dual output beside current OpenCL source, OpenCL-from-`IrGpu` parity, runtime compile request/options, backend-lowering boundary, and source/ASM frontends feeding the same IR storage path. Keep runtime optimization profile `off` by default.
5. `I4 Optional IR optimizer module split`
   Before implementing real optimizer transforms, freeze the module boundary: validator stays read-only, backend-neutral optimizer contracts live behind optional dependencies, vendor optimizers are separate providers, and all mutation remains proposal/opt-in/fail-closed until proof and rollback are present.
6. `I3.7 Core extension hooks, lifecycle events, JavaDocs, and QOL`
   Before adding more optimizer complexity, harden the Core extension surface: lifecycle event bus, safe hook points, extension patch packs, example modules, JavaDocs, test harnesses, and friendlier diagnostics. This lets users observe, customize, and replace parts of the library deliberately without maintaining forks.
7. `I4.2 IR-Optimizer v2 e-graph core`
   After the current alpha optimizer remains useful in review/apply mode, start the v2 algebraic core on pure expression regions only: typed-IR extraction, guarded rewrite catalog, bounded equality saturation, backend-aware cost model, review evidence, and immutable proposal lowering. Keep existing peephole materializers as fallback/regression fixtures until each family migrates safely.
8. `A1 Intel runner bring-up when hardware exists`
   The remaining cross-vendor production gate stays open until an Intel OpenCL stack can run the same bucket set.
9. `Improved ASM parser/frontend`
   Broader ASM ingestion should lower into `IrGpu` first, then reuse the same runtime compile request, validation, backend lowering, and future optimizer path instead of growing a separate pipeline. The first broader-ASM diagnostics layer is already in place through `asmFailure.*` metadata and public preflight APIs.
10. `I3/I4 prototype runtime optimization`
   After `IrGpu` storage and OpenCL parity are stable, add opt-in prototype optimization with rollback, pre/post runtime-equivalence artifacts, and NVIDIA/AMD evidence first. Keep production mutation disabled until A1/A2 confidence and the future Intel gate are satisfied.
11. `H Lower-priority backend/optimization work`

## Current Working Conclusion

JavaToGpu is already beyond the "toy compiler" stage.

The broad repetitive intrinsic-family generation detour is now closed for current priorities, so the active focus returns to production-core/runtime validation rather than expanding optional API symmetry.

After the first serious dogfooding pass, the main repo-local language/runtime gaps for the selected workload classes are no longer the active blocker. Section C and F1 are closed for current practical workload coverage: 3D launch config, union-style packed views, root-blob ergonomics, launch-sensitive attributes, and the focused packed/root-blob dogfooding slice are all covered. Operational confidence now includes NVIDIA and AMD lanes; Intel remains the remaining hardware validation gap. The next release should therefore focus on A6: a backend-neutral runtime selection orchestrator, public backend/device controls, OpenCL as the first complete adapter, selection explanation, method-level `@GPUTest` probes for kernel-specific placement evidence, lifecycle/compile journaling, friendlier launch helpers, common image-host helper polish, and curated examples that prove the common OpenCL path end-to-end. After that practical OpenCL 90% track is solid, the next major architecture frontier remains the I3 Production IR pipeline plus the I4 optional optimizer split: `IrGpu` should become the stored backend-neutral artifact, OpenCL/CUDA/Vulkan/Metal should become backend lowerers selected at runtime from compile options and device profile, `ir-validation` must remain read-only, and future `ir-optimizer` / `ir-vendor-optimizer` modules should plug in as optional proposal/opt-in/fail-closed providers. Before adding another wave of optimizer logic, the Core extension surface should become a first-class product feature: lifecycle events, safe hook points, extension packs, JavaDocs, examples, and QOL diagnostics should let users observe, customize, and replace parts of the library deliberately without maintaining forks. The current rule-based IR-Optimizer alpha is a useful evidence/materialization layer, but the long-term v2 core should become an e-graph / equality-saturation optimizer for pure algebraic expression regions so broad generated-form optimization does not devolve into ordering-sensitive hand-written tree conditions. Broader ASM ingestion should feed that same `IrGpu` path instead of creating a second compiler pipeline.

Latest I2/L2 reconciliation: the current CI contract layer is closed for present priorities. Direct contract coverage now pins current readiness CI summaries, optimizer-gate consistency/acceptance, optimizer CI gate-index consistency/acceptance, regression/baseline CI summaries, nested artifact-field composition, and opt-in real-example dogfooding reports for `examples-app` / `test-app`. The dogfooding contract keeps safety fail-fast while treating optimizer readiness as a read-only stability artifact: production mutation must remain disabled, rewrite applicability must stay false, known CSE policy blockers are counted, and no-candidate CSE literal-promotion / auto-vectorization blockers are accepted as the current baseline. The remaining I2 items are intentionally broader frontier work: deeper transformation-safety proofs, stronger canonicalization/common-computation detection, runtime-equivalence evidence for selected optimizer families, and eventual production rewrite promotion after A1/A2 runtime confidence is stable. These should stay open until backed by runtime evidence rather than being marked complete from read-only artifact coverage alone.
