## 1. Что строим

**В одном абзаце.** Пользователь пишет GPU-код на Java (строго подмножество, не произвольный код); библиотека на этапе
сборки превращает его в компактный бинарный IR, а в рантайме (JIT) генерирует OpenCL C под конкретное устройство,
компилирует, кэширует и запускает. Если GPU нет — тот же метод выполняется на JVM. Архитектура рассчитана на будущий
перенос ядра на Rust (AnyToGpu) без переписывания дизайна.

**Ключевая боль, ради которой всё затеяно:** адаптация кода под разные видеокарты (AMD / NVIDIA / Intel) и распределение
работы между несколькими, в т.ч. разнородными GPU. Это **будущие планы** (разд. 8), в v1 закладываются только швы.

### Цели v1

| ID | Цель                                                                                                                 |
|----|----------------------------------------------------------------------------------------------------------------------|
| G1 | Метод с `@Kernel` на Java-подмножестве работает на OpenCL-устройстве через обычный вызов `K.f(a, b)`                 |
| G2 | Единственный канонический, сериализуемый, детерминированный IR (контракт Java↔Rust)                                  |
| G3 | Строгая диагностика на этапе компиляции (`GPU####`, позиция в исходнике, подсказка)                                  |
| G4 | Корректность проверяется без железа: IR-интерпретатор + golden-файлы + JVM-эталон                                    |
| G5 | JVM-fallback и `@GPUTest`: тот же метод и тесты работают без GPU                                                     |
| G6 | Простая модульная структура с проверяемыми границами; никакого over-engineering                                      |
| G7 | Возможности v1: скаляры, массивы, векторы, `@Struct`, pointer-типы, local memory, `barrier`, atomics, helper-функции |

### Не-цели v1 (сознательно НЕ делаем)

Оптимизатор (e-graph), CUDA/SPIR-V/ROCm-эмиттеры, ASM-фронтенд, images/samplers, async-API, multi-GPU,
Benchmark/AutoTune, вендорная адаптация кодгена, `@GpuNative`, разбиение одного запуска между картами. В языке: объекты
и куча, виртуальные вызовы, исключения, рекурсия, мониторы, labeled `break/continue`, `try/finally`, `assert`, строки.

## 2. Нерушимые принципы (проверьте себя перед каждым коммитом)

1. **Данные плоские (DOD).** IR и все таблицы ядра — SoA на примитивных массивах (`int[] op, type, a, b, c` + боковые
   таблицы). Ссылки — целочисленные id, не объекты. Строки интернируются. Никаких `Object`-графов, `Map<String,String>`
   как модели, reflection, иерархий узлов.
2. **Логика — статические функции над данными.** Запрещены
   `Registry / Factory / Provider / Service / Catalog / Contributor / Hook`-паттерны в ядре. Разрешены ровно три точки
   расширения: `Backend`, `OptimizerPass`, `EventListener` (разд. 10 архитектуры).
3. **Нет глобального изменяемого состояния в ядре.** Контекст (`GpuContext`) — явный объект. Единственное
   «ambient»-место — тонкий хост-фасад пользователя (ленивый default-контекст + scoped override).
4. **Ошибки — значения.** Ядро (`ir`, `codegen-opencl`, `ir-interpreter`, `runtime`-core) возвращает `Result`/список
   `Diagnostic` (код + позиция + сообщение + подсказка). Исключения — только на публичной границе (`GpuException` с
   полным отчётом) и во фронтенде для javac `Messager`.
5. **Детерминизм.** Один и тот же вход → побайтово тот же IR, хэш и OpenCL C. Нет зависимости от порядка `HashMap`,
   `String.hashCode`, времени, пути.
6. **Один канонический IR.** Запрещены текстовый IR, обратный парсинг IR в исходник, параллельные представления.
   Текстовый дамп (в `tools`) — только для людей и golden-тестов, в IR не парсится обратно.
7. **IR vendor-neutral и backend-neutral.** Вендорная/бэкендовая специализация — только на выходе, в кодгене (
   `emit(IrModule, Target)`).
8. **Нет кастов в IR и в исходнике ради типов.** Знак — метка типа; опкоды полиморфны; неявных приведений нет; `convert`
   только явный. Касты к `unsigned` допустимы лишь внутри сгенерированного C (чтобы дать Java-семантику).
9. **Java-семантика целых и `float→int` гарантирована контрактом IR** (оборот знаковых, маскирование сдвигов, насыщение,
   NaN→0); деление на ноль — «не определено, без падения».
10. **JVM ≡ GPU по конструкции.** Подмножество языка и валидатор исключают расхождения (векторы immutable; `@Struct` без
    aliasing). Float сравнивается «в ULP» из таблицы builtins, точного равенства не обещаем.
11. **Платформа:** Java 25, FFM (`java.lang.foreign`) для OpenCL, **без LWJGL** и сторонних нативов. ASM — только в
    `weaver`.
12. **Границы модулей проверяются сборкой.** Не обходите `verifyModuleBoundaries` — меняйте граф осознанно (и запись в
    `REWORK_ARCHITECTURE.md`, разд. 11).
13. **Единый источник истины.** Builtins — один декларативный файл; `Gpu.java`, типы и таблицы **генерируются**, руками
    не правятся.
14. **Каждый новый узел IR / правило / публичный метод — с тестом**, и узел IR сразу в трёх местах: валидатор,
    интерпретатор, кодген.

## 3. Архитектура кратко

```
[Сборка пользователя]   @Kernel Java  --frontend-java (javac Tree API)-->  IR (бинарный, колонками) в ресурсах
                                       --weaver (ASM)-->  тело метода → делегат хост-фасаду; оригинал → <name>$jvm

[Выполнение]            вызов K.f(a,b) → хост-фасад → GpuContext
                        IR → (optimize: identity в v1) → codegen-opencl: emit(IrModule, Target) → OpenCL C
                        → компиляция драйвером → кэш (память + диск) → запуск → результат
                        нет устройства → JVM-fallback поверх <name>$jvm
```

## 5. Глоссарий

- **IR / IrModule** — канонический бинарный образ GPU-программы: таблицы типов, узлов, функций, строк, констант + секция
  `debug`.
- **kernelId** — `hash(IR без debug)`.
- **Узел** — строка таблицы `nodes` (`op,type,a,b,c`); id = индекс; операнды всегда с меньшим id.
- **Открытый узел** — читает локаль или память (`local_get`, `load`, …); у него ровно один родитель. **Закрытый** —
  константа/параметр/чистая арифметика над закрытыми; им можно делиться.
- **Target** — `{backend, vendor, deviceClass, features, subGroupSize, computeUnits, …}` из `DeviceInfo`; вход кодгена и
  часть ключа кэша.
- **DeviceInfo** — vendor, name, driver, features, sub-group size, compute units, memory.
- **required_features** — битовая маска возможностей (fp64, int64-atomics, fp16…), считает валидатор IR; проверяется до
  компиляции.
- **uses_group_sync** — функция использует `barrier` или local memory (транзитивно); такие ядра не уходят в
  JVM-fallback.
- **`<name>$jvm`** — оригинальное тело `@Kernel`-метода (один work-item), сохранённое weaver'ом: JVM-fallback и эталон
  тестов.
- **KernelSample** — генератор аргументов + опциональные ожидаемые результаты; общий для `@GPUTest` (v1) и AutoTune (
  позже).
- **KernelGroup** — (зарезервировано) варианты одного ядра с одной ABI.
- **golden-файлы** — эталонные текстовые дампы IR и OpenCL C; будущая конформанс-сюита для Rust-версии.

## 7. Вехи v1

Стратегия: **тонкий вертикальный срез** (M1–M7: baseline-ядро от исходника до запуска), затем **ширина** (M8–M13: по
одной возможности, каждая — расширение IR → интерпретатор → кодген → рантайм → тесты). Всегда есть работающая сборка.

Baseline-подмножество среза: скаляры, массивы, `if/for/while/do-while/switch`, арифметика/сравнения/логика/тернарный,
helper-вызовы, builtins, `FloatPtr` — позже (M9).

### M0 — Сброс `[x]`

Тег `legacy-alpha5`; старый код удалён; скелет из 10 модулей; Gradle 9.8.1, JDK 25, JUnit 6.1.3, ASM 9.11.1;
`verifyModuleBoundaries` (проверено негативными тестами). Коммит `5ce86b90`.

### M1 — Модуль `ir` `[x]`

**Цель:** канонический IR, валидатор и сериализация — без единой зависимости. Фундамент всего остального.

**Сделано** (`ir/src/main/java/com/sixik/gpu/ir`):

- Таблица типов (`Types`, `AddressSpace`): фиксированные id скаляров `0..11` (+`VOID`), `12..15` зарезервированы;
  динамические `Vec`, `Ptr`, `Array`, `Struct` (с `align`) с дедупликацией, struct номинальны.
- SoA-таблицы (`IrModule`): `nodes` (`op,type,a,b,c`), пул списков, 64-битные константы (≤32 бит и `f32` — прямо в
  колонке `a`), семантические строки, таблица функций (18 колонок: kind, параметры, локали, `reqd_wg`, `inline`, `opt`,
  `required`, `body_kind`, `fallback`, `tune_*`). Каталог опкодов `Op` (≈55) и единая схема операндов `Operands`.
- `IrBuilder`: типизированные методы со своим выводом типов, детерминированная нумерация (операнды раньше узла),
  отладочные имена и позиции (`DebugInfo`).
- `Validator`: **все правила 5.12** (`IR-S/T/V/E/C/M/F/B`) + вычисление `required_features`, `uses_group_sync`, режимов
  доступа параметров, эффектов; возвращает `Diagnostic`, **не бросает исключений даже на мусорных данных**.
- `IrBinary`: колоночный формат `"GIR\0"`, секции `TYPE STRS CNST NODE LIST FUNC DBUG`; `hash`/`kernelId` (SHA-256) без
  `DBUG`; чтение возвращает `Result` (`IR-S05` версия, `IR-S06` повреждение).
- `AbiLayout` (O4): size/align/offset по правилам OpenCL C, `float3` = 16 байт.
- `Builtins` (O1, часть): `builtins/builtins.def` в корне репозитория упаковывается в ресурсы `ir` и читается в
  рантайме;
  15 builtins (индексы, математика, `assumeUniform`, `atomicAdd`); сигнатуры проверяются по классам `genf/geni/genn`.
- `tools`: `IrDump` — текстовый дамп (с/без отладки) + golden-тесты. `ir`: `testFixtures` (`Fixtures.computeSine()`,
  `Fixtures.rich()`) для тестов следующих модулей. JMH: `gradle/jmh.gradle`, `ir/src/jmh`.

**Критерии приёмки:**

- [x] Тест на каждое правило `IR-S/T/V/E/C/M/F/B` — 107 тестов валидатора; мутационная проверка: отключение правила

### M4 — Модуль `ir-interpreter` `[x]`

**Критерии приёмки:**

- [x] **дифференциальные тесты**: на 20 образцах-ядрах результат интерпретатора совпадает с прямым вызовом оригинального Java-метода по
  work-item'ам (целые и логика — точно, `float/double` — побитово либо в ULP там, где задан допуск); если JVM бросила исключение,
  интерпретатор обязан отказать;
- [x] крайние значения: все пары `MIN/MAX/0/±1` и случайные пары для `int` и `long`, `NaN`/`±Inf`/`±0` и границы насыщения для

- [x] нет зависимостей кроме `ir` (production); `api` и `frontend-java` подключены только к тестам; `verifyModuleBoundaries` зелёный;
- [x] мутационная проверка вручную: сдвиг без маски, потеря «липкого» бита `U64→F64`, знаковое деление для `U32`, убранный `NaN→0`,
  беззнаковое расширение/сдвиг/сравнение, жадный `select`, `continue` мимо шага обновления, `switch` без проваливания, непереобнулённый
  приватный массив, перепутанные `max/min`, неосвобождаемые приватные массивы, перепутанные `local/group id`, потеря нулевого
  расширения `U8` — все роняют тесты (выжившая мутация про освобождение буферов породила тест `manyCalls`).

**Решения, принятые в M4** (подробности — `REWORK_ARCHITECTURE.md`, 5.16): значение — один `long` на скаляр, указатель — `(буфер, индекс)`;
**целое деление на ноль — ошибка `IN-R02`** (строже IR, чтобы тест не принял случайное значение); **`float→byte/short/char` — как Java:
насыщение до `int`, затем сужение с оборотом — кодогенератор M5 обязан совпасть**; `atomicAdd` исполняется последовательно; JMH не
добавлен — интерпретатор не на hot path.

**Не входит:** `barrier`, `local_array_decl` (M10), `local_addr`, `field_ptr` (M9), векторы и структуры (M8), `spec_const`, нативные тела —
все дают `IN-U01`; параллельное исполнение work-item'ов; сверка с реальным устройством (M6+).
**Опирается на:** 5.10, 8.3, 13.

- `gradle-plugin` (`io.github.deussixik.javatogpu`): зависимости и annotation processor, weave-шаг после `JavaCompile`, `--enable-native-access=ALL-UNNAMED` для
  `Test`/`JavaExec`; блок `gpu { version, group, autoDependencies, weave, extraJvmArgs }`.
- `runtime`: хост-фасад `JavaToGpu` (**O2 закрыт**): ленивый контекст по умолчанию + shutdown hook + `configureDefault`, `use(ctx)`, `launch(LaunchConfig)`,
  `invoke(...)`; JVM-fallback поверх `$jvm`; `GpuContext.Fallback {ALLOWED, NEVER}`, событие `FALLBACK`.
- `testFixtures` weaver: `KernelCompiler` (javac in-process с processor'ом frontend-java).
- Тесты: 13 (weaver) + 16 E2E без железа (runtime) + 6 TestKit (плагин) + `WovenKernelDeviceTest` (`./gradlew :runtime:deviceTest`).

**Критерии приёмки:**

- [x] TestKit-проверка плагина на тестовом проекте: сборка, weave, запуск `runDemo`, up-to-date и повторная компиляция, выключатели `weave` и `autoDependencies`,
  аргументы JVM, регистрация расширения;
- [x] байткод-тест weaver'а: оригинал сохранён как `$jvm` (те же сигнатура, флаги, число инструкций; без аннотаций), делегат вызывает фасад с верными константами
  и упаковкой, `@Kernel` и аннотации параметров остаются на делегате, идемпотентность, класс загружается и проходит верификацию;
- [x] E2E `@Tag("device")`: `computeSine` запускается обычным вызовом на реальном OpenCL (NVIDIA GeForce RTX 5070, режим `NEVER`) и совпадает с `Math.sin` и с `$jvm`
  в пределах 4 ULP;
- [x] E2E без железа: weave + IR-ресурс присутствуют, обычный вызов исполняется на `FakeDeviceApi` и на JVM-fallback (устройства нет / драйвер отверг ядро);
- [x] мутационная проверка вручную (18 мутаций weaver'а, фасада, контекста и плагина: слоты `long/double`, аннотации на `$jvm`, идемпотентность, static/void,
  `kernelId`, упаковка, дескриптор в индексе, `NEVER`, `usesGroupSync`, размер work-group в fallback, пропуск последнего work-item'а, размер по умолчанию, порядок
  областей, повторные попытки, повторные предупреждения, переключатель weave, `--enable-native-access`) — все роняют тесты. Две слабости тестов найдены и закрыты:
  кэш фасада по `kernelId` (дефект, исправлен) и проверка флага по подстроке вывода (JDK сам упоминает флаг в предупреждении).

**Решения, принятые в M7** (подробности — `REWORK_ARCHITECTURE.md`, 5.19): имя фасада `JavaToGpu` (O2); делегат вызывает
`JavaToGpu.invoke(Class, String, String kernelId, Object[])`, `kernelId` берётся из `kernels.idx`; кэши фасада привязаны к классу-владельцу (`ClassValue`);
fallback только при отсутствии устройства или отказе компиляции (ошибки пользователя не маскируются), одно предупреждение на ядро; ядра с barrier/local на JVM
не уходят; weave внутри задачи компиляции (up-to-date видит подменённые файлы); размер запуска по умолчанию — длина первого массива.

**Не входит:** выбор `@Kernel(fallback = ...)`-варианта при нехватке возможностей устройства; дисковый кэш и prepared launcher; Maven-плагин и Java-агент;
публикация артефактов; `@Struct` и указатели в сигнатуре ядра (O3, M8/M9).
**Опирается на:** 3.4, 3.6, 3.7. **Открыто:** — (O2 закрыт).

### M8 — Векторы + `@Struct` + ABI `[x]`

**Цель:** векторы и `@Struct` проходят весь путь от исходника до устройства.

**Сделано:**

- `api`: неизменяемые `Float/Int/Long/DoubleN` с операциями (`splat`, `lane`, `with<Lane>`, `shuffle`, арифметика, для целых - побитовые), генерируются из `builtins.def`.
- `ir`: `HostObjects` — соответствие агрегатов IR Java-объектам хоста (листья, смещения по `AbiLayout`, `mismatch`/`flatten`/`rebuild`) (**O3 закрыт**).
- `ir-interpreter`: агрегаты в кадрах и буферах, покомпонентная арифметика и builtins, массивы объектов хоста, агрегаты по значению.
- `codegen-opencl`: `Layouts` (типы, `typedef struct`, swizzle), динамические помощники, векторная арифметика, расширенный набор зарезервированных имён OpenCL.
- `frontend-java`: распознавание векторов/struct, правила value-семантики (`GPU0191..0196`), цепочки записи в поля, методы векторов.
- `runtime`: упаковка и возврат массивов объектов, агрегаты по значению (`setArgBytes`), размер запуска по массиву объектов.

**Критерии приёмки:**

- [x] дифференциальные тесты векторов и struct: JVM (`$jvm`) ≡ интерпретатор на `VectorKernels`/`StructKernels`;
- [x] golden C для векторных и struct-ядер и ручных модулей; каждый модуль компилируется драйвером NVIDIA;
- [x] device-тест массивов struct и векторов: образцы с объектами сравниваются с интерпретатором на реальном OpenCL (NVIDIA GeForce RTX 5070);
- [x] мутационная проверка вручную (15 мутаций: смещения и канонизация листьев, правила свежести, деление на ноль по компонентам, сдвиги, swizzle >4 компонент,
  возврат объектов в хост, `null`-элемент, смещения упаковки, размер аргумента по значению) — все роняют тесты.

**Решения, принятые в M8** (подробности — `REWORK_ARCHITECTURE.md`, 5.20): хост-представление — массивы объектов с упаковкой по ABI (генерируемые аксессоры
отложены); struct обновляется на месте, вектор создаётся заново; значение struct должно быть свежим (`new`, `copy()`, `@DeviceFunction`) — иначе `GPU0193`;
`float3` = 16 байт; все имена OpenCL builtins зарезервированы в `Names`; `GpuBuffer` для массивов агрегатов не поддержан (`RT-A02`).

**Не входит:** `GpuBuffer` массивов агрегатов и плоские аксессоры; `convert`/`bitcast` векторов в Java API; векторы малых элементов; локальные массивы агрегатов;
`new P()` без аргументов в ядре; pointer-типы и `field_ptr`/`local_addr` (M9); проверка на AMD/Intel.
**Опирается на:** 3.2, 5.10–5.12, 5.20. **Legacy (идеи):** `OpenClStructLayout`, `OpenClVectorLayout`, `OpenClValueLayout`, `docs/OpenCL-Data-Model.md`.

### M9 — Pointer-типы и address spaces `[x]`

**Цель:** ссылки `FloatPtr` и явные указатели `Global*/Local*/Constant*Ptr` проходят весь путь от исходника до устройства; `@Global(constant = true)` целиком.

**Сделано:**

- `api`: 12 классов явных указателей `Global|Local|Constant × Float|Double|Int|Long` (`of/get/set/plus`; у `Constant*` записи нет), генерируются из `builtins.def`.
- `ir`: правила `IR-M01/M04`, `local_addr/elem_ptr/field_ptr` были в M1; **исправлено** вычисление режима доступа параметров: указатель, сохранённый в локаль или
  возвращённый, помечает базовый массив читаемым и записываемым (иначе записанные через указатель данные не возвращались бы на хост).
- `ir-interpreter`: адрес - номер ячейки, `STACK` - буфер-стек для `local_addr`, `field_ptr`, арифметика `elem_ptr` по ширине элемента, проверка границ по ширине доступа.
- `codegen-opencl`: типы `__space T*`, `&x`, `&lvalue.f`, `(*p).f`, указатели в параметрах и локалях device-функций.
- `frontend-java`: вид `K_PTR`; ссылка как локаль с `local_addr`, `r.value` (чтение, запись, `op=`, `++`), методы указателей, пространство массива (`GPU0199`); `GPU0122`
  (запись в constant-массив), `GPU0197`, `GPU0198`; `GPU0190` удалён.
- `runtime`: `DeviceInfo.maxConstantBuffer/maxConstantArgs`, проверка `__constant`-аргументов до загрузки данных (`RT-A04`).

**Критерии приёмки:**

- [x] тесты семантики по ссылке (JVM ≡ GPU): дифференциальные `PointerKernels` (JVM `$jvm` против интерпретатора), те же ядра на NVIDIA GeForce RTX 5070 против интерпретатора,
  `PointerDeviceTest` - обычный вызов woven-ядра на устройстве совпал с JVM-эталоном точно и вернул запись через указатель в массив хоста;
- [x] запись в `constant` отклоняется: `GPU0122` во фронтенде, `IR-M01` в валидаторе (для чужих фронтендов), у `Constant*Ptr` метода записи нет; чтение constant-массива и
  превышение `CL_DEVICE_MAX_CONSTANT_BUFFER_SIZE`/`_ARGS` (`RT-A04`) проверены на фейке и на реальном устройстве;
- [x] golden C для `pointers` и `PointerKernels.*`, golden IR `pointers.ir.txt` просмотрены построчно; каждый модуль компилируется драйвером NVIDIA;
- [x] мутационная проверка вручную (21 мутация интерпретатора, кодгена, валидатора, фронтенда, рантайма): все роняют тесты, одна оказалась эквивалентной (дубль проверки) - удалена.

**Решения, принятые в M9** (подробности - `REWORK_ARCHITECTURE.md`, 5.21): ссылка - локаль, чей адрес отдаётся (владелец `new FloatPtr`, без переприсваивания); явный указатель -
значение «массив + смещение», переприсваивается стейтментом, не сравнивается; указатель не бывает параметром ядра; режим доступа через указатель - консервативно чтение+запись;
в интерпретаторе адрес - ячейка, стек значений - особый буфер.

**Не входит:** сквозная проверка `Local*Ptr` на устройстве (нужен `local_array_decl`, M10); `field_ptr` из исходника Java (проверен ручными модулями); `atomicAdd` в Java API (M10);
указатель-параметр ядра; проверка на AMD/Intel.
**Опирается на:** 3.B, 5.5, 5.12, 5.21.

### M10 — Local memory, `barrier`, atomics `[x]`

**Цель:** группы work-item-ов проходят весь путь от исходника до устройства: `@Local`-массивы, `Gpu.barrier()`, атомики.

**Сделано:**

- `builtins.def` и `api`: `Gpu.barrier()`, `Gpu.barrierGlobal()`, атомики `atomicAdd/Sub/Min/Max/And/Or/Xor/Xchg` над `Global*/Local* Int|Long Ptr`; генератор научился указателям в
  сигнатуре и блочным JVM-телам.
- `ir`: флаги builtin `sync` и `ext`, правило `IR-S08` (точка синхронизации - только узел `barrier`), возможность `INT64_EXT_ATOMICS`. Узлы и `IR-B01` были готовы с M1.
- `ir-interpreter`: исполнение по группам, local-массивы на группу (нулями), барьер на сопрограммах (`Coop`: по одному work-item-у за раз, детерминированно), `IN-R05` (группа не
  вышла на один и тот же барьер), остановка группы при нарушении без зависания, семейство атомиков.
- `codegen-opencl`: `__local T имя[N]`, `barrier(CLK_*_MEM_FENCE)`, `atomic_*`/`atom_*`, прагма расширенных 64-битных атомиков.
- `frontend-java`: `Gpu.barrier*` - узел `barrier`; указатель как аргумент атомика; `IR-B01` - `GPU0130` (предупреждение) и `GPU0131` (`-Ajavatogpu.strictBarriers=true`).
- `gradle-plugin`: `gpu { strictBarriers = true }`. `runtime`: проверка local-памяти ядра против устройства (`RT-D04`), `INT64_EXT_ATOMICS` по расширению.

**Критерии приёмки:**

- [x] редукция/тайлинг-примеры в интерпретаторе и на устройстве: `LocalKernels` (редукция с барьером в device-функции, транспонирование 8x8 через тайл, префиксная сумма, гистограмма с
  local-атомиками, глобальные счётчики, 64-битные атомики) - результат совпал с посчитанным на хосте (интерпретатор), с интерпретатором (NVIDIA GeForce RTX 5070), `GroupDeviceTest` -
  обычный вызов woven-ядер на устройстве;
- [x] тесты на `IR-B01`: расходящийся барьер, барьер в вызываемой функции, `assumeUniform`, равномерный цикл с барьером, `strictBarriers` (фронтенд и плагин Gradle);
- [x] golden C для `LocalKernels.*`; каждое ядро компилируется драйвером NVIDIA;
- [x] мутационная проверка вручную: 20 мутаций интерпретатора, кодгена, валидатора, фронтенда, рантайма и плагина - все роняют тесты.

**Решения, принятые в M10** (подробности - `REWORK_ARCHITECTURE.md`, 5.22): групповые ядра не сверяются с `$jvm` (барьер на JVM невыполним), эталон считает хост; ядро с барьером в
JVM-fallback не уходит (`RT-F01`); интерпретатор строже OpenCL (барьер обязан быть общим, local-память обнулена); `__local`-параметры ядра - вне v1.

**Не входит:** `__local`-параметры ядра с размером из launch-конфига; `atomicCmpxchg`, вещественные атомики; подгруппы; проверка на AMD/Intel.
**Опирается на:** 5.5, 5.12, 5.22.

### M11 — Prepared launcher и `GpuBuffer` `[x]`

**Цель:** повторные запуски одного ядра без повторной подготовки; владение памятью вместо флагов-масок.

**Сделано:**

- `PreparedLauncher` (`runtime`) - единственная реализация: `ctx.prepare(kernel, args...)` и `JavaToGpu.prepare(класс, имя, args...)`; аргументы проверяются один раз, буферы под массивы хоста и нативная
  память упаковки создаются один раз; `launch/run(config)`, `set(i, значение)`, `close()`.
- Правила владения: `GpuBuffer` - данные пользователя, ничего не передаётся (static-таблицы, цепочки, пинг-понг); массив хоста - буфер принадлежит запуску, записывается целиком перед запуском, назад
  возвращается только записываемое ядром; скаляры и агрегаты по значению - `set`.
- Привязка аргументов `cl_kernel`: `CompiledKernel.boundTo` - после чужого запуска выставляются все аргументы, иначе только изменённые.
- JMH (`src/jmh` в `runtime`): `FakeLaunchBenchmarks` (накладные расходы библиотеки на фейке) и `DeviceLaunchBenchmarks` (реальное устройство).

**Критерии приёмки:**

- [x] JMH накладных расходов запуска: фейк - 1552 нс (обычный запуск, массивы) против 387 нс (подготовленный), `GpuBuffer` 223 против 151 нс; RTX 5070 - 329 против 125 мкс (1024 элемента), 4416 против
  1467 мкс (1 048 576 элементов); с `GpuBuffer` оба по 30 мкс (время в драйвере);
- [x] тесты владения/освобождения буферов: буферы запуска освобождаются `close()` и закрытием контекста, буферы пользователя не трогаются, повторное закрытие безопасно, нет утечек на фейке, алиасинг массива;
- [x] на устройстве: 20 запусков с меняющимися данными и скаляром и 25 итераций пинг-понга на `GpuBuffer` ровно с 0 переданных байт совпали с расчётом на хосте;
- [x] мутационная проверка вручную: 13 мутаций - все роняют тесты (одна выжившая закрыла слабость теста).

**Решения, принятые в M11** (подробности - `REWORK_ARCHITECTURE.md`, 5.23): массив хоста всегда загружается целиком (как у обычного вызова), экономия - через `GpuBuffer`; подготовленный запуск не уходит
на JVM; `set` не заменяет массивы хоста.

**Не входит:** async-запуск и очереди; пул буферов между запусками; `GpuBuffer` для массивов векторов/struct; проверка на AMD/Intel.
**Опирается на:** 9, 9.5, 5.18, 5.23.

### M12 — Дисковый кэш, политика устройства, Timings, варианты по `required` `[ ]`

Диск-кэш (user-cache dir, ключ = hash IR без debug + версия кодгена + устройство + опции, атомарная запись tmp+rename,

`inline/optLevel` — информативные атрибуты.
**Критерии:** [ ] тесты кэша (попадание/промах/повреждение/инвалидация версией кодгена); [ ] политика на фейковых
устройствах.

### M13 — JVM-fallback и `test-support` `[ ]`

JVM-fallback: последовательный цикл по global id поверх `<name>$jvm` (контекст work-item — O6); `uses_group_sync`-ядра →

источников).
**Критерии:** [ ] все образцы M3–M10 имеют `@GPUTest`; [ ] fallback-тесты без железа; [ ] device-тесты по тегу.

| **ASM-фронтенд**                           | чтение байткода любых JVM-языков                                                                   | IR как контракт                                                                                      | В legacy — `frontend/asm/*`, не подключено к пайплайну                                                                                                                      |

## 12. Быстрый старт для исполнителя (в т.ч. нейросети)

1. Прочитайте разд. 0–2 этого файла и разделы 5, 5.10–5.12 в `REWORK_ARCHITECTURE.md`.
2. Возьмите первую веху со статусом `[ ]` (сейчас **M12**). Работайте только в модулях этой вехи.
3. Перед кодом выпишите узлы/правила, которые затрагиваете, и где они должны появиться (валидатор + интерпретатор +
   кодген).
4. Пишите тест раньше или вместе с кодом; golden обновляйте осознанно.
5. `./gradlew build` → зелёный. Отметьте критерии приёмки вехи и обновите статусы здесь.
6. Если нужное решение не записано или противоречит принципам — **не придумывайте молча**: добавьте вопрос в
   `REWORK_ARCHITECTURE.md` (разд. 15) и сообщите владельцу.
