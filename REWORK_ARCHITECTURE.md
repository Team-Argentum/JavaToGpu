## 0. Исходные положения (со слов автора)

- **Суть продукта (со слов автора):** пользователь пишет GPU-код на родном языке (не произвольный — только
  GPU-подмножество), библиотека превращает его в корректный код. **Ключевая боль — адаптация под разные GPU**:
  runtime-модуль подстраивает код под конкретное железо через `AutoTune` + Benchmark и умеет распределять работу между
  несколькими (в т.ч. разнородными) видеокартами. Подробно — раздел 9A. **Адаптивная часть (AutoTune, Benchmark,
  Multi-GPU, адаптация под вендоров AMD/NVIDIA/Intel) — будущие планы наравне с Rust backend, в v1 не входит**; v1
  закладывает только швы.
- Нужна **полная перепроектировка**, а не рефакторинг. Сначала план того, что библиотека *должна уметь*, потом
  структура.
- Всё, что попадает в план, должно быть продумано до реализации.
- Проект вырос поверх прототипа: из «Java → OpenCL» в замашки уровня SPIR-V (CUDA + ROCm). Структура не была
  спроектирована, а наросла.
- Текущая сложность — результат over-engineering (генерация гейтов/evidence/preflight/CLI «про запас»).
- Ядро проектируется в стиле **DOD**: данные — плоские структуры (struct-подобные классы / массивы), логика — функции,
  принимающие данные. Без глубоких иерархий и реестров.
- Концептуально проект = **AnyToGpu**: языковые фронтенды (парсеры + внедрение в язык) и **вся компиляция в одном месте
  ** (бэкенд на Rust). Сейчас пишем на Java, но так, чтобы перенос на Rust не болел.
- Оптимизатор: идеально — аналог **egg (e-graphs / equality saturation)** из Rust.
- ASM-фронтенд (bytecode): достроить, но **отдельным модулем**; на время рефакторинга **вырезается**.

## 2. Не-цели (что сознательно НЕ делаем)  `[IN PROGRESS]`

**[DECIDED] Не в v1 (в API закладываем место, реализацию не делаем):**

  *не в v1**: это будущие планы наравне с Rust backend (раздел 9A — проработанная заготовка; в v1 закладываются только

- Оптимизатор (e-graph) — отдельный модуль после v1 (раздел 7).
- CUDA / SPIR-V / ROCm-специфичные эмиттеры — после v1 (раздел 8).
- ASM-фронтенд — отдельный модуль, не в v1 (раздел 3).

**[DECIDED] В v1 остаётся:** Timings/статистика (upload/kernel/readback, счётчики кэша) — через `EventListener`.

**Не-цели языка (как и сейчас):** объекты/куча, виртуальная диспетчеризация, исключения, рекурсия, мониторы — внутри
`@GPU` методов не поддерживаются. Перечень допустимого подмножества Java — раздел 5.

*Открытые вопросы:* список проверок subset-валидатора и формат его диагностик.

## 3. Архитектурная схема: фронтенд / ядро / рантайм  `[IN PROGRESS]`

### 3.A Контракт Java-фронтенда и subset (детально)

**[DECIDED] 3.6 Weaver — Gradle-плагин.** `plugins { id 'io.github.deussixik.javatogpu' }` сам подключает зависимости,
annotationProcessor и weave-шаг после `compileJava` (вместо двух ручных блоков в `build.gradle`). Логика подмены —
чистая функция над `ClassNode` в модуле `weaver`; плагин — тонкая обёртка в отдельном модуле `gradle-plugin`. Только
Gradle в alpha (Maven/agent — позже, не меняют `weaver`).

**[DECIDED, делегировано Claude] 3.7 Контекст и фасад.**

- Ядро/runtime принимают **явный `GpuContext`** (раздел 4, правило 4). Глобального состояния в ядре нет.
- Единственное место «ambient»-состояния — пользовательский фасад `JavaToGpu` (модуль `runtime`, тонкий слой): ленивый
  process-wide default-контекст + scoped override на поток `try (var s = JavaToGpu.use(ctx))`. Это необходимо, чтобы
  обычный вызов `K.f(a, b)` через weaver знал, где исполняться.
- Закрытие: shutdown hook на JVM + явный `close()`; прежний ручной `shutdownOpenClSharedCache()` не нужен.

**[DECIDED] 3.8 Когда включается fallback.** Если устройства нет или компиляция ядра на драйвере падает — по умолчанию *
*разрешён**: уход на JVM + одно WARNING-событие в `EventListener` (причина + build log драйвера). В `GpuContext` строгий
режим (`fallback = NEVER`) бросает `GpuException`. Ядра с `uses_group_sync` (3.5) в fallback не уходят — в любом режиме
ошибка «нужно устройство».

**[DECIDED] 3.5 JVM-fallback v1.**

- Fallback = последовательный цикл по global ids поверх `<name>$jvm` (тело одного work-item; JIT JVM). Атомики в
  fallback — обычные последовательные операции.
- Ядра с `barrier` / local memory в fallback **не поддерживаются**: явная ошибка «нужно устройство» с кодом
  диагностики (не молчаливое неверное поведение).
- Для проверки таких ядер без железа служит IR-интерпретатор (только в тестах, не production-fallback).
- Фронтенд помечает в IR-метаданных функции флаг `uses_group_sync` (barrier/local) — по нему рантайм принимает решение.

**[DECIDED] 3.4 Размер запуска.**

- Дефолт: 1D, `global` = длина **первичного** массива/буфера (первый параметр с `@GPUGlobal`, либо явно
  `@GPU(size = "<имя параметра>")`).
- Override — явный: scoped-запуск `Gpu.launch(launch2D(w, h)).run(() -> K.f(a, b))` или
  `prepared.invoke(config, args…)`.
- Никаких generated-перегрузок лаунчеров (`...WithConfig`, `...WithCompileOptions`, …) — прежний комбинаторный взрыв API
  удаляется.

**[DECIDED] 3.3 Неподдерживаемые конструкции — ошибка компиляции.** javac `Messager` error на точном узле исходника,
стабильный код (`GPU0123`), краткая подсказка «что делать». `@GPU` — явный контракт: нарушение = сборка падает. Режима
«молча уйти на JVM» нет. Таблица кодов диагностик — данные, общая для будущих фронтендов/Rust.

**[DECIDED] 3.2 Value-семантика — строго, JVM ≡ GPU.**

- Векторы (`Float4` и др.) **immutable** (final-поля); «изменение» = новое значение.
- `@GPUStruct`: **без aliasing**. Struct-переменная не присваивается другой struct-переменной без явного `copy()`/`new`;
  поля меняются только у локальной переменной или элемента массива в точной форме (`arr[i].x = …` / `p.x = …`).
  Нарушения — диагностика subset-валидатора фронтенда.
- Цель: результат `<name>$jvm` и GPU совпадает по конструкции, а не «по возможности» — иначе `@GPUTest` и JVM-fallback
  бессмысленны.

**[DECIDED] 3.1 Java-типы API — закрытый набор, генерация.** Векторы `(скаляр × lanes)`, `Ptr/Array`-обёртки и константы
генерируются из того же декларативного файла, что и builtins/`GPU.java` (5.7). Фронтенд узнаёт их по таблице, без
аннотационной магии. Пользовательские типы — только `@GPUStruct`. Аннотации
`@GPUVectorType / @GPUPointerType / @GPUVectorOperator` и т.п. удаляются.

**[DECIDED] Граница AnyToGpu (целевая, Rust):**

- Rust-ядро = IR → оптимизация → кодоген **и** запуск (устройства, буферы, кэш, вызовы OpenCL/CUDA).
- Языковая обёртка (Java) = только фронтенд (парсинг/внедрение) + тонкий FFI.

**[DECIDED] Этап 1 (сейчас): всё на чистой Java, без нативных зависимостей в ядре.**

- Ядро и рантайм пишем как модули, **независимые от Java-типов фронтенда** (граница = плоские данные, а не Java-объекты
  языка).
- Нативные зависимости (LWJGL/OpenCL) допускаются только в изолированном слое доступа к устройству, не в ядре
  компиляции.
- Перенос на Rust — позже, и не должен требовать переписывания архитектуры.

**[DECIDED] Режим работы: JIT.**

- Фронтенд при сборке (annotation processor) выдаёт **только плоский сериализуемый IR** (никакого OpenCL-текста в
  артефакте).
- Оптимизация и кодоген под конкретный backend/устройство — в рантайме на первом вызове, с кэшем.
- Следствие: IR — это **стабильный сериализуемый контракт** между фронтендом и ядром (это же будущая граница Java ↔
  Rust).
- AOT-генерация исходника — не в ядре; максимум опциональная надстройка позже, не влияет на дизайн.

**[DECIDED, выбор делегирован Claude — пересматриваемо] Java-фронтенд и внедрение:**

- **Извлечение IR:** annotation processor на **javac Tree API** (`com.sun.source` + `Trees`): атрибутированное дерево
  даёт разрешённые типы, константы и позиции без JavaParser и без собственного type resolver. Фронтенд пишет в `ir` и
  ничего больше. Ограничение: только javac (ECJ не поддерживается) — приемлемо для alpha; проверить обход
  Gradle/IDE-прокси `ProcessingEnvironment`.
- **Внедрение (замена вызова на GPU-запуск):** отдельный маленький модуль `weaver` (ASM, post-compile bytecode). Вместо
  поиска call-site'ов он **переписывает тело самого `@GPU` метода**: оригинальное тело переезжает в `<name>$jvm` (
  используется как JVM-fallback и референс для `@GPUTest`), а сам метод становится делегатом
  `Gpu.launch(kernelId, args…)`. Работает для любых вызывающих, в т.ч. из других модулей.
- **Не генерируются классы-лаунчеры с OpenCL/CUDA-кодом.** Артефакт ядра = IR-ресурс по `kernelId`; один универсальный
  рантайм. (Сейчас генерируются launcher'ы с десятками перегрузок — уходит.)
- ASM используется **только в `weaver`** (и в будущем `frontend-asm`), не в ядре.
- Форма запуска weaver'а (Gradle-задача vs javaagent на загрузке классов) — открытый вопрос.

Схема (черновик, уточняется в следующих разделах):

```
[Frontend: Java]  ->  (плоский IR / DOD-таблицы)  ->  [Core: optimize + codegen]  ->  [Runtime: device/memory/launch/cache]
```

## 4. Портируемость на Rust (правила дизайна ядра)  `[IN PROGRESS]`

Правила для модулей `ir`, `codegen-*`, `runtime`-core (всё кроме тонкого слоя LWJGL и Java-фронтенда):

1. **Данные — плоские:** примитивы, массивы примитивов, id вместо ссылок (раздел 6). Никаких `Object`-графов,
   `Map<String,String>` как модели, reflection, `instanceof`-иерархий.
2. **Логика — статические функции над данными.** Наследование и паттерны «Registry/Factory/Service/Provider» запрещены в
   ядре, кроме 3 разрешённых точек расширения (раздел 10).
3. **Ошибки — значения:** ядро возвращает `Result` / список `Diagnostic` (код + позиция + сообщение + подсказка);
   исключения — только на публичной границе (`GpuException` с полным отчётом) и в фронтенде для javac Messager. *
   *[DECIDED]**
4. **Нет глобального изменяемого состояния:** контекст (`GpuContext`) — явный объект, передаётся параметром. Никаких
   `static` реестров, `setXForTesting`.
5. **Детерминизм:** одинаковый вход → побайтово одинаковый IR, hash и OpenCL C (иначе сломаются кэш и
   golden-конформанс).
6. **Сериализуемый контракт:** бинарный формат IR (версия + таблицы) — единственный мост Java↔Rust. Текстовый дамп —
   только для людей/тестов.
7. **Нативный слой изолирован:** LWJGL/OpenCL — за узким интерфейсом `DeviceApi` (≈ список C-функций OpenCL); в Rust
   заменяется `opencl3`/FFI без изменения верхних слоёв.
8. **Строки/числа:** UTF-8/`long`/`double` явно; никакой зависимости от `String.hashCode`, `HashMap` порядка итерации.

Критерий готовности к порту: каждый модуль ядра можно описать как «функция: таблицы → таблицы/байты».

## 5. IR (единое каноническое представление)  `[IN PROGRESS]`

**[DECIDED] Форма: Structured IR + плоская арена выражений.**

- Control flow структурирован: `if / loop / switch / block` — узлы-регионы (без базовых блоков и phi). Напрямую ложится
  на Java-источник и на OpenCL C.
- Выражения — плоская арена узлов, ссылки по целочисленному id (не по указателям/объектам). Это DOD и 1:1 переносится на
  Rust (`Vec<Node>` + `NodeId(u32)`).
- Чистые выражения (без эффектов) — кандидаты для e-graph (egg-стиль). Стейтменты с эффектами (store, barrier, atomic,
  вызовы с побочными эффектами) — упорядоченный список внутри региона, e-graph их не переставляет.
- Единственное каноническое представление. **Запрещено**: текстовый IR (`ir-text-v1`), stringly-typed
  `Map<String,String>` узлы, обратный парсинг IR в исходник, параллельные деревья.
- IR сериализуем в компактный бинарный формат (контракт Java↔Rust и артефакт на диске).

### 5.1 Скалярные типы  **[DECIDED]**

- Фиксированный набор констант-id (не создаются динамически): `BOOL, I8, U8, I16, U16, I32, U32, I64, U64, F32, F64` (
  `F16` — позже).
- Знак — **метка (колонка) в таблице типов**, не отдельное семейство правил.
- Опкоды **полиморфные** (`add, sub, mul, div, rem, shr, lt, …`); знак определяется типом операндов. OpenCL C
  типизирован, поэтому `a / b` над `uint` уже беззнаковое — **кодген не вставляет касты**.
- Единственное правило валидатора для бинарных операций: типы операндов совпадают. **Неявных приведений нет**; касты —
  только явный узел `convert`, соответствующий явному преобразованию в исходнике.
- Знак учитывают только: `div/rem/shr/cmp/convert`, `min/max/abs`, свёртка констант, IR-интерпретатор, несколько правил
  e-graph (проверка метки).
- **Арифметика, сравнения и сдвиги определены только на 32/64-битных целых и F32/F64.** `I8/U8/I16/U16` — типы
  *хранения* (`load/store/convert`, элементы массивов и структур). Это повторяет Java (повышение до `int`) и убирает
  сужающие касты из-за C integer promotion.

### 5.2 Векторные типы  **[DECIDED]**

- Вектор = первоклассный тип `(скаляр, lanes ∈ {2,3,4,8,16})`; таблица типов создаёт их по требованию, id
  детерминированные.
- Те же полиморфные опкоды работают покомпонентно. Дополнительные узлы: `splat`, `extract`, `insert`, `shuffle` (
  swizzle), `build`.
- Нативно ложится на `float4` и т.п. в OpenCL C.
- **ABI-ловушка:** 3-компонентный вектор в памяти занимает как 4 (`sizeof(float3) == 16`) — правило фиксируется в
  ABI-layout (раздел 15, открытый вопрос о модуле `abi`).

### 5.3 Структуры  **[DECIDED]**

- `struct` — тип в таблице типов (упорядоченный список полей `(имя, тип)`), **value-семантика**.
- Узлы: `struct_build`, `field_get`, `field_set` (даёт новое значение), `load/store` целиком. Вложенные struct
  разрешены; **массивы внутри struct — не в v1**.
- Раскладка в памяти (offset/align/size) — отдельная чистая ABI-функция над таблицей типов, не часть узлов.

### 5.4 Локальные переменные  **[DECIDED]**

- Канонический IR содержит **изменяемые локали**: слоты переменных и узлы `local_decl / local_get / local_set` (как в
  исходнике Java). Выражения с `local_get` не считаются чистыми без анализа.
- Будущий optimizer-модуль сам делает внутри себя `mem2reg → e-graph → обратно`; внешний контракт `IrModule → IrModule`
  не меняется. Структурированный SSA (в стиле MLIR `scf`) — внутренняя форма оптимизатора, **не** второй канонический
  IR.
- Следствие для арены: узел `local_get` создаётся на каждое использование (дерево, а не DAG) — hash-consing выражений с
  локалами в v1 не делается.

### 5.5 Массивы и указатели  **[DECIDED]**

- `Array(addrspace, elem)` — отдельный тип, **не равен** `Ptr`. Параметр `float[]` / `GpuBuffer` кодген раскрывает в
  `__global float* a, int a_len`; рантайм сам передаёт длину из `GpuBuffer`. `.length` работает как в Java;
  bounds-check — возможная debug-опция позже.
- `Ptr(addrspace, pointee)` — явные указатели (`Global*/Local*/Constant*Ptr`) с арифметикой, длины не имеют. Address
  space ∈ {global, local, constant, private}.
- Узлы: `array_len`, `load`, `store` (по `Array` + индекс и по `Ptr`), `ptr_offset`.

### 5.6 Функции и вызовы  **[DECIDED]**

- `IrModule` = набор **функций** (kernel + helper'ы); узел `call(funcId, args)`. Кодген эмитит C-функции. Рекурсия
  запрещена валидатором.
- Helper'ы из других классов/библиотек попадают в модуль транзитивным замыканием достижимости.
- Inlining — проход оптимизатора, не фронтенда. Маппинг на исходник сохраняется.
- Builtins/intrinsics (`sin`, `get_global_id`, `atomic_add`, `barrier`, …) — узел `intrinsic(id, args)`, где `id` —
  запись в **таблице builtins (данные)**; сигнатуры и OpenCL-шаблоны живут в этой таблице, а не в 8000 строках ручных
  Java-перегрузок.

### 5.7 Таблица builtins  **[DECIDED]**

- Единственный источник истины — **один декларативный файл** (имя, сигнатуры по семействам типов, OpenCL-шаблон,
  JVM-референс как выражение/стандартный Java-метод, флаги чистоты/эффектов).
- Из него генерируются: `GPU.java` (обычные Java-методы с автодополнением и JVM-реализацией для fallback), таблица
  builtins для `ir`/`codegen-opencl`, таблица для IR-интерпретатора. Руками `GPU.java` не правится.
- Формат файла простой и читаемый из Rust без Java-рефлексии.

### 5.8 Control flow  **[DECIDED, выбор делегирован Claude — пересматриваемо]**

Узлы-регионы: `block`, `if(cond, then, else?)`, `loop(cond, body, update?)` (покрывает `for` и `while`),
`do_while(body, cond)`, `switch(value, cases, default?)`, `break`, `continue`, `return(value?)`.

- Labeled `break/continue` — **не в v1**, диагностика во фронтенде (в OpenCL C меток нет; обход через флаги — позже).
- `return` со значением — только в helper-функциях; kernel — `void`.
- Исключения, `try/finally`, `synchronized`, `assert` — запрещены валидатором subset (диагностика во фронтенде).

### 5.9 Формат сериализации  **[DECIDED]**

- Собственный бинарный формат, колонками: `magic + version + секции`; каждая секция — таблица (длина + little-endian
  `int[]/long[]/double[]` или UTF-8 string table). Точно те же SoA-массивы, что в памяти (раздел 6).
- Секции: `types`, `strings`, `consts`, `nodes` (колонки), `lists` (общий пул операндов), `functions`, `debug`.
- **Секция `debug`** (spans, имена локалей, исходные имена методов) отделена и **не входит в хэш кэша** — правка
  комментария/пробела в исходнике не должна инвалидировать скомпилированное ядро. Хэш = от остальных секций в
  каноническом порядке.
- Версия формата — часть заголовка; несовместимые версии отвергаются явной диагностикой (не «best effort»).
- Текстовый дамп (для людей, golden-тестов, отладки) — в `tools`, строится из тех же таблиц; обратно не парсится.

### 5.10 Каталог узлов  **[DECIDED после ревью]**

| Группа                                                                  | Узлы                                                                                                                                                                                              |
|-------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Константы                                                               | `const_int(type, value)`, `const_float`, `const_bool`, `spec_const(id)` (зарезервирован под 9A)                                                                                                   |
| Арифметика (полиморфная; только `I32/U32/I64/U64/F32/F64` и их векторы) | `add sub mul div rem neg`                                                                                                                                                                         |
| Битовые/сдвиги                                                          | `and or xor not` (побитовые, eager), `shl`, `shr` (арифметический для знаковых, логический для беззнаковых), `ushr` (логический сдвиг для **знакового** типа — Java `>>>`)                        |
| Сравнения (только скаляры)                                              | `eq ne lt le gt ge` → `BOOL`; векторные сравнения (маска `-1/0`) — через builtins                                                                                                                 |
| Выбор и логика                                                          | `select(cond, a, b)` — **ленивый** (вычисляется только выбранная ветка); `a && b` ≡ `select(a, b, false)`, `a or b` ≡ `select(a, true, b)`; `not` для `BOOL`                                      |
| Приведения                                                              | `convert(type, x)`, `bitcast(type, x)` — только явные                                                                                                                                             |
| Локали                                                                  | `local_decl(type, init)`, `local_get`, `local_set`, `local_addr(l)` (адрес локали → `Ptr<private>`; локаль становится «в памяти», нужна для `FloatPtr`)                                           |
| Адреса и память                                                         | `elem_ptr(arrayOrPtr, idx)`, `field_ptr(ptr, k)`, `load(ptr)`, `store(ptr, v)`, `array_len(array)`, `private_array_decl(elem, N)`, `local_array_decl(elem, N)` (`N` — константа или `spec_const`) |
| Вектор                                                                  | `splat extract insert shuffle build`                                                                                                                                                              |
| Struct (value-операции)                                                 | `struct_build field_get field_set`                                                                                                                                                                |
| Вызовы                                                                  | `call(funcId, args)`, `intrinsic(builtinId, args)`                                                                                                                                                |
| Эффекты/синхронизация                                                   | `expr_stmt(e)`, `barrier(flags)`; `atomic_*` — builtin с флагом эффекта, принимает `Ptr`                                                                                                          |
| Control flow                                                            | `block if loop do_while switch break continue return`                                                                                                                                             |

**Что изменилось по результатам ревью:** добавлены `ushr`, `expr_stmt`, `local_array_decl`, `elem_ptr`, `field_ptr`,
`local_addr`, `spec_const`; **память упрощена** — все `load/store` идут по `Ptr`, а `a[i]` = `load(elem_ptr(a, i))`,
`arr[i].x = v` = `store(field_ptr(elem_ptr(arr, i), x), v)` (пишется одно поле, а не вся структура); кодген сворачивает
`load(elem_ptr(a,i))` обратно в `a[i]`. `min/max/abs` — builtins. Compound-присваивания (`+=`, `++`) фронтенд
разворачивает в `local_set/store(add(...))`.

**Семантика (контракт IR):**

- **[DECIDED V1] Целые = Java-семантика.** Знаковые `add/sub/mul/neg` оборачиваются как в Java; счётчик сдвига
  маскируется (`n & 31` / `n & 63`). Кодген гарантирует это (внутри C — арифметика через `unsigned`; касты видны только
  в сгенерированном C и golden, **не в IR и не в исходнике**). Деление/остаток на ноль и `MIN / -1` — «значение не
  определено, но без падения»; JVM бросит исключение — расхождение задокументировано.
- **[DECIDED V2] `convert` float→int = Java:** насыщение к `MIN/MAX`, `NaN → 0`. Как этого достигает кодген (
  `convert_*_sat` + обработка NaN) — его задача; проверяется device-тестами на крайних значениях и golden.
- `select` ленив; чистые частичные операции (`div`, `rem`, `load`) оптимизатор не имеет права поднимать из ветки
  `select`.
- `switch` — как в C: проваливание, `break` выходит из `switch`, ключ — целое; стрелочный `switch` фронтенд раскрывает.
- `continue` в `loop` ведёт в `update`, в `do_while` — в проверку `cond`.
- `BOOL` — тип только значений: нельзя в `Array/Ptr`-элементе, поле struct, параметре kernel (`boolean[]` ↔ `U8` с явным
  `convert` во фронтенде).

### 5.11 Примеры IR (иллюстрация, синтаксис языка — по `OldCodeConcept`, см. 3.B)

**Инварианты, видимые в примерах:** (1) операнды узла всегда имеют **меньший** id, чем сам узел — валидатор,
интерпретатор и Rust читают таблицу одним проходом; (2) статементы и выражения — в одной таблице узлов, регион = узел со
списком детей в общем пуле; (3) малые константы (≤32 бит, `f32`) лежат прямо в колонке `a` (float — сырыми битами), в
таблице констант — только 64-битные; (4) builtin ссылается числовым id из таблицы builtins (версия таблицы — в
заголовке), строк в «горячих» секциях нет; (5) все имена и позиции — только в секции `debug`.

**Пример 1 — исходник**

```java

@Kernel
@WorkGroup(x = 256)
public static void computeSine(@Global float[] input, @Global float[] output) {
    int id = Gpu.getGlobalId(0);
    output[id] = Gpu.sin(input[id]) + 2.0f;
}
```

**Человекочитаемый дамп (`tools`, строится из таблиц; обратно не парсится):**

```
module fmt=1 builtins=1
type t16 = Array<global, f32>
type t17 = Ptr<global, f32>
func f0 "computeSine" kernel reqd_wg=(256,1,1) features={} group_sync=no
  param p0 "input"  : t16  access=READ
  param p1 "output" : t16  access=WRITE
  body = n14
```

**Таблица узлов (колонки SoA; `op,type,a,b,c` — int32, id = индекс строки):**

| id  | op         | type | a          | b             | c | смысл                           |
|-----|------------|------|------------|---------------|---|---------------------------------|
| n0  | CONST_I32  | I32  | 0          |               |   | `0`                             |
| n1  | INTRINSIC  | I32  | global_id  | list[0] len 1 |   | `getGlobalId(n0)`               |
| n2  | LOCAL_DECL | VOID | l0         | n1            |   | `int id = n1`                   |
| n3  | PARAM      | t16  | p0         |               |   | `input`                         |
| n4  | LOCAL_GET  | I32  | l0         |               |   | `id`                            |
| n5  | ELEM_PTR   | t17  | n3         | n4            |   | `&input[id]`                    |
| n6  | LOAD       | F32  | n5         |               |   | `*n5` ⇒ `input[id]`             |
| n7  | INTRINSIC  | F32  | sin        | list[1] len 1 |   | `sin(n6)`                       |
| n8  | CONST_F32  | F32  | 0x40000000 |               |   | `2.0f`                          |
| n9  | ADD        | F32  | n7         | n8            |   | `n7 + n8`                       |
| n10 | PARAM      | t16  | p1         |               |   | `output`                        |
| n11 | LOCAL_GET  | I32  | l0         |               |   | `id`                            |
| n12 | ELEM_PTR   | t17  | n10        | n11           |   | `&output[id]`                   |
| n13 | STORE      | VOID | n12        | n9            |   | `*n12 = n9` ⇒ `output[id] = n9` |
| n14 | BLOCK      | VOID | list[2]    | len 2         |   | `{ n2; n13; }`                  |

Проверка инвариантов: `n4` и `n11` (читают локаль) имеют по одному родителю (`n5`, `n12`) — `E02`; `n3`, `n10` (
параметры) — «закрытые», ими можно делиться; эффект (`n13` `STORE`) стоит на уровне стейтмента — `E01`; операнды всех
узлов имеют меньший id — `S02`.

Пул списков `int[] = [n0, n6, n2, n13]`. Размер таблицы узлов = 15 × 5 × 4 = **300 байт**.

**Бинарный контейнер (колонками):**

```
"GIR\0" | format=1 | builtins_table=1 | flags
[types]      2 rows  : ARRAY(space=GLOBAL, elem=F32), PTR(space=GLOBAL, pointee=F32)
[consts]     0       : (64-битных констант нет)
[nodes]      15 rows : op[15] type[15] a[15] b[15] c[15]
[lists]      4 ints
[functions]  1 row   : kind=KERNEL root=n14 params=[(t16,READ),(t16,WRITE)] reqd_wg=(256,1,1) features=0 group_sync=0
[debug]      strings: "computeSine","input","output","id"   spans: node->line
hash = H(types ‖ consts ‖ nodes ‖ lists ‖ functions)           // debug НЕ входит
```

Имя entry-точки OpenCL в release = `k_<hash8>`, в debug = `computeSine`.

**Пример 2 — `do { value = Gpu.max(value, step) + a; step++; } while (step < 2);`** (фрагмент):

```
n19 BLOCK  [ n14 local_set l1 = ADD(INTRINSIC max(l1,l2), PARAM p2)
           , n18 local_set l2 = ADD(l2, CONST 1) ]            // step++ развёрнут
n22 LT  BOOL  (local_get l2, CONST 2)
n23 DO_WHILE body=n19 cond=n22
func f1 "processSteps" kernel inline=ALWAYS opt=0 reqd_wg=(32,1,1) required={SIMD} fallback=f9
```

**Пример 3 — типы/функции из концепта:**

```
type t20 = Struct "GamePos" align=16 { x:f32, y:f32, z:f32 }   // size=16 (ABI-функция)
type t21 = Vec<f32,2>                                           // Float2
type t22 = Ptr<private, f32>                                    // FloatPtr (by-reference скаляр)
func f2 "clamp" device (p0 "ptr": t22)  body: if (load p0 > LIMIT) store p0, LIMIT
func f5 "nativeAddByBackend" device native { OPENCL: "return a + b;", CUDA: "return a + b;" } fallback=f9   // body_kind=NATIVE — зарезервировано, не v1
```

**Сравнение с текущим IR:** сейчас тело метода — строка `ir-text-v1` (`var int id = …`,
`set output[id] = (sin(input[id]) + 2.0f)`), выражения внутри — тоже строки; рантайм заново разбирает их регулярками (
`OpenClIrTextBodyParser`) и «реконструирует» исходник. В новом IR разбирать нечего: это таблицы чисел, читаемых одним
проходом.

### 5.12 Инварианты валидатора  **[DECIDED]**

Валидатор — контракт IR: ему подчиняется любой фронтенд (Java, потом ASM/Rust) и любой `OptimizerPass`. Каждое правило
имеет ID, диагностику (код + id узла → span из `debug` + подсказка) и обязательный тест в M1.

**Структура (`IR-S`)**

- `S01` все id (узлов, типов, функций, локалей, builtins) в допустимых диапазонах. `S02` операнды узла имеют **меньший**
  id. `S03` нет недостижимых узлов (каждый достижим от корня какой-либо функции — иначе хэш зависит от мусора). `S04`
  списки пула в границах. `S05` версия формата и таблицы builtins совместимы с читающим.

**Типы (`IR-T`)**

- `T01` типы операндов бинарной операции совпадают. `T02` арифметика/сравнения/сдвиги — только на допустимых типах (
  5.1). `T03` `convert/bitcast` — допустимые пары (`bitcast` — равный размер). `T04` `select`: `cond` — `BOOL`, ветки
  одного типа; `cond` у `loop/if/do_while` — `BOOL`. `T05` `load/store`: тип совпадает с pointee. `T06` `BOOL` запрещён
  в `Array/Ptr` элементе, поле struct, параметре kernel. `T07` вектор: `lanes ∈ {2,3,4,8,16}`, индекс `extract` и маска
  `shuffle` — константы в пределах. `T08` struct: `struct_build/field_get/field_set` соответствуют таблице типов; индекс
  поля — константа.

**Области видимости (`IR-V`)**

- `V01` локаль объявлена раньше использования и в охватывающем регионе. `V02` у `local_decl` всегда есть инициализатор.
  `V03` `local_addr` — только для скаляра/вектора/struct (не для массива).

**Эффекты и порядок (`IR-E`)**

- `E01` эффектные узлы (`call` с эффектом, `atomic_*`, `store`, `barrier`) — **только на уровне стейтмента** (
  `expr_stmt/local_decl/local_set/store`); внутри выражений запрещены (фронтенд сам раскладывает `f(x++, g())` по
  локалям в Java-порядке). `E02` **«открытые» узлы** (читающие локали/память: `local_get`, `load` и всё, что их
  содержит) имеют ровно одного родителя; делиться ими между стейтментами нельзя. Делиться могут только «закрытые» (
  константы, параметры, чистая арифметика над закрытыми).

**Control flow (`IR-C`)**

- `C01` `break` — только внутри `loop/do_while/switch`; `continue` — только внутри `loop/do_while`. `C02` `return`
  соответствует типу функции; kernel — `void`. `C03` `switch`: ключ целый, константы `case` уникальны.

**Память (`IR-M`)**

- `M01` запись через `Ptr` в `constant` запрещена. `M02` `local_array_decl` — только в kernel, на верхнем уровне тела,
  `N` — константа/`spec_const`. `M03` `private_array_decl`: `N > 0` — константа/`spec_const`. `M04` параметры kernel:
  `Ptr/Array` только `global/constant/local`, не `private`. `M05` struct не содержит `Array/Ptr` (v1). `M06` индекс
  `elem_ptr` — `I32`.

**Функции (`IR-F`)**

- `F01` граф вызовов ацикличен (нет рекурсии). `F02` `call`: число и типы аргументов совпадают с сигнатурой. `F03`
  work-group-атрибуты (`reqd_wg` > 0) — только у kernel. `F04` `required`/`inline`/`opt` — известные значения.

**Барьеры (`IR-B`)**

- `B01` **[DECIDED V3]** `barrier` под управлением, зависящим от `global_id/local_id` (простой taint: источники — эти
  builtins и всё, из них произведённое через локали/память; `group_id` внутри группы одинаков), даёт диагностику. По
  умолчанию **WARNING**; `strictBarriers = true` делает её **ошибкой**. В исходнике подавляется `Gpu.assumeUniform(x)`.

**Вычисляется валидатором (не проверка, а результат):** `required_features` (8.4), `uses_group_sync` (транзитивно через
вызовы; `barrier` или local memory в kernel или в callee), режимы доступа параметров `READ/WRITE/READ_WRITE` (9.5).

### 5.13 Уточнения по результатам реализации M1  **[DECIDED]**

**Дополнительные коды правил** (появились при реализации, обязательные тесты есть):

| Код | Правило |
|---|---|
| `IR-S06` | контейнер повреждён (обрыв, неверный счётчик, лишние данные, неверная сигнатура) — только при чтении |
| `IR-S07` | категория операнда: условие/ключ/значение — выражение, дети `BLOCK/IF/LOOP/DO_WHILE/SWITCH` — стейтменты; корень тела функции — `BLOCK` |
| `IR-T09` | результат узла не соответствует операции; стейтмент не `VOID`; `VOID` использован как значение |
| `IR-T10` | аргументы `intrinsic` не соответствуют сигнатуре builtin из таблицы |
| `IR-V04` | массив нельзя объявлять/присваивать как обычную локаль (только `private_array_decl/local_array_decl`) |

**Таблица «операция × тип» (бывший открытый вопрос O7, правило `IR-T02`):**

| Операции | Допустимые типы операндов |
|---|---|
| `add sub mul div rem neg` | скаляры и векторы `I32 U32 I64 U64 F32 F64` |
| `and or xor not` | скаляры/векторы `I32 U32 I64 U64`; скаляр `BOOL` |
| `shl shr ushr` | скаляры/векторы `I32 U32 I64 U64`; **счётчик того же типа, что значение** (для Java `long << int` фронтенд вставляет явный `convert`) |
| `eq ne` | скаляры `I32 U32 I64 U64 F32 F64` и `BOOL` |
| `lt le gt ge` | скаляры `I32 U32 I64 U64 F32 F64` |
| `convert` | скаляр↔скаляр (числовые, `BOOL`↔целые), вектор↔вектор с тем же числом компонент |
| `bitcast` | равная ширина: скаляр↔скаляр, вектор↔вектор с тем же числом компонент |

**Эффекты вызовов выводятся из функции.** `call` эффектен, если вычисленный `FunctionInfo.effects` вызываемой функции истинен
(запись, барьер, эффектный builtin, транзитивно); чистые вызовы (`effects = false`) допустимы внутри выражений, а если функция
читает память, узел `call` «открыт». Следствие для фронтенда: функции с записью вызываются только на уровне стейтмента.

**Следствие правила `IR-E02` для фронтенда.** Открытый узел имеет не более одного родителя, поэтому для `a[i] += 1`
(`store(p, add(load(p), 1))`) фронтенд создаёт **два** узла `elem_ptr`/`local_get` (индекс пересчитывается — он чистый). Общими
могут быть только закрытые узлы (константы, параметры, чистая арифметика над ними).

**`IR-B01`: расходимость после выходов.** `return` под расходящимся условием делает расходящимся весь последующий код функции;
`break/continue` — только остаток тела ближайшего цикла/`switch` (после цикла потоки сходятся). `group_id`, `groupSize` и
`assumeUniform` не порождают taint; источники taint — builtins с флагом `div` (`getGlobalId`, `getLocalId`) и всё из них
производное через локали, указатели и аргументы.

**Устойчивость к повреждённым данным (требование к `ir`).** Читатель и валидатор не бросают исключений ни на каких входных
байтах; нарушения возвращаются диагностиками. Если у узла повреждён любой операнд, узел тоже считается повреждённым и дальнейшими
проходами пропускается (каскад). Проверено фаззингом (2,1 млн итераций).

**Builtins в M1 (O1, часть).** Файл `builtins/builtins.def` (корень репозитория) упаковывается в ресурсы `ir` и разбирается
классом `Builtins` при загрузке; числовые id стабильны и не переиспользуются. Генерация `Gpu.java` и типов из того же файла —
сделана в M2 (5.14).

### 5.14 Уточнения по результатам реализации M2  **[DECIDED]**

**Один файл — две стороны (O1, закрыт).** `builtins/builtins.def` читают `ir` (в рантайме: сигнатуры, флаги, допуски) и генератор
`api` (при сборке). Помимо строк builtin файл содержит директивы, которые `ir` пропускает: `doc` (Javadoc), `jvm [типы] = выражение`
(JVM-реализация; параметры называются `a b c`; векторные перегрузки строятся покомпонентно автоматически), `vectors <скаляры> : <lanes>`,
`pointers <скаляры>`; флаг `ulp64=N` — допуск для `f64`, если он отличается от `ulp` (`sqrt`: 3 ULP для float, корректное округление
для double). Парсер генератора строгий: ошибка формата ломает сборку с номером строки.

**Генерация.** Генератор — отдельный source set `generator` внутри модуля `api` (не входит в jar); задача `generateApi` пишет
`api/build/generated/sources/api/java` (`Gpu`, векторы, классы-ссылки), каталог принадлежит генератору и очищается перед записью.
Сгенерированное не коммитится, поэтому разойтись с таблицей не может (критерий «сгенерированное = закоммиченному» заменён
генерацией в сборке). Тесты `api` используют тот же парсер для сверки допусков.

**Java-типы API.** Векторы `Float|Double|Int|Long × {2,3,4,8,16}` — неизменяемые final-классы с публичными final-полями (`x y z w`
для ≤4 компонент, `s0..s9,sA..sF` для 8 и 16), равенство побитовое (как `Float.equals`). Беззнаковых и `char/short`-векторов в API нет
(в Java нет беззнаковых примитивов; `I8..U16` — типы хранения, 5.1). Операции над векторами (`add/sub/mul`, `splat`, `shuffle`) — M8.
Классы-ссылки `FloatPtr/DoublePtr/IntPtr/LongPtr` — изменяемое поле `value`, сравнение по ссылке.

**builtins с указателями без Java-представления.** `atomicAdd` (сигнатура `ptr<...>`) в `Gpu` пока не генерируется: pointer-типы
появляются в M9, atomics — в M10. Генератор перечисляет пропущенные builtins в Javadoc `Gpu`, тест фиксирует список (`[atomicAdd]`).

**JVM-реализации.** `sin/cos` — `StrictMath` (fdlibm: одинаковый результат на всех платформах), `sqrt` — `Math.sqrt` (корректное
округление по IEEE 754), `fma` — `Math.fma`. **`max/min` для float — семантика `Math.max/min`** (NaN распространяется, `-0 < +0`).
Это **расходится** с OpenCL: `fmax/fmin` возвращают не-NaN аргумент, а `max/min` при NaN не определены. Следствие для M5: кодген
обязан выдавать для float `max/min` код с Java-семантикой (иначе нарушается «JVM ≡ GPU»); проверять device-тестом на NaN и `±0`.

**Допуски ULP.** `sin/cos` 4/4, `sqrt` 3/0, `fma` 0/0 (f32/f64), `max/min/assumeUniform` — точно. Значения соответствуют таблице
«Relative Error as ULPs» спецификации OpenCL C (full profile); в M2 они подтверждены сторонней выпиской и знанием спецификации, но не
прочитаны из первоисточника — **сверить с текстом спецификации в M5** (там же проверка по драйверам). Тесты `api` сравнивают JVM-реализации
с независимыми эталонами (`Math.*`, точная арифметика `BigDecimal`) на крайних значениях: подмена функции или ошибка в реализации
роняет тест (мутационно проверено).

**Контекст work-item (O6, закрыт).** `WorkItem.run(ctx, body)` привязывает `WorkItemContext` к потоку через `ScopedValue` (Java 25):
привязка снимается сама, в том числе при исключении, вложенный запуск временно заменяет внешний, другие потоки её не наследуют. Чтение
вне запуска — `IllegalStateException` (молчаливое значение по умолчанию скрыло бы вызов device-кода вне ядра). `WorkItemContext` —
плоские `int[3]` на величину, `setGlobalId(x,y,z)` пересчитывает `groupId = globalId / localSize`, `localId = globalId % localSize`;
оси вне `workDim` — как в OpenCL (индексы 0, размеры 1); `globalSize` обязан делиться на `localSize`. Накладные расходы (JMH, короткий
прогон): ≈ 8 нс на work-item сверх прямого цикла, привязка контекста — ≈ 15 нс на запуск.

**Аннотации.** Retention `CLASS` (weaver читает их из байткода). `@Kernel(inline, optLevel, workgroup, required, fallback)`;
`workgroup` — сокращение `@WorkGroup(x=…)`, их совместное использование — ошибка фронтенда. `InlinePolicy {DEFAULT, ALWAYS, NEVER}` —
порядок совпадает с `INLINE_*` в IR. Строки `required` — имена `Features` IR (`FP64`, `INT64_ATOMICS`, …); `"SIMD"` из концепта
возможностью IR не является — фронтенд (M3) обязан дать диагностику на неизвестное имя. `@GpuNative`, `@GpuFallback`, `@AutoTune`,
`Backend`, `Metric` не созданы (не v1, 3.B): концепт компилируется без них (`ConceptSample` в тестах `api`, выполняется на JVM).
`@Local` (`LOCAL_VARIABLE` и `PARAMETER`, Retention `CLASS`) — локальная память work-group: локальная переменная-массив в теле
ядра (`@Local float[] tile = new float[256]` → `local_array_decl`, IR-M02) и `__local`-параметр ядра (IR-M04, размер из launch-конфига,
8.2). Ядра с `@Local` имеют `uses_group_sync` и не уходят в JVM-fallback (3.5). Фронтенд читает аннотацию локальной переменной из
исходника (javac не пишет такие аннотации в class-файл). Pointer-типы `Local*Ptr` — M9, `barrier` — M10.

### 5.15 Уточнения по результатам реализации M3  **[DECIDED]**

**Tree API проверен.** Эксперимент на JDK 25: типы и элементы выражений в телах методов (`Trees.getTypeMirror`, `Trees.getElement`)
доступны уже в раундах annotation processing, а `Filer` позволяет писать ресурсы в любом раунде, включая последний. Поэтому
фронтенд — обычный процессор без `TaskListener` и без внутренних API javac (`com.sun.tools.javac.*` не используются). ECJ по-прежнему
не поддерживается.

**Обход обёрток окружения (закрыто).** Gradle/IDE передают процессору обёртку над `ProcessingEnvironment`, на которой
`Trees.instance` падает (JDK разворачивает лишь прокси с полем `val$delegateTo`). `ProcessingEnvironments.unwrap` перебирает поля
обёртки или обработчика прокси и берёт значение типа `ProcessingEnvironment`, повторяя поиск до 8 раз; рефлексия — только по классам
обёрток. Проверено тестами: класс-обёртка, `Proxy` с произвольным именем поля, двойная обёртка. Если окружение не развернуть —
ошибка `GPU0201` без падения javac.

**Состав и порядок модуля.** Один IR-модуль на ядро: ядро, достижимые `@DeviceFunction` и варианты `fallback` с их замыканиями.
Функции идут от листьев вызовов к корню (builder требует существования вызываемой), **ядро — всегда последняя функция** (точка входа).
Варианты `fallback` — тоже функции вида `KERNEL` (их запускает рантайм); цикл `fallback` — `GPU0014`. Два ядра с общей функцией получают
каждое свою копию.

**Ресурсы (O5, закрыт).** `META-INF/gpu/ir/<kernelId>.gir` — бинарный IR (`kernelId` = 64 hex-символа `hash` без `debug`); одинаковые ядра
дают один файл. `META-INF/gpu/kernels.idx` — индекс для weaver'а (он не зависит от `ir` и хэш считать не умеет): по строке на ядро,
поля через табуляцию `<двоичное имя класса>\t<метод>\t<JVM-дескриптор>\t<kernelId>`, строки отсортированы, UTF-8, `\n`. Индекс пишется в
последнем раунде; процессор не объявляет себя инкрементальным (Gradle перекомпилирует всё).

**Подмножество (проверка до построения IR, все нарушения за один проход).** Параметры: `int/long/float/double` и одномерные массивы
примитивов (`boolean[]` хранится как `U8`); скалярные `boolean/byte/short/char` — нет (`boolean` запрещён и валидатором, IR-T06).
Результат device-функции: `void/boolean/int/long/float/double`. Вызывать можно только builtins `Gpu.*` и методы с `@DeviceFunction`,
исходник которых есть в той же компиляции (в том числе из других классов); метод без аннотации — `GPU0113` (строгая проверка из 3.B),
библиотечная device-функция без исходника — `GPU0114` (**ограничение v1**: чтобы использовать функции из jar, потребуется
распространять их IR или исходники и связывать модули). Не поддерживаются и дают диагностики: исключения, `synchronized`, `assert`,
метки, строки, объекты и `new`, лямбды, `instanceof`/ссылочные приведения, `for-each`, `switch` как выражение и pattern-matching,
рекурсия, поля кроме констант, многомерные массивы; векторные типы, `@Struct` и pointer-типы — `GPU0190` (до M8/M9).

**Массивы.** Массив — только имя параметра или локального массива: индексация, `.length`, передача аргументом. Присваивание, возврат и
копии ссылок запрещены (`GPU0116`, иначе нарушалось бы IR-V04 и появлялся бы aliasing). `T[] a = new T[константа]` — `private_array_decl`;
с `@Local` — `local_array_decl` (только в ядре, на верхнем уровне тела, `GPU0120`). Пространство параметра: `@Local` → local,
`@Global(constant = true)` → constant, иначе global; при передаче в функцию оно обязано совпасть (`GPU0121`).

**Нормализация эффектов (IR-E01/E02).** Выражение переводится в узел, а эффекты «поднимаются» в список стейтментов текущего блока:
(1) операнды вычисляются слева направо, и если вычисление очередного породило стейтменты, ранее вычисленные операнды, читающие
изменяемую локаль или память, сохраняются во временные локали *до* этих стейтментов (временные локали пишутся один раз и повторно не
сохраняются); (2) `x++`, `++x`, `x op= y`, присваивание-выражение разворачиваются в `local_set`/`store`, значение — временная локаль или
перечитывание; для `a[i] op= y` создаются два `elem_ptr`: индекс пересчитывается, если он и `y` чистые, иначе сохраняется во временную
локаль; (3) `&&`, `||`, `?:` без эффектов в операндах — ленивый `select`, с эффектами — `if` со временной локалью; (4) вызов функции с
эффектами всегда поднимается в стейтмент; (5) условие цикла с эффектами: `loop(true, { стейтменты; if (!c) break; тело })`, а для
`do-while` — флаг первой итерации, чтобы `continue` проходил через проверку; (6) присваиваемый параметр заменяется локалью с начальным
значением (параметры IR неизменяемы); (7) локаль без инициализатора получает нулевое значение (IR-V02). Арифметика повторяет Java:
`byte/short/char` повышаются до `int`, обратное сужение — явный `convert`, счётчик сдвига приводится к типу значения, константы
`byte/short/char` становятся `int`-константами.

**Атрибуты ядра.** `required` проверяется по именам `Features` (`GPU0009`) и записывается канонически (без повторов, по алфавиту);
`workgroup` и `@WorkGroup` вместе — `GPU0008`; `optLevel` вне `0..3` — `GPU0012`; размеры work-group должны быть положительными — `GPU0013`.

**Диагностики.** Таблица кодов — данные: `diagnostics/diagnostics.def` в корне репозитория (упаковывается в ресурсы `frontend-java`; код,
серьёзность, сообщение, подсказка). Группы: `GPU00xx` объявления и аннотации, `GPU01xx` тела методов, `GPU02xx` окружение, `GPU09xx`
внутренние ошибки (`GPU0901` IR не прошёл валидатор, `GPU0902` сбой фронтенда, `GPU0903` предупреждение IR). Позиция — точная, через
`Trees.printMessage`. Тесты: образец с меткой строки на каждый код, проверка согласованности таблицы и кода в обе стороны.

### 5.16 Уточнения по результатам реализации M4  **[DECIDED]**

**Назначение.** `ir-interpreter` — эталон семантики IR на CPU и инструмент тестирования, а не рантайм: он исполняет IR по виртуальному
NDRange и служит оракулом для кодогенераторов (M5+). Зависит только от `ir` (production); `api` и `frontend-java` подключены **только к
тестам** (JVM-реализация `Gpu.*` для прямого вызова оригинального метода и annotation processor, собирающий образцы в IR точно так же, как
у пользователя). `verifyModuleBoundaries` видит лишь production-граф — исключение сознательное и описано в `ir-interpreter/build.gradle`.
JMH не добавлялся: интерпретатор не на hot path.

**Каноническое представление значения.** Скаляр — один `long`: `BOOL` 0/1; `I8/U8/I16/U16` — числовое значение (знаковое/беззнаковое
расширение); `I32/U32/F32` — биты, расширенные знаком до 64 (для `U32` числовое значение берётся маской `0xFFFFFFFF` при сравнении,
делении, сдвиге вправо и преобразованиях); `I64/U64/F64` — сырые биты. Массив — номер буфера; указатель — `(buf << 32) | (idx & 0xFFFFFFFF)`.
Приватные массивы выделяются на work-item/вызов и освобождаются при возврате из функции; повторное выполнение `private_array_decl`
обнуляет массив заново (IR-V02). Все операции — статические функции без состояния (`Alu`); состояние исполнения — плоские массивы
(`Machine`).

**Семантика, зафиксированная этим эталоном** (кодогенераторы обязаны совпасть):

- целые — оборот по модулю 2^N; счётчик сдвига маскируется (`n & 31` / `n & 63` по ширине значения); знаковость операций определяется
  типом (`U*`: беззнаковые `div/rem/shr/сравнения`);
- `float→int` насыщающий, `NaN → 0`; для `I8/U8/I16/U16` — **как Java `(byte)(int)f`: насыщение до диапазона `int`, затем сужение с
  оборотом** (а не насыщение до диапазона узкого типа). Это решение принято ради равенства с оригинальным методом (критерий приёмки M4);
  **кодогенератор M5 обязан дать то же** (`convert_int_sat` + сужение), иначе `(byte) 300.0f` разойдётся с JVM;
- `int→float/double` — округление к ближайшему чётному, включая беззнаковые 64-битные (через «липкий» бит при сдвиге на 1);
- `select` — ленивый: невыбранная ветка не вычисляется; `&&`/`||`/`?:` приходят из фронтенда уже в таком виде;
- `switch` — с проваливанием, `default` может стоять в любом месте; `continue` в `for` идёт на шаг обновления; `break` выходит из
  ближайшего цикла/`switch`;
- builtins: `sin/cos/...` через `StrictMath`, `max/min` как `Math.max/min` (NaN и `±0` — как в JVM), `fma` — `Math.fma`,
  `atomicAdd` исполняется последовательно (work-item'ы идут один за другим); id вне размерности NDRange — 0, размеры — 1.

**Деление целых на ноль — ошибка исполнения `IN-R02`.** В IR это «неопределённое поведение», у JVM — исключение, у OpenCL —
неопределённое значение. Эталон строже: падает, чтобы тест не принял случайный результат за правильный. Если JVM бросила исключение, а
интерпретатор нет (или наоборот), дифференциальный тест считает это расхождением. Вещественное деление на ноль ошибкой не является.

**Ошибки как значения.** Весь вход проходит `Validator` (нарушения — его же коды `IR-*`), затем проверки запуска. Коды: `IN-A00` функция
не ядро; `IN-A01` число аргументов; `IN-A02` класс аргумента не соответствует параметру; `IN-L01` NDRange несовместим с ядром
(`reqd_work_group_size`, делимость на размер группы, ось за пределами размерности); `IN-U01` узел/тип/builtin пока не поддержан; `IN-R01`
выход за границы массива (чтение и запись, в том числе отрицательный индекс); `IN-R02` деление на ноль; `IN-R03` исчерпан бюджет
шагов (`Options.maxSteps`, 0 = без ограничения); `IN-R04` недопустимая длина приватного массива (> 2^22). Первая ошибка запоминается,
исполнение останавливается; **при отказе массивы хоста не изменяются** (запись обратно только после успеха).

**Что пока не поддержано (`IN-U01`, проверяется до запуска обходом достижимых функций):** векторы и структуры (M8), `local_addr`,
`field_ptr` (M9), `barrier` и `local_array_decl` (M10), `spec_const`, нативные тела. Это границы вех, а не пробелы.

**Соответствие хоста и IR.** `I8` — `byte[]`; `U8` — `byte[]` или `boolean[]`; `I16` — `short[]`; `U16` — `char[]` или `short[]`; `I32/U32` —
`int[]`; `I64/U64` — `long[]`; `F32` — `float[]`; `F64` — `double[]`; скаляры строго `Integer/Long/Float/Double`. Один и тот же массив,
переданный дважды, — один буфер (aliasing сохраняется, как в Java).

**Тесты.** Дифференциальные: образцы — настоящие `@Kernel`-методы (`src/test/.../samples`), IR берётся из ресурсов
`META-INF/gpu/kernels.idx` + `ir/<id>.gir` (проверяется весь путь «исходник → ресурс → исполнение»); `Differential` вызывает оригинальный
метод под `WorkItem.run(WorkItemContext)` и сравнивает массивы (вещественные побитово, `NaN == NaN`, опционально в ULP). Целые и
`long` операции проверены на всех парах крайних значений плюс случайные пары. Беззнаковые типы в Java отсутствуют, поэтому они проверены
отдельно: `AluTest` сверяет `Alu` с независимым оракулом на `BigInteger`/`BigDecimal`, а `InterpreterTest` — модулями, собранными
вручную. Ограничение: эталон проверен против JVM и против арифметики произвольной точности, а не против железа.

### 5.17 Уточнения по результатам реализации M5  **[DECIDED]**

**Назначение и граница.** `codegen-opencl` - чистая функция `emit(IrModule, kernel, Target, EmitOptions) -> Result<Artifact>`: ни рантайма,
ни файлов, ни FFM в production-коде (границы проверяет `verifyModuleBoundaries`). Зависит только от `ir`. Одинаковый вход даёт те же байты:
имена выдаются по возрастанию индексов, вспомогательные функции печатаются в фиксированном порядке. Ошибки - значениями:
диагностики валидатора `IR-*` как есть, `CG-A00` (нет такой функции), `CG-A01` (функция не ядро), `CG-U01` (конструкция следующих вех: векторы и
struct - M8, `local_addr`/`field_ptr` и pointer-параметры - M9, `barrier`, `local_array_decl` и `__local`-параметры - M10, `spec_const`, нативные
тела); все нарушения возвращаются за один проход, до генерации текста. Проверяются только функции, достижимые из ядра.

**Артефакт и ABI.** `Artifact` = текст, имя точки входа, раскрытая сигнатура `List<KernelArg>`, маска `required_features`, опции `clBuildProgram`,
`Target` и `EmitOptions`, с которыми он получен. Параметр `Array(T)` раскрывается в два аргумента OpenCL подряд - указатель с пространством
`__global/__constant` и `int name_len` (8.2); скаляр - один аргумент по значению. Рантайм (M6) упаковывает аргументы строго по `Artifact.args()`,
а не пересчитывает раскладку сам. Если ядро вызывает device-функцию с массивом, то и там массив - пара «указатель, длина»; длина
private-массива известна при генерации и подставляется числом.

**Release и debug (8.1).** В release нет ни одного имени и ни одного `#line`: функции `k<i>` (ядро) и `f<i>`, параметры `p<i>`, локали `v<i>`;
текст не зависит от debug-секции (проверено: модуль с отладочными именами и без них даёт один текст). В debug имена берутся из IR и
приводятся к идентификаторам C: недопустимые символы - `_`, зарезервированное имя (ключевые слова, типы, встроенные функции, которые вызывает
сам код, префиксы `get_ as_ convert_ atomic_ atom_ gpu_ cont_ CLK_`) получает префикс `u_`, повтор - суффикс `_1, _2...`. Перед каждым стейтментом с
известной позицией пишется `#line N`. **В debug-секции IR нет имени исходного файла**, поэтому по умолчанию пишется `#line N` без имени;
имя можно передать в `EmitOptions.sourceName`. Целевое устройство в v1 на текст не влияет (8.5), но входит в `Artifact`, а значит в ключ кэша.

**Java-семантика поверх C.** Решения принимались по тому, что делает эталон `ir-interpreter` (5.16), и проверялись на устройстве:

- знаковые `+ - * -x <<` считаются в беззнаковом типе той же ширины (`(int)((uint)a + (uint)b)`), потому что переполнение знакового целого в C - UB;
  вложенные выражения остаются в беззнаковом типе целиком; константы пишутся сразу беззнаковым литералом;
- счётчик сдвига маскируется (`& 31` / `& 63`), константный - при генерации; OpenCL C сам маскирует счётчик, маска нужна читателю и другим компиляторам;
- знаковые `/` и `%` - через `gpu_div_i32/i64`, `gpu_rem_i32/i64` (`MIN / -1` в C не определено; делитель `-1` разбирается отдельно). Деление на
  ноль в IR по-прежнему не определено: интерпретатор падает (`IN-R02`), устройство вернёт мусор;
- `float -> int` насыщающее, `NaN -> 0`: `gpu_<f32|f64>_to_<i32|u32|i64|u64>` = `isnan(x) ? 0 : convert_T_sat(x)`; явная проверка `NaN` стоит,
  чтобы результат не зависел от драйвера. **К 8/16-битным типам - как в Java и в интерпретаторе: насыщение до `int`, затем сужение с оборотом**
  (`(char)gpu_f32_to_i32(x)`), а не насыщение до диапазона узкого типа;
- `%` для float - `fmod` (знак делимого, как у Java); `max/min` для float - `gpu_max_*`/`gpu_min_*` с семантикой `Math.max/min` (`NaN` побеждает,
  `+0 > -0`), потому что `fmax/fmin` возвращают не-`NaN`, а `max/min` OpenCL для `NaN` не определены; для целых - встроенные `max/min`;
- `select` с булевой константой печатается как `&&`/`||` (ленивость сохраняется, текст короче); иначе `?:`;
- `continue` в цикле с простым шагом остаётся `continue` (`for (; c; шаг)`); в цикле со сложным шагом (объявления, ветвления) цикл
  печатается как `while`, а `continue` - как `goto cont_N`, метка стоит перед шагом; `switch` печатается с телами в `{}` (проваливание и `default` в
  любом месте как в C);
- `bool` в C - тип `bool`; сравнения дают `int 0/1`, что в позиции `BOOL` равно `true/false`; `convert` в `BOOL` - `x != 0`;
- float-литералы - кратчайшая десятичная запись (`Float.toString` - возвращает то же число), `NaN`/`Inf` - `NAN`/`INFINITY`, нестандартные `NaN` - через `as_float`.

**Строгий float (8.3).** Без `fastMath` в тексте `#pragma OPENCL FP_CONTRACT OFF` (запрет слияния в FMA), опции сборки пусты. С `fastMath` pragma не
пишется, а в `Artifact.buildOptions()` попадает `-cl-fast-relaxed-math`. Расширения: `cl_khr_fp64`, `cl_khr_int64_base_atomics`, `cl_khr_fp16` - по маске
`required_features` ядра. Целевая версия - OpenCL 1.1+ (32-битные `atomic_add` и байтовые записи в ядре, 64-битные - через расширение).
`inline`/`opt`-атрибуты функций в v1 текст не меняют. **Открыто для M6:** деление и `sqrt` float на GPU по умолчанию неточные (до 2.5 / 3 ULP),
опции `-cl-fp32-correctly-rounded-divide-sqrt` генератор не добавляет; решение - вместе с политикой допусков в `@GPUTest`.

**Тесты.** Образцы-ядра (настоящие Java-методы `@Kernel`, собранные фронтендом) переехали из тестов `ir-interpreter` в его `testFixtures`
(`SampleKernels`) и общие для интерпретатора и кодогена. Ручные модули (`HandModules`): все операции каждого типа `i32/u32/i64/u64/f32/f64`,
все 10x10 пар преобразований, `bitcast`, логика, сложные циклы, `switch`, device-функции с массивами `global/private/constant`, константы-крайности,
builtins на 1D/2D/3D, atomics. Golden: по `.release.cl` и `.debug.cl` на каждый модуль в `src/test/resources/golden/<target>/`, обновление -
`-PgoldenUpdate` (результат смотреть глазами). **Device-тест** (`@Tag("device")`, задача `deviceTest`, в `build` не входит, без драйвера
пропускается): сгенерированный C компилируется реальным драйвером (release, debug и fast-math для каждого модуля) и исполняется; результат
совпадает с интерпретатором - целые бит в бит, вещественные в пределах нескольких ULP, знак нуля и `NaN` строго. Для этого в тестах есть
минимальная FFM-обвязка `ClDevice` (одно устройство, синхронный запуск, ошибка - исключение); это не `DeviceApi` из M6. Проверено на
NVIDIA GeForce RTX 5070 (NVIDIA OpenCL): один вендор и одна версия драйвера, AMD/Intel не проверялись.

очередь, буферы, программа, ядро, аргументы, `enqueue`, `finish`, `release`), `OpenClApi` (реализация на `java.lang.foreign`, без LWJGL), `DeviceInfo`

**`DeviceApi`.** Объекты OpenCL - `long`; метод бросает `DeviceApiException` (код и имя функции) и не принимает решений; слой не потокобезопасен -
сериализацию делает `GpuContext`. Неудачная сборка программы - не исключение, а `BuildOutcome(status, log)`: ошибка исходника - ожидаемое событие.
Блокирующие передачи (`MemorySegment` хоста). Отсутствие `libOpenCL`, ошибка загрузки или «платформ нет» - пустой список устройств, а не падение:
`OpenClApi.load()` возвращает `null`, а `GpuContext.builder().tryBuild()` - `RT-D01` (значение). Используется `clCreateCommandQueue` (OpenCL 1.x): его
экспортируют и драйверы 2.x/3.0.

**Политика выбора (9.4).** Фильтры: тип (`ANY/GPU/CPU`), подстрока производителя или имени, минимум глобальной памяти, обязательные `Features`; затем GPU раньше
остальных, внутри группы - порядок перечисления. Явный `override` побеждает фильтры: `"2"` (номер среди всех), `"nvidia"` (первое с такой подстрокой),
`"nvidia:1"` (второе из подходящих). Источник: `DevicePolicy.override`, иначе системное свойство `javatogpu.device`, иначе переменная `JAVATOGPU_DEVICE`
(`Builder.ignoreEnvironment()` отключает чтение окружения). Выбор среди оставшихся - один детерминированный порядок, без оценок и подсказок.

**`GpuContext`.** `Builder.tryBuild()` → `Result` (ошибки `RT-D01` устройств нет/политика ничего не оставила, `RT-D03` ошибка драйвера), `build()` бросает
`GpuException`. Владение `DeviceApi`: загруженный самим контекстом закрывается вместе с ним, переданный пользователем - нет. Все обращения к драйверу и
очереди идут под одним замком (запуски на устройстве выстраиваются в очередь, 9.1); кэш компиляции конкурентный и строит ядро ровно один раз на ключ,
остальные потоки ждут результат. Закрытие освобождает ядра, программы, незакрытые буферы, очередь и контекст; повторное закрытие безопасно; после него
`compile`/`launch` возвращают `RT-X02`, `allocate`/`run` бросают `GpuException`.

**Компиляция и кэш.** Путь: `OpenClEmitter.emit` → проверка `required_features` против устройства **до** обращения к драйверу (`RT-D02` с именем устройства и
возможности, 8.4) → программа → `clBuildProgram` → ядро. Диагностики генератора (`IR-*`, `CG-*`) проходят без изменений. Ошибка сборки разбирается в
`RT-C01`/`RT-C02` (формат `источник:строка:колонка: error|warning: текст`, продолжения - цитата кода и `^` - присоединяются; нераспознанный log целиком - одной
ошибкой, обрезанной до 4000 символов); предупреждения успешной сборки - диагностики результата и события `WARNING`. Ключ кэша: хэш IR без отладочных данных +
номер ядра + `debug`/`fastMath` + цель + устройство + версия драйвера; **неудачная компиляция тоже кэшируется** (повтор детерминированно провален). Кэш только в
памяти; в ключе нет отладочных имён, поэтому два модуля, равных по IR, но с разными именами, делят одно ядро (имена и `#line` в debug берутся у первого).

**Запуск.** `launch(CompiledKernel, LaunchConfig, Object...)` → `Result<LaunchStats>`; `run(IrModule, LaunchConfig, Object...)` = `compile` + `launch` с
`GpuException`. Аргументы: `GpuBuffer`, Java-массив или скаляр (`Integer` для `I32/U32`, `Long`, `Float`, `Double` - строго, как у интерпретатора). Проверки
собираются за один проход: `RT-A01` число аргументов, `RT-A02` аргумент не подходит параметру (буфер чужого контекста/закрытый/другого вида, не тот массив
или скаляр), `RT-L01` размеры запуска (деление NDRange на work-group, `reqd_work_group_size` ядра, предел размера группы для устройства и для самого ядра,
ось за пределами размерности). Размер work-group не задан - его выбирает драйвер (ядро не должно зависеть от `getLocalId/getGroupId`); у ядра с
`reqd_work_group_size` берётся размер из ядра. Раскладка аргументов - строго по `Artifact.args()` (5.17): массив = буфер + `int` длина в элементах.

**Массивы хоста как сахар - уточнение 9.5.** Валидатор считает режим доступа параметра, но «загружать только читаемые» неверно для массивов, которые ядро
пишет частично: нетронутые элементы вернулись бы с устройства мусором, а JVM-семантика (3.2) требует, чтобы они сохранились. Поэтому **на устройство
передаются все массивы, а на хост возвращаются только записываемые** (`ACCESS_WRITE` хотя бы по одному из параметров, получивших этот массив). Один и тот же
массив, переданный дважды, - один буфер (алиасинг как в JVM). Чтобы не платить за передачу при цепочках ядер, данные держат в `GpuBuffer`
(в тесте цепочка из двух ядер на явных буферах передаёт 0 байт). При ошибке запуска массивы хоста остаются нетронутыми, временные буферы освобождаются.

**`GpuBuffer`.** Явное владение: `allocate(тип, длина)`, `upload(массив)`, `write`, `read`, `close`; вид элемента проверяется (одинаковый размер и «природа»:
`int[]`-буфер подходит `I32` и `U32`, но не `F32`); длина ограничена максимальной аллокацией устройства (`RT-A03`). Не потокобезопасен. Методы, которыми
пользуются напрямую, бросают `GpuException` (граница), внутри рантайма ошибки - `Result`.

**События и статистика.** Один `EventListener`: `DEVICE_SELECTED`, `COMPILE` (`built`/`cache-hit`/`failed`), `UPLOAD`, `KERNEL`, `READBACK`, `WARNING`, `CLOSED` с
длительностью и числом байт; исключения наблюдателя подавляются. `LaunchStats` (тайминги передач и ядра, байты) и `CacheStats` (попадания, промахи, записи).

**Не вошло в M6 (отложено осознанно).** JVM-fallback (3.5, 3.8) и хост-фасад с ambient-контекстом (3.7, O2) - M7, они зависят от weaver; дисковый кэш (9.3) и
prepared launcher (hot path) - после M7: M6 даёт примитивы (кэш в памяти, `GpuBuffer`, `launch` на скомпилированном ядре), на которых они строятся;
`local`-память и `barrier` в аргументах (`__local`-параметры) - M10; опция `-cl-fp32-correctly-rounded-divide-sqrt` не добавляется.

**Тесты.** 71 обычный (фейк `DeviceApi`: выбор устройства, кэш и одна компиляция на ключ при 8 потоках, отказы драйвера, разбор log, режимы доступа, алиасинг,
размеры запуска, буферы, закрытие и утечки, потокобезопасность) и 23 на устройстве (`./gradlew :runtime:deviceTest`): `computeSine` на реальном OpenCL, цепочка
через `GpuBuffer`, 16 образцов-ядер против `ir-interpreter`, разбор настоящего build log, параллельные запуски. Проверено на NVIDIA GeForce RTX 5070
(драйвер 595.97); AMD/Intel не проверялись.

### 5.19 Уточнения по результатам реализации M7  **[DECIDED]**

**O2 закрыт: хост-фасад — `com.sixik.gpu.runtime.JavaToGpu`.** Имя из 3.7 осталось рабочим обозначением и стало настоящим; `Gpu` по-прежнему занят builtins внутри
ядра. Фасад — единственное место ambient-состояния: процессный контекст по умолчанию (лениво, по политике устройства, закрывается shutdown hook'ом и
`resetDefault()`; настраивается до первого вызова через `configureDefault(builder -> ...)`), переопределение на поток и на время блока
`try (var s = JavaToGpu.use(ctx))` и размера запуска `try (var s = JavaToGpu.launch(LaunchConfig.of2D(w, h)))` (области вкладываются, закрывать нужно в обратном порядке).
Ядро и рантайм по-прежнему принимают явный `GpuContext`; фасад нужен только вызову `K.f(a, b)`, у которого другого способа узнать контекст нет.

**Weaver.** Чистая функция `Weaver.weave(byte[], KernelIndex) → Outcome` над ASM tree API плюс `weaveTree(Path)` для каталога class-файлов. Для статического `void`-метода
с `@Kernel` и записью в `kernels.idx`: (1) тело целиком (инструкции, локали, обработчики, номера строк, таблицы кадров) переезжает в `<имя>$jvm` с теми же сигнатурой и
флагами доступа, **без аннотаций**; (2) исходный метод сохраняет имя, сигнатуру, аннотации метода и параметров, а тело становится делегатом
`JavaToGpu.invoke(Owner.class, "имя", "<kernelId>", new Object[]{арг0, ...})`, скаляры упаковываются в обёртки, массивы передаются как есть. Подмена идемпотентна
(есть `<имя>$jvm` — метод пропускается), ядро не-static, не-void, без тела или без записи в индексе — замечание, а не молчаливый пропуск. Запись класса через
`ClassWriter(COMPUTE_MAXS)`: кадры не пересчитываются (делегат без ветвлений), загрузка классов не требуется. `weaveTree` переписывает файлы на месте через временный файл.
`kernelId` берётся из индекса (weaver не зависит от `ir` и не считает хэш).

**Gradle-плагин `io.github.deussixik.javatogpu`.** Тонкая обёртка: применяет `java`, добавляет зависимости (`implementation`: `api, ir, codegen-opencl, runtime`;
`annotationProcessor` и `testAnnotationProcessor`: `frontend-java, api, ir`), после каждой задачи `JavaCompile` вызывает `Weaver.weaveTree` над её каталогом
вывода, а задачам `Test` и `JavaExec` добавляет `--enable-native-access=ALL-UNNAMED`. Weave выполняется **внутри** задачи компиляции (`doLast`), поэтому up-to-date
и кэш сборки видят уже подменённые файлы, а повторный запуск ничего не меняет. Настройки `gpu { version, group, autoDependencies, weave, extraJvmArgs }`;
версия по умолчанию — из манифеста jar плагина. Зависимости перечислены явно (а не транзитивно), чтобы плагин работал и с `flatDir` без POM. Только Gradle;
Maven и Java-агент позже и `weaver` не меняют.

**Вызов ядра: порядок решений `JavaToGpu.invoke`.** (1) IR берётся из ресурса `META-INF/gpu/ir/<kernelId>.gir` **загрузчиком класса-владельца** (нет — `RT-F02`);
(2) размер запуска: область `launch(...)`, иначе 1D по длине первого массива среди аргументов (3.4), иначе `RT-L02`; (3) контекст: область `use(...)`, иначе
контекст по умолчанию; (4) `compile + launch`, ошибка запуска (аргументы, размеры) — `GpuException`, **не** fallback; (5) если устройства нет или ядро не
компилируется для него (любая ошибка стадии компиляции, включая `CG-U01`) и `Fallback.ALLOWED` — JVM-fallback, иначе `GpuException`.
Кэши (IR-модуль, обработчик `$jvm`) привязаны к классу-владельцу через `ClassValue`, а не к `kernelId`: одинаковый IR из разных загрузчиков не должен делить
обработчик (так нашёлся реальный дефект кэша по `kernelId`, он же удерживал бы загрузчик от выгрузки).

**JVM-fallback (3.5, 3.8).** Последовательный цикл по `global id` (z, y, x) поверх `<имя>$jvm` под `WorkItem.run`; размер work-group — из `reqd_work_group_size`
ядра, иначе заданный, иначе 1 (как в интерпретаторе). Исключения тела ядра (например, индекс за границами) пробрасываются как есть. События:
`GpuEvent.Kind.FALLBACK` **один раз на ядро и контекст** с причиной (диагностики компиляции); без контекста — одно сообщение `System.Logger` `com.sixik.gpu`
при неудачном создании контекста по умолчанию (повторных попыток найти устройство нет до `resetDefault()`). Ядра с `usesGroupSync` (barrier/local-память) на JVM не
уходят ни в одном режиме — `RT-F01`. Контекст получил политику `GpuContext.Fallback {ALLOWED, NEVER}` (по умолчанию `ALLOWED`) и метод `reportFallback`.
Диагностики фасада: `RT-F01` fallback невозможен, `RT-F02` нет/не читается IR-ресурс, `RT-F03` у класса нет `<имя>$jvm` (weave не выполнен), `RT-L02` размер не определён.

**Не вошло в M7.** Выбор варианта `fallback`-ядра из `@Kernel(fallback = ...)` при `RT-D02` (устройство без нужной возможности) — рантайм пока компилирует только
основное ядро, а `required`-вариант остаётся данными IR; дисковый кэш и prepared launcher; ядра-методы экземпляра и перегрузки с одинаковыми дескрипторами
(фронтенд их и так не принимает); Maven-плагин и Java-агент; публикация артефактов (координаты зависимостей плагина готовы, публикации нет). Хост-представление
`@Struct` и указатели в сигнатуре ядра (O3) — M8/M9.

**Тесты.** `weaver`: байткод-тесты на настоящих class-файлах (13); `runtime`: E2E без железа (16) — исходник → javac с processor'ом → weaver → загрузка → обычный
вызов на `FakeDeviceApi` и на JVM-fallback; `gradle-plugin`: TestKit (6) — вложенная сборка Gradle на тестовом проекте с плагином и `flatDir`; device-тест
`WovenKernelDeviceTest`: `computeSine` обычным вызовом на реальном OpenCL (NVIDIA GeForce RTX 5070) в строгом режиме `NEVER`, результат совпадает с `Math.sin` и с
`$jvm` в пределах 4 ULP. `KernelCompiler` (javac in-process с processor'ом) лежит в `testFixtures` weaver и переиспользуется.

## 6. DOD-модель данных ядра  `[IN PROGRESS]`

**[DECIDED] SoA на примитивных массивах.**

- Узлы IR — таблицы колонок: `int[] op`, `int[] type`, `int[] a`, `int[] b`, `int[] c` (+ боковые таблицы). Id узла =
  индекс. Ссылки только по id.
- Строки интернируются в string table; константы — в `long[]`/`double[]`; списки аргументов/операндов переменной длины —
  в общем `int[]` pool со смещением и длиной.
- Типы — тоже таблица (type id), без объектов-типов с иерархией.
- Логика — статические функции над данными (`Passes`, `Codegen`, `Validator`), без наследования и реестров.
- Builders пишут в таблицы; для отладки/тестов — read-only view и текстовый dumper (в `tools`, не в ядре).
- Правила портируемости: только примитивы/плоские массивы/record-подобные структуры; никаких `Object`-графов,
  reflection, статического изменяемого состояния, исключений как control flow.

*Открытые вопросы:* ёмкость id (int vs u32), рост массивов, стабильность порядка узлов (нужна для хеша IR и кэша),
иммутабельность после `freeze()`.

## 8. Кодогенерация и бэкенды (OpenCL → SPIR-V → CUDA/ROCm)  `[IN PROGRESS]`

**[DECIDED] v1: только OpenCL C.** (ROCm-устройства покрываются через OpenCL.)

- Кодоген = чистая функция «оптимизированный IR + целевые параметры → артефакт (текст/бинарь)». Никаких зависимостей от
  рантайма.
- CUDA C/PTX и SPIR-V — **позже, отдельными эмиттерами** поверх того же IR, без переделки ядра. До тех пор CUDA-код
  замораживается/вырезается из основного артефакта.

### 8.A Детали кодгена OpenCL C

**[DECIDED] 8.1 Вид кода — читаемый.** Имена локалей/функций берутся из debug-секции IR (иначе `v12` / `f3`), манглинг
детерминированный; на каждый стейтмент `#line N "File.java"`, чтобы ошибки драйвера и профайлеры указывали на
Java-исходник. В **release-режиме** debug-вывод выключен (имена и `#line` не попадают в текст), поэтому текст и ключ
кэша бинаря драйвера стабильны. Golden-файлы фиксируются в release-режиме; отдельный набор golden — для debug-режима.

**[DECIDED, делегировано Claude] 8.4 Требуемые возможности устройства.** `IrModule` несёт битовую маску
`required_features` (fp64, int64-atomics, fp16, …; images — позже), вычисляется валидатором IR. Кодген эмитит нужные
`#pragma OPENCL EXTENSION … : enable`; рантайм проверяет маску против возможностей устройства **до** компиляции и отдаёт
понятную диагностику («устройство X не поддерживает fp64; ядро K использует double в строке N») — вместо ошибки сборки
драйвера. Тот же механизм используется выбором устройства (политика отсеивает неподходящие).

**[DECIDED] 8.3 Семантика float — strict по умолчанию.**

- Кодген эмитит `#pragma OPENCL FP_CONTRACT OFF`; без `-cl-fast-relaxed-math` / `-cl-mad-enable`. Опция `fastMath=true`
  в compile options снимает ограничения (входит в ключ кэша).
- Таблица builtins хранит **допустимую погрешность в ULP** для каждой математической функции; на ней строятся
  дифференциальные тесты: `JVM ↔ IR-интерпретатор ↔ GPU` для float сравниваются «в ULP», для целых и логики — точно.
- Битовое равенство float между JVM и GPU **не обещаем** (в документации явно); обещаем детерминизм кодгена и
  воспроизводимость на одном устройстве/драйвере.

**[DECIDED, уточнение автора] 8.5 Адаптация под вендора — автоматическая, в кодгене (реализация после v1; шов в v1).**

- Адаптация под AMD / NVIDIA / Intel делается **автоматически кодгеном**, а не ручными пользовательскими вариантами: тот
  же vendor-neutral IR → разный OpenCL C под разные вендоры/классы устройств (размер warp/wavefront/subgroup, кратность
  work-group, расширения, особенности local memory и т.п.).
- **Шов в v1:** кодген — чистая функция `emit(IrModule, Target) → Artifact`, где `Target` =
  `{backend, vendor, deviceClass, features, subGroupSize, computeUnits, …}` из `DeviceInfo`. В v1 вендор-специфичных
  правил нет (единый нейтральный путь), но `Target` уже передаётся и входит в ключ кэша бинаря (9.3) и в golden-имя
  файла.
- **Вендорные знания — данные, не код:** таблица правил («quirks») по вендору/классу устройства (формат — рядом с
  таблицей builtins, 5.7); источник для наполнения — накопленные знания legacy (`Device-Quirks.md`,
  `ir-vendor-optimizer`). Правила, меняющие результат (8.3), требуют явного согласия пользователя.
- IR остаётся vendor-neutral всегда; вендорная специализация происходит только на выходе (в кодгене).
- Проверка: golden-файлы по таргетам + device-тесты по тегу (раздел 13); Rust-версия обязана выдавать тот же текст для
  того же `Target`.

**[DECIDED, делегировано Claude] 8.2 Сигнатура kernel и ABI.**

- `Array(T)` → два аргумента `__global T* name, int name_len`; индексы и длина массива — `I32` (как в Java). Лимит v1:
  `2^31 − 1` элементов на массив; 64-битные размеры — позже (место в IR: `array_len` типизирован `I32`, смена — через
  версию формата).
- Скаляры/векторы/struct-значения — по значению; большие struct — по значению же (OpenCL допускает struct в аргументах
  kernel) либо через `__global`-буфер при ограничениях драйвера (решает ABI-функция раскладки).
- `Local*Ptr` аргументы — `__local T*` с размером из launch-конфига.
- Раскладка и порядок аргументов — чистая ABI-функция над таблицей типов, общая для codegen и runtime (чтобы упаковка
  аргументов и сигнатура не разошлись).

## 9. Рантайм (устройства, память, запуск, кэш)  `[IN PROGRESS]`

**Базовый набор:** найти устройство → скомпилировать → залить буферы → запустить → забрать результат → понятные ошибки.

**[DECIDED] 9.6 `@GPUTest` — тонкая тест-библиотека.** Отдельный модуль `test-support` (JUnit 5). `@GPUTest` — обычный
тестовый метод; данные описываются кодом (генераторы/seed). `GpuAssert.sameResult(K.class, "f", args…)` прогоняет
`<name>$jvm` → (IR-интерпретатор) → GPU и сравнивает: целые/логика — точно, float — в ULP из таблицы builtins (8.3).
Device-тесты помечаются тегом (раздел 13). Никаких fixture-ресурсов, payload-парсеров, probe-кэшей и метаданных тестов в
IR/процессоре; `runtime/methodtest` (≈9k строк) не переносится.

**[DECIDED] 9.4 Выбор устройства — `DevicePolicy` как данные.**

- Фильтры: тип устройства (GPU/CPU/ANY), vendor, минимум global memory, обязательные `required_features` (fp64 и т.п. —
  мы знаем их из IR, 8.4).
- Явный override: id/имя через `GpuContext.builder()` и env/system property (`JAVATOGPU_DEVICE=nvidia:0`); побеждает
  фильтры.
- Выбор среди оставшихся — **один задокументированный детерминированный порядок** (GPU раньше CPU/accelerator, дальше
  порядок перечисления платформ/устройств). Никаких score-contributors и workload-hints.
- **Отложено (будущие планы, 9A):** ранжирование по измеренным профилям, Benchmark и self-test устройств. В v1
  `DevicePolicy` = фильтры + override + детерминированный порядок.

**[DECIDED, делегировано Claude] 9.5 Доступ к буферам определяется IR.** Валидатор IR считает для каждого
параметра-массива режим доступа (`READ`, `WRITE`, `READ_WRITE`) — для вызова через сахар массивов рантайм загружает
только читаемые и копирует обратно только записываемые. Вместо флагов-масок
`withoutHostUploadArguments/withoutHostReadbackArguments` (старый API) пользователь управляет копиями владением
`GpuBuffer`.

**[DECIDED] 9.3 Дисковый кэш.** Включён по умолчанию в user-cache dir ОС (Windows `%LOCALAPPDATA%\javatogpu`, Linux
`~/.cache/javatogpu`, macOS `~/Library/Caches/javatogpu`); отключается/переопределяется:
`GpuContext.builder().diskCache(path | OFF)`.

- Ключ = `hash(IR без debug-секции)` + версия кодгена + устройство (vendor, name, driver version) + compile options (
  включая `fastMath`, режим debug/release).
- Атомарная запись (tmp + rename); повреждённый файл = промах и пересборка; LRU-очистка по размеру. Кэш в памяти —
  поверх диска.

**[DECIDED] 9.2 Платформа: Java 25 LTS + FFM (Panama), без LWJGL.**

- Базовая версия Java для всех модулей — **25**. Пользователи на Java 17/21 в alpha не поддерживаются (осознанно).
- `DeviceApi` — наш тонкий слой над `libOpenCL` через `java.lang.foreign` (≈40 функций OpenCL в одном модуле/файле).
  Сторонних нативных зависимостей нет; `.lwjgl/*.dll` и LWJGL BOM удаляются. `GPU.java` больше не зависит от
  `org.lwjgl.opencl.CL10` (константы — свои).
- Нужен `--enable-native-access=ALL-UNNAMED` для приложений/тестов: Gradle-плагин (3.6) выставляет его для `test`/`run`
  задач автоматически.
- Отсутствие `libOpenCL` / ошибка загрузки = «устройств нет» → политика fallback (3.8), а не падение при старте.
- Модель `DeviceApi` (≈ список C-функций OpenCL) 1:1 повторяется в Rust (`opencl3`/FFI) — это и есть граница
  портирования рантайма.

**[DECIDED] 9.1 Потоки.** `GpuContext` потокобезопасен: кэш компиляции concurrent (одна компиляция на ключ, остальные
ждут), запуски на одном устройстве сериализуются через внутреннюю in-order очередь (v1 — синхронный запуск с ожиданием;
async позже — тривиальное расширение). `GpuBuffer` внутри не потокобезопасен (пользователь не должен конкурентно
использовать один буфер).

**[DECIDED] Дополнительно в v1:**

- Выбор устройства **по политике** (ранжирование/предпочтения/override). Политика — данные + одна функция выбора, без
  реестров и SPI-иерархий.
- **Kernel-кэш: память + диск** (ключ = IR-hash + device + compile options; на диске — бинарь драйвера).
- **Prepared launcher (hot path)**: переиспользуемые буферы, static-аргументы, политика upload/readback. Одна реализация
  вместо трёх вложенных.
- **JVM-fallback + `@GPUTest`**: выполнение того же метода на JVM, если GPU недоступен; сравнение GPU↔JVM как референс
  для тестов.

**[DECIDED] Модель данных пользователя: массивы как сахар + явный `GpuBuffer`.**

- Первоклассный объект — `GpuBuffer` (device-resident; явное владение и время жизни; нет лишних копий между запусками).
  В Rust-версии = handle.
- `float[]/int[]/…` в вызове `@GPU` метода — синтаксический сахар: рантайм создаёт временный `GpuBuffer`, копирует туда
  и обратно по политике.
- Prepared launcher оперирует `GpuBuffer`; static-аргументы и политика upload/readback выражаются владением буфером, а
  не флагами-масками.
- Следствие: `@GPU` методы должны допускать в сигнатуре и массив, и буфер/указатель (маппинг на один и тот же тип IR) —
  детали в разделе 5.

*Открытые вопросы:* pinned/zero-copy, модель ошибок, потокобезопасность, lifecycle сессии/контекста, статистика.

## 9A. Адаптивный рантайм (будущий план, не v1)  `[DESIGNED — post-v1]`

**Видение автора:**

1. Пишешь GPU-код на родном языке — библиотека преобразует его в правильный код под устройство (произвольный код не
   допускается).
2. Ключевая боль — адаптация под разные GPU. Аппаратно-независимые оптимизации (e-graph, раздел 7) ничего не знают о
   конкретной карте; **значимая подстройка под железо возможна только через измерения** — это `AutoTune`. Без тестовых
   данных/измерений оптимизироваться нечему.
3. Несколько видеокарт, в т.ч. разнородных (пример автора: RTX 5070 + GTX 1060 + Arc B580 + RX 480): заготовленный
   Benchmark устройств; результаты `AutoTune` метода приоритетнее общего Benchmark; распределение работы (например ~
   80/20 между мощной и слабой картой); runtime-балансировщик нагрузки; слабые GPU можно исключать — **всегда с записью
   в лог** (причина + измеренные числа).

**Статус (уточнение автора):** Multi-GPU, AutoTune и адаптация кода под производителя (AMD / NVIDIA / Intel) — **будущие
планы, наравне с Rust backend; в v1 не входят.** Раздел — проработанная заготовка дизайна, чтобы v1 не закрыл к ней
дорогу (швы — в 9A.4).

**Компоненты (черновик):**
| Компонент | Роль |
|---|---|
| `DeviceBenchmark` | Заготовленный набор микро-бенчмарков (fp32/int throughput, пропускная способность памяти, H2D/D2H,
задержка запуска) → профиль устройства |
| `ProfileStore` | Постоянное хранилище профилей: ключ = устройство (vendor, name, driver) → benchmark; (kernelHash,
устройство, размеры) → результаты AutoTune |
| `TuneSpace` / `AutoTuner` | Пространство кандидатов (work-group, параметры специализации, варианты метода) и измерение
на устройстве |
| `Scheduler` | Распределение работы по устройствам по измеренной производительности (приоритет: профиль метода > общий
benchmark) |
| `Balancer` | Динамическое перераспределение: простаивающая слабая карта подхватывает задачи при условиях пригодности |
| `ExclusionPolicy` | Исключение слабых устройств с обязательным событием в лог |

**[DECIDED] 9A.1 Гранулярность: задачи целиком.** Раздаём по картам *целые запуски ядер* через очередь с work-stealing и
оценкой времени завершения; разбиение одного NDRange между картами — **потом** (в IR закладываем метаданные доступа к
параметрам — уже есть из 9.5 — под будущий анализ «пишет только в свой индекс»).

- Следствия: нужен async-API (`submit(...) → GpuFuture`); буфер привязан к устройству, перенос между картами — через
  хост с учётом стоимости (PCIe) в оценке времени; зависимости между запусками (выход одного — вход другого) удерживают
  цепочку на одной карте, если перенос дороже выигрыша.

**[DECIDED] 9A.2 Данные для AutoTune — только от пользователя.** Источник тестовых данных: `testParameters` (JSON из
концепта) и/или Java-генератор в коде. Синтетические данные, замеры на реальных вызовах и фоновый тюнинг — **не делаем
** (риск неверного профиля для data-зависимых ядер и скрытых побочных эффектов; тюнинг должен быть предсказуем).

- Ядро без тестовых данных **не тюнится**: используется дефолтная конфигурация + общий Benchmark устройства. Это явное
  событие в логе («kernel K: нет тестовых данных, AutoTune пропущен»).
- Единая абстракция **`KernelSample`** (генератор аргументов + опциональные ожидаемые результаты + класс размера)
  используется и `@GPUTest` (9.6), и `AutoTune`; JSON из концепта — один из загрузчиков `KernelSample`. Это возвращает
  JSON-фикстуры, но как тонкий загрузчик, а не как подсистему `runtime/methodtest`.
- `verifyWithCpu`: результат лучшего кандидата сверяется с `$jvm` (ULP/точно по 8.3) на тех же данных — защита от
  «быстрого, но неверного» кандидата.

**[DECIDED] 9A.3 Правило слабой карты = оценка времени завершения + 48 % как защита от аномалий.**

- Задача уходит на ту карту, где **ожидаемое время завершения** минимально:
  `очередь карты + время выполнения (профиль метода, иначе общий benchmark) + перенос данных`. Слабая карта берёт
  задачу, если закончит не позже, чем быстрая с учётом её очереди — отсюда естественное распределение ~80/20.
- Порог **48 %** — защита от аномалий: если для данного ядра измеренное отставание слабой карты **больше ожидаемого по
  общему benchmark более чем на 48 %**, ядро «не для этой карты» и она его не берёт (даже при простое). Порог
  настраиваемый.
- Исключение карт из пула (`ExclusionPolicy`): по порогу минимального вклада; **каждое исключение — событие в лог** (
  карта, причина, числа benchmark/AutoTune, порог).

**[DECIDED, уточнение автора] 9A.4 Статус и вехи.**

- Всё описанное в 9A (Benchmark, ProfileStore, AutoTune, мульти-GPU, балансировщик, адаптация под вендоров) — **после v1
  **. v1 = ядро (раздел 14, M0–M14).
- **Швы, закладываемые в v1 (дёшево, чтобы потом не переделывать):**
    1. Формат IR: зарезервированы `SPEC_CONST`, `KernelGroup` (варианты с одной ABI и предикатом применимости по
       `DeviceInfo`), атрибуты функции (`reqd_wg`, `inline`, `opt`, `required`, `tune_candidates`, `body_kind`); версия
       формата.
    2. Режимы доступа к параметрам (9.5).
    3. `DeviceInfo` (vendor, name, driver, features, sub-group size, compute units, memory) — единый источник для
       политики (9.4), ключа кэша (9.3) и будущих профилей.
    4. `GpuContext` потокобезопасен (9.1); выбор устройства — одна точка (`DevicePolicy`).
    5. `KernelSample` — общая абстракция для `@GPUTest` (9.6) и будущего AutoTune.
    6. События `EventListener` несут id устройства.
- **Не делаем в v1:** async `submit`, набор устройств в контексте, `Scheduler`, Benchmark, ProfileStore, `@AutoTune`,
  `@Tunable`. `GpuContext` = ровно одно активное устройство.
- Из директив концепта в v1: `@WorkGroup`, `required`, `fallback`-вариант (выбор по `required`, без измерений),
  `inline`/`optLevel` (информативны, оптимизатора нет).

**[DECIDED] 9A.5 TuneSpace v1 = три измерения:**

1. **Work-group size** (1D/2D/3D) — кандидаты как в концепте (`@WorkGroup` в `candidates`).
2. **Specialization constants** — именованные параметры компиляции (`@Tunable(values = {4, 8, 16}) int TILE`: размер
   тайла, unroll, ширина вектора, использовать ли local memory). В IR — узел `SPEC_CONST(id)` + таблица кандидатов (
   аналог SPIR-V spec constants); значение подставляется кодгеном при JIT и входит в ключ кэша бинаря.
3. **Варианты метода** — несколько Java-реализаций одного логического ядра с **одной ABI** (naive / tiled / vectorized).
   `fallback` из концепта — частный случай: вариант, который берётся, когда `required` не выполнено; AutoTune выбирает
   лучший среди вариантов, **допустимых** на устройстве.

- Флаги компиляции драйвера **не** подбираются автоматически (меняют результат, 8.3) — только по явному согласию
  пользователя.

**[DECIDED, делегировано Claude — пересматриваемо] Стратегия поиска и хранение.**

- Поиск не полный перебор (комбинаторный взрыв): этапами — сначала варианты × spec-константы на грубом размере, затем
  work-group для лучшего; ограничения `maxCandidates` / `maxTime` задаются в `@AutoTune`, при превышении берётся лучший
  найденный (+ событие в лог).
- Результат хранится в `ProfileStore` по ключу `(kernelHash, устройство, класс размера)`; **класс размера** =
  log2-корзина global size (оптимум для 1 К и 10 М элементов разный).
- Перед принятием кандидата — `verifyWithCpu` на тех же `KernelSample` (9A.2); неверный кандидат отбрасывается с
  событием.
- В IR закладывается: группа вариантов (`KernelGroup`: список функций с одной ABI + дефолтная), `SPEC_CONST` и таблица
  кандидатов, атрибут `tune_candidates` у функции.

**[DECIDED] 9A.6 Benchmark: быстрый автоматический + глубокий по явной команде.**

- **Quick** (< ~2 с): запускается автоматически при первом использовании устройства; результат в `ProfileStore`;
  повторяется при смене драйвера/устройства (ключ профиля содержит vendor + name + driver version).
- **Deep**: явно — `GpuContext.calibrate()` / Gradle-задача / CLI в `tools`; даёт точные числа для мульти-GPU (v1.1). В
  CI автоматического deep нет.
- Нет данных → консервативный профиль по характеристикам устройства (compute units × частота), помечается в логе как
  «оценочный».
- Состав набора (предложение): fp32/int32 throughput, fp64 (если есть), пропускная способность global memory, local
  memory, H2D/D2H, задержка запуска ядра; набор — **данные + заготовленные ядра**, без отдельной подсистемы.

*Открытые вопросы раздела:* модель зависимостей между задачами (v1.1), формат хранения профилей и их инвалидация.

## 13. Тестирование и бенчмарки  `[IN PROGRESS]`

**[DECIDED] Четыре уровня проверки:**

1. **IR-интерпретатор на CPU** (эталон семантики IR, виртуальные `global_id/local_id/group_id`, барьеры).
   Дифференциальные тесты: `JVM-метод (<name>$jvm)` ↔ `IR-интерпретатор` ↔ `GPU`. Проверяет фронтенд и IR без железа.

## 16. Будущие планы (post-v1): желаемые возможности автора  `[IN PROGRESS]`

**Ключевые будущие планы автора (наравне с Rust backend):** Multi-GPU + балансировщик, AutoTune + Benchmark, адаптация

Порядок работы: сначала детально проработать v1 (разделы 1–14), затем собрать сюда список желаемых возможностей, для

3. Приоритет и зависимость от других пунктов.

*Входные данные от автора:*

**Rust-принимающая сторона (AnyToGpu).** Язык-фронтенд передаёт в Rust **IR в бинарном виде** (IRBinary, формат — 5.9);
Rust сам оптимизирует (e-graph живёт там), генерирует код под устройство и возвращает **ссылку на вызов** (
`KernelHandle`, непрозрачный id). Дальше фронтенд вызывает `launch(handle, args…)`. Это ровно та схема, на которую
рассчитан v1 (JIT, IR-как-контракт, 1:1 `DeviceApi`); для неё в Java-версии уже закладываем: `kernelId = hash(IR)`,
`KernelHandle` в API рантайма, оптимизатор строго на стороне потребителя IR (не во фронтенде).
**[DECIDED] Формат IRBinary = колонки (5.9), единственный** — для диска, FFI и Rust. Линейный «байткод» (varint,
WASM-style) — только как возможный транспортный слой позже (декодер в те же таблицы), если станут важны размер/стриминг;
в v1 не делаем.
