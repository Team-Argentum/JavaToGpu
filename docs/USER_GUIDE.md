# Руководство пользователя gpu

Состояние: подготовка alpha, версия сборки `0.2.0-SNAPSHOT`. Поддерживаются Java 25 и javac;
единственный бэкенд v1 — OpenCL C. Реальное устройство в текущих проверках — NVIDIA GeForce RTX 5070;
результаты для AMD и Intel пока не подтверждены.

## Подключение

Сначала соберите локальный Maven-репозиторий:

```powershell
.\gradlew.bat publishLocal
```

Чтобы посмотреть возможности на запускаемых примерах, пройдите [тур](../examples/tour/README.md): двенадцать коротких
уроков от первого ядра до слияния ядер и явного API, каждый с комментариями и идеями, что поменять.

Далее используйте [независимый Gradle-проект](../examples/standalone/README.md). Он содержит полные настройки
`pluginManagement`, репозитория библиотек, JDK и JUnit. Задача `publishLocal` пишет только в `build/local-maven`.

Релизы собирает JitPack по git-тегу: `com.github.Team-Argentum.JavaToGpu:<модуль>:<тег>` из репозитория
`https://jitpack.io`. Плагин подключается по id `io.github.deussixik.javatogpu` через `resolutionStrategy`, который
сопоставляет id модулю `gradle-plugin`; плагин из JitPack сам берёт библиотеки той же группы и версии. Готовые
фрагменты `settings.gradle`/`build.gradle` — [docs/AGENTS.md](AGENTS.md), раздел 3.

Потребителю нужны JDK 25 для приложения и **JDK 25 для запуска Gradle с плагином**. Сам репозиторий библиотеки
можно собирать Gradle на 21+ с установленным toolchain 25. Плагин подключает `api`, `ir`, `ir-optimizer`, `codegen-opencl`,
`runtime`, бэкенд драйвера, processor `frontend-java` и подменяет тела `@Kernel` после javac. Для `Test` и `JavaExec` он
добавляет `--enable-native-access=ALL-UNNAMED`; в `applicationDefaultJvmArgs` для скриптов `installDist` этот флаг задаётся отдельно.

### Бэкенд драйвера и Java 17

Ядро рантайма (`runtime`) и компиляторная часть (`api`, `ir`, `ir-optimizer`, `codegen-opencl`, `frontend-common`,
`frontend-asm`) собраны под **Java 17**: их можно встраивать в приложения на Java 17 и новее (Minecraft 1.18–1.21.x).
Эталонный интерпретатор `ir-interpreter` нужен только тестам и инструментам и собран под Java 21. Вызовы OpenCL
вынесены в отдельный модуль-бэкенд:

| Модуль | Java | Как вызывает OpenCL |
|---|---|---|
| `runtime-opencl-ffm` | 25 | FFM (`java.lang.foreign`), без сторонних нативов. По умолчанию |
| `runtime-opencl-lwjgl` | 17 | `lwjgl-opencl` 3.3.3; ядро LWJGL с нативами даёт приложение (например, Minecraft) |

```groovy
gpu {
    backend = 'lwjgl'   // 'ffm' (по умолчанию), 'lwjgl' или 'none' - бэкенд добавит сама сборка
}
```

Бэкенд находится через `ServiceLoader` (`DeviceApiProvider`). Если на classpath оба, выбирается FFM, когда JVM 25+, иначе
LWJGL; явно — `-Djavatogpu.backend=ffm|lwjgl` или `JAVATOGPU_BACKEND`. Бэкенд, классы которого не грузятся в этой JVM,
пропускается. Для мода на Minecraft подключайте `runtime-opencl-lwjgl` (ядро LWJGL — `compileOnly`, его даёт игра),
при переходе мода на Java 25 достаточно заменить его на `runtime-opencl-ffm`: код мода не меняется. Бэкенд собран с
LWJGL 3.3.3 (как у Minecraft 1.21.1); версии игры до 1.20.5 дают более старое ядро LWJGL, и совместимость с ним пока
не проверена.

Память хоста в API рантайма — `HostMemory` (не `MemorySegment`): виды `GpuBuffer.readView()/writeView()` читаются
`view.getFloat(4L * i)`. С FFM-бэкендом тот же вид доступен как сегмент: `FfmMemory.segment(view)`.

### Фронтенд байткода

По умолчанию IR ядер строит annotation processor `frontend-java` во время javac. Второй вариант — `frontend-asm`: он
читает уже скомпилированные class-файлы и строит тот же IR.

```groovy
gpu {
    frontend = 'asm'   // 'java' (по умолчанию) или 'asm'
}
```

В режиме `'asm'` processor не подключается. После каждой задачи компиляции плагин строит IR из class-файлов, пишет
ресурсы `META-INF/gpu/**` и затем подменяет тела ядер. Зачем это нужно:

- **device-функции из JAR без исходников** — байткод библиотеки на classpath компиляции (у processor'а это `GPU0114`);
- **не только javac** — ядро, собранное другим JVM-компилятором, обрабатывается, если его байткод укладывается в то же
  подмножество Java.

Требования и отличия:

- class-файлы с `LocalVariableTable` (javac `-g`; Gradle и Maven так компилируют по умолчанию), иначе `GPU0301`;
- те же правила подмножества и те же коды `GPU####`, позиция — `pkg/Имя.java:строка` (колонок в байткоде нет);
  нарушение роняет задачу компиляции;
- байткод, который не сводится к структурному IR, отвергается кодами `GPU0302`–`GPU0306`;
- при инкрементальной сборке индекс ядер пересобирается по всему каталогу классов, IR удалённых ядер удаляется;
- `kernelId` и поведение совпадают с `frontend-java`. Константы, которые javac уже свернул, могут дать другой текст
  IR (`0` вместо `convert(0)`); после оптимизатора он тот же;
- смешанного режима нет: весь модуль собирается одним фронтендом.

Программный вход фронтенда байткода — `AsmJit.compile(Unit, Options)` (сгенерированные в памяти классы). Поля
`static` в нём можно привязать (`AsmJit.Unit.bindings`):

```java
Bindings b = Bindings.none()
        .constant("gen/Flags", "AQUIFERS", false)              // getstatic → константа, ветка сворачивается
        .table("gen/Tables", "PERM", new int[]{5, 3, 7, 1});    // getstatic → __constant int tbl0[4] = {...}
```

Таблица (`int[]`, `long[]`, `float[]`, `double[]`, `short[]`, `byte[]`, `char[]`) копируется при привязке и
печатается в программе инициализированным `__constant`-массивом. Ядро её индексирует и берёт `length`. Записывать в
неё и сохранять её в локальную переменную нельзя (`GPU0116`). Суммарный размер таблиц не должен превышать
`CL_DEVICE_MAX_CONSTANT_BUFFER_SIZE` устройства (обычно 64 КБ, иначе `RT-D04`): большие таблицы передавайте
буфером `@Global(constant = true)`.

## Первое ядро

```java
import com.sixik.gpu.api.Gpu;
import com.sixik.gpu.api.annotations.Global;
import com.sixik.gpu.api.annotations.Kernel;

public final class Kernels {
    @Kernel
    public static void scale(@Global float[] input, @Global float[] output, float factor) {
        int i = Gpu.getGlobalId(0);
        output[i] = input[i] * factor + 1f;
    }
}
```

Вызов `Kernels.scale(input, output, 2f)` выполняет ядро. По умолчанию global size — длина первого массива.
Остальные массивы должны вмещать все индексы, используемые ядром. Скаляр `factor` передаётся по значению.

Для двумерного запуска:

```java
import com.sixik.gpu.runtime.JavaToGpu;
import com.sixik.gpu.runtime.LaunchConfig;

try (var scope = JavaToGpu.launch(LaunchConfig.of2D(width, height))) {
    Kernels2D.compute(input, output);
}
```

Ядро само использует `Gpu.getGlobalId(0)` и `Gpu.getGlobalId(1)` для вычисления линейного индекса.
`@WorkGroup(x = 256)` задаёт обязательный размер группы: global size по соответствующей оси должен делиться на него.
Без явного размера группы на устройстве его выбирает драйвер.

## Подмножество Java

| Возможность | Поддержка v1 |
|---|---|
| Ядро | `static void`, без перегрузок имени ядра |
| Числа | арифметика `int`, `long`, `float`, `double`; `byte`, `short`, `char` — хранение и преобразования |
| Массивы | одномерные примитивные массивы, массивы поддерживаемых векторов и struct |
| Управление | `if`, `for`, `while`, `do-while`, statement-`switch`, обычные `break`, `continue`, `return` |
| Функции | статические `@DeviceFunction` из той же компиляции, без рекурсии |
| Векторы | неизменяемые `Float/Double/Int/Long × 2/3/4/8/16`, операции и покомпонентные builtins |
| Struct | `@Struct`, value-семантика, вложенные struct и векторы; без массивов и указателей внутри |
| Память | `@Global`, `@Global(constant = true)`, приватные массивы константного размера, `@Local` в теле ядра; параметры device-функций `@Local` и `@Private` |
| Указатели | ссылки `FloatPtr` и аналоги; `Global/Local/Constant*Ptr` внутри ядра и в device-функциях |
| Синхронизация | work-group barriers, целочисленные атомики 32/64 бит при поддержке устройства (`atomicAdd`…`atomicXchg`, `atomicCmpxchg`) |

Запрещены произвольные объекты и куча, виртуальные вызовы, исключения, `try`, мониторы, строки,
лямбды, рекурсия, `for-each`, labeled `break/continue`, switch-выражения и pattern matching.
Создание поддерживаемых векторов, struct и pointer-обёрток допускается по правилам этих типов.

Device-функции из JAR без исходников processor не связывает (`GPU0114`): их исходники должны входить в ту же
компиляцию, либо модуль собирается фронтендом байткода (`gpu { frontend = 'asm' }`, см. «Подключение»).
Аннотация `@DeviceFunction` обязательна и для приватного helper-метода.

Параметр-массив device-функции без аннотации — `__global`. Чтобы передать в helper массив, созданный в теле
(`int[] stack = new int[16];`), пометьте параметр `@Private`: массив передаётся по ссылке, записи видны вызывающему,
`stack.length` работает. Массив другого пространства — ошибка `GPU0121`; `@Private` у параметра ядра, у скаляра или
вместе с `@Local`/`@Global` — `GPU0123`.

```java
@DeviceFunction
static int push(@Private int[] stack, int top, int v) {
    stack[top] = v;
    return top + 1;
}
```

`Gpu.atomicCmpxchg(ptr, expected, value)` — сравнение с обменом (`atomic_cmpxchg`, для `long` — `atom_cmpxchg` из
`cl_khr_int64_base_atomics`): записывает `value`, если ячейка равна `expected`, и возвращает прежнее значение.

У struct открытые изменяемые поля и конструктор без аргументов для хоста; конструктор по полям сохраняет значения.
Чтобы получить самостоятельное значение в ядре, используйте `new`, глубокий `copy()` либо результат `@DeviceFunction`.
Простое присваивание struct-переменной другой переменной запрещено: JVM-ссылка и GPU-копия дали бы разное поведение.
Вектор `Float3` занимает 16 байт в OpenCL ABI.

## Контекст и fallback

При обычном вызове используется ленивый контекст по умолчанию. Настройки задаются до первого запуска:

```java
JavaToGpu.configureDefault(builder -> builder
        .fallback(com.sixik.gpu.runtime.GpuContext.Fallback.NEVER)
        .listener(event -> System.out.println(event.kind() + ": " + event.detail())));
```

Собственный контекст можно ограничить областью:

```java
try (var context = com.sixik.gpu.runtime.GpuContext.builder().build();
     var scope = JavaToGpu.use(context)) {
    Kernels.scale(input, output, 2f);
}
```

По умолчанию при отсутствии устройства либо отказе компиляции ядра используется JVM: последовательный цикл
по work-item поверх оригинального тела `$jvm`. Причина перехода записывается в предупреждение.
Ошибки аргументов и размеров запуска не маскируются fallback. `Fallback.NEVER` запрещает переход на JVM,
включая отсутствие устройства при создании контекста по умолчанию; `builder.build()` отдельно сообщает об отсутствии устройства.

**Ядрам с barrier или local memory требуется устройство** (`RT-F01`). Для их проверки без железа есть
IR-интерпретатор в `test-support`. Он не используется как production-fallback. Подготовленные запуски также требуют устройства.

Выбор устройства: `builder.device("nvidia:0")`, свойство `javatogpu.device` либо `JAVATOGPU_DEVICE`.
Явный выбор побеждает фильтры. По умолчанию предпочтительны GPU, затем действует порядок перечисления драйвера.
`GpuContext` потокобезопасен; обращения к одному устройству сериализуются. `GpuBuffer` и `PreparedLauncher`
пользователь не должен изменять конкурентно.

## Массивы, GpuBuffer и подготовленные запуски

Массивы удобны для единичных вызовов. Перед каждым запуском **все массивы целиком** загружаются на устройство,
после него обратно копируются только записываемые ядром. Так сохраняются элементы, которые ядро не изменило.
Один массив в двух параметрах соответствует одному буферу, права доступа объединяются.

Для повторных запусков:

```java
try (var context = com.sixik.gpu.runtime.GpuContext.builder().build();
     var scope = JavaToGpu.use(context);
     var prepared = JavaToGpu.prepare(Kernels.class, "scale", input, output, 2f)) {
    prepared.run(LaunchConfig.of1D(input.length));
    prepared.set(2, 3f);
    prepared.run(LaunchConfig.of1D(input.length));
}
```

`PreparedLauncher` переиспользует выделенную память, но массивы хоста всё равно передаёт целиком при каждом запуске.
Для цепочек ядер без передач на хост используйте `GpuBuffer`:

```java
try (var context = com.sixik.gpu.runtime.GpuContext.builder().build();
     var scope = JavaToGpu.use(context);
     var deviceInput = context.upload(input);
     var deviceOutput = context.allocate(com.sixik.gpu.ir.Types.F32, input.length);
     var prepared = JavaToGpu.prepare(Kernels.class, "scale", deviceInput, deviceOutput, 2f)) {
    prepared.run(LaunchConfig.of1D(input.length));
    deviceOutput.read(output);
}
```

Буферы принадлежат пользователю и закрываются им. Подготовленный запуск освобождает только собственные буферы.
`set` заменяет скаляр, значение агрегата или `GpuBuffer`; для замены массива хоста создайте новый запуск.
`GpuBuffer` массивов векторов/struct пока не поддержан (`RT-A02`).

Массив, который ядро только пишет и перезаписывает целиком, на устройство не загружается — передаётся только обратно.
Распознаётся запись на верхнем уровне тела (не внутри `if`/цикла и не после возможного `return`) по индексу вида:

- `out[Gpu.getGlobalId(0)]` — запуск по оси 0 равен длине массива;
- `out[y * width + x]` (`x`, `y` — `getGlobalId(0)`, `getGlobalId(1)`) — `width` равен размеру запуска по оси 0, длина
  массива — `width * ` размер по оси 1;
- `out[(z * ny + y) * nx + x]` и т.п. для трёх осей; шагом может быть `int`-параметр, константа или
  `Gpu.getGlobalSize(k)`, промежуточные значения можно держать в локалях, которым присвоено один раз.

Условие проверяется перед каждым запуском по фактическим размерам и аргументам. Если ядро пишет лишь часть элементов
(запуск уже массива, смещённый индекс), массив загружается, и нетронутые элементы сохраняют значения хоста. Для
изображения 4096×1536 `int` (25 МБ) это 4.3 мс на запуск против 7.3–8.0 мс с загрузкой.

Крупные массивы (от 1 МиБ) передаются через закреплённую (pinned) память и копируются в Java-массив несколькими потоками:
на PCIe это примерно вдвое быстрее. Подготовленный запуск (`ctx.prepare`) держит такую память для своих массивов всё время
жизни; обычный `ctx.launch` и `GpuBuffer` делят один буфер контекста.

Обычный вызов ядра `Kernels.scale(input, output, 2f)` сам переиспользует подготовленный запуск: если ядро снова вызвано
с теми же массивами (теми же объектами), буферы устройства и закреплённая память не выделяются заново. Результат тот же:
входы загружаются при каждом вызове, поэтому изменения массивов между вызовами видны, скаляры подставляются заново.
Контекст держит до 16 таких запусков и до 512 МиБ массивов, лишние вытесняются; пока запуск в кэше, он удерживает
ссылки на свои массивы, освободить всё сразу можно через `GpuContext.trimLaunchCache()`. Явный `prepare` нужен, только
если хочется управлять временем жизни буферов самому.

Если результат нужен не в Java-массиве, а для дальнейшей обработки, его можно читать без копирования:
`GpuBuffer.readView()` переносит содержимое буфера в закреплённую память и возвращает `MemorySegment` только для чтения.
Для 23.6 МБ это 0.85 мс против 2.3 мс у `read(float[])`.

```java
try (GpuBuffer out = ctx.allocate(Types.F32, n)) {
    ctx.launch(kernel, LaunchConfig.of1D(n), out, input);
    MemorySegment v = out.readView();
    float first = v.getAtIndex(ValueLayout.JAVA_FLOAT, 0);
}
```

Вид действует до закрытия буфера или контекста (после закрытия обращение бросает `IllegalStateException`). Следующий
`readView()` перезаписывает ту же память.

Вход можно так же заполнять без Java-массива: `GpuBuffer.writeView()` возвращает изменяемый `MemorySegment` на ту же
закреплённую память, `commitView()` передаёт его на устройство. Передача 23.6 МБ — 1.3 мс против 2.9 мс у
`write(float[])`; вместе с заполнением (значения пишутся в вид вместо массива) — 3.7 мс против 4.4 мс.

```java
try (GpuBuffer in = ctx.allocate(Types.F32, n)) {
    MemorySegment w = in.writeView();
    for (int i = 0; i < n; i++) {
        w.setAtIndex(ValueLayout.JAVA_FLOAT, i, source(i));
    }
    in.commitView();                 // блокирующая передача; после неё вид можно снова менять
    ctx.launch(kernel, LaunchConfig.of1D(n), out, in);
}
```

`writeView()` сам ничего не передаёт: содержимое вида — то, что в нём осталось (после `readView()` — прочитанное, у новой
памяти — не определено). Пара `readView()` → правка в `writeView()` → `commitView()` меняет буфер на месте; `readView()`
до `commitView()` перезаписывает незафиксированные изменения.

## Несколько ядер одной программой

Модуль IR с несколькими ядрами (например, `AsmJit.Result.module()` фронтенда байткода) можно собрать одной программой
драйвера: общие `@DeviceFunction` компилируются один раз, образ на диске — один на модуль.

```java
CompiledProgram program = context.compileProgram(jit.module()).value();
context.launch(program.kernel("square"), LaunchConfig.of1D(a.length), (Object) a);
```

`kernel(String)` ищет по имени метода (или имени `__kernel`), `kernel(int)` — по индексу функции в модуле
(`AsmJit.Kernel.function()`). Подбора `fallback`-вариантов здесь нет: если устройство не поддерживает то, что нужно
хотя бы одному ядру, вся программа получает `RT-D02`. Для своего рантайма OpenCL тот же модуль превращается в текст и
ABI ядер без `runtime`: `OpenClEmitter.program(module, EmitOptions.RELEASE)` → `ClProgram` (исходник, опции сборки,
по ядру — порядок аргументов `clSetKernelArg`, тип и размер элемента, адресное пространство, чтение/запись буфера,
`localMemoryBytes()` объявленных `@Local`-массивов; у программы — `constantBytes()` таблиц констант). Сравните их с
`CL_DEVICE_LOCAL_MEM_SIZE` и `CL_DEVICE_MAX_CONSTANT_BUFFER_SIZE` до `clBuildProgram`.

## Массивы, данные которых живут на устройстве

`GpuFloatArray`, `GpuIntArray`, `GpuLongArray` и `GpuDoubleArray` (пакет `com.sixik.gpu.api.types`) пишутся в сигнатуре
ядра вместо `float[]` и т.д. Внутри ядра — `a.get(i)`, `a.set(i, v)`, `a.length()`: это компилируется в то же, что
`a[i]` и `a.length`. Отличие в том, где лежат данные между вызовами:

- ядро, записавшее массив, оставляет свежие данные на устройстве; на хост они читаются лениво — при первом `get`,
  `toArray` или `copyTo`;
- запись с хоста (`set`, `fill`, `copyFrom`) помечает копию устройства устаревшей, и следующий вызов загрузит массив;
- цепочка ядер, передающих массив друг другу, не гоняет данные через шину.

```java
@Kernel
public static void step(GpuFloatArray a, GpuFloatArray b, float k) {
    int i = Gpu.getGlobalId(0);
    b.set(i, a.get(i) * k + 1f);
}

GpuFloatArray a = GpuFloatArray.of(initial);
GpuFloatArray b = new GpuFloatArray(initial.length);
for (int s = 0; s < 20; s++) {
    Kernels.step(s % 2 == 0 ? a : b, s % 2 == 0 ? b : a, 0.5f);
}
float[] result = a.toArray(); // единственное чтение с устройства
```

На RTX 5070 такая цепочка из 20 шагов над 16 МБ занимает 15.6 мс против 92 мс с `float[]`, результат совпадает
побитово. Вызовы с такими массивами не ждут завершения ядра, если хосту из них ничего не нужно читать: ожидание
происходит один раз, при первом чтении на хосте. Поэтому `LaunchStats.kernelNanos` такого запуска — время постановки
в очередь, а возможная ошибка исполнения ядра проявится при следующем чтении (`RT-X01`); сообщение тогда перечисляет
ядра, запущенные без ожидания, - ошибка могла произойти в любом из них. При закрытии контекста свежие данные возвращаются на хост; буфер устройства освобождается, когда массив
собирает GC. Без устройства (JVM-fallback) это обычные Java-методы. Массив не потокобезопасен, как и `float[]`.

Такой массив можно передать и в подготовленный запуск (`ctx.prepare(kernel, a, b, k)`), и заменить через
`launcher.set(i, other)`: правила те же, что при прямом вызове. Состояние синхронизации массива меняет только рантайм
(служебный `com.sixik.gpu.api.internal.GpuArrayAccess` — не публичный API).

## Свёртки: `@Reduction`

Посчитать по большому диапазону одно число (сумму, количество, минимум, максимум) — свёртка. Её пишут обычным
последовательным циклом и помечают `@Reduction`; вызов возвращает результат, а рантайм исполняет цикл на устройстве
параллельно:

```java
@Reduction
public static int solidCount(GpuIntArray chunkX, GpuIntArray chunkZ, int samples, /* ... */ int octaves) {
    int perChunk = horizontal * horizontal * vertical;   // до цикла - вычисления без записи в память
    int count = 0;                                       // аккумулятор, начальное значение любое
    for (int i = 0; i < samples; i++) {                  // ровно такой цикл: i < end, i++
        int chunk = i / perChunk;
        if (sampleIn(i % perChunk, chunkX.get(chunk), chunkZ.get(chunk), /* ... */) > 0f) {
            count++;                                     // аккумулятор меняется только как acc = acc op e
        }
    }
    return count;                                        // сразу после цикла
}

int solid = TerrainNoise.solidCount(x, z, n, /* ... */);
```

Результат — `int`, `long`, `float` или `double`. Операция над аккумулятором одна на всё тело: `+=`, `-=`, `++`, `--`,
`acc = Gpu.min(acc, e)`, `acc = Gpu.max(acc, e)`, `&=`, `|=`, `^=`. Итерации должны быть независимы: тело читает что
угодно, но не пишет в память (кроме своих private-массивов), не меняет переменные, объявленные до цикла, не читает
аккумулятор иначе как в его обновлении и не выходит из цикла через `break` или `return` (внутри вложенных циклов
`break` можно). Нарушение — ошибка компиляции `GPU0018` с причиной; `GPU0016` — неподходящий тип результата, `GPU0017` —
метод помечен и `@Kernel`, и `@Reduction`.

Несколько чисел за один проход — несколько аккумуляторов, у каждого своя операция; результат — `@Struct` или вектор,
собранный из них в `return`:

```java
@Struct
public static final class MinMax {
    public float lo;
    public float hi;
    public MinMax() { }
    public MinMax(float lo, float hi) { this.lo = lo; this.hi = hi; }
}

@Reduction
public static MinMax range(GpuFloatArray v) {
    float lo = Float.POSITIVE_INFINITY;
    float hi = Float.NEGATIVE_INFINITY;
    for (int i = 0; i < v.length(); i++) {
        lo = Gpu.min(lo, v.get(i));
        hi = Gpu.max(hi, v.get(i));
    }
    return new MinMax(lo, hi);   // каждая компонента - свой аккумулятор, как есть
}
```

Компоненты результата — `int`/`long`/`float`/`double` или векторы из них (вложенные struct не допускаются), не больше
8 аккумуляторов и 64 байт на все вместе; каждая — отдельная переменная-аккумулятор (не константа, не выражение, не один
аккумулятор дважды), и аккумуляторы не читают друг друга. Типы можно смешивать: `new Stats(sum, count, max)` с `long`,
`int`, `int`. Векторный аккумулятор сворачивается покомпонентно — `acc = acc.add(v)`, `acc = Gpu.max(acc, v)` — и
возвращается как есть (`return acc;` с результатом `Float3`) или полем struct (`new Box(hi, count)` с полем `Int4 hi`).
Вызов возвращает новый объект. Один проход вместо нескольких свёрток экономит чтение данных: `range` против `low` + `high` на
RTX 5070 (`MultiReductionDeviceTest`, данные уже на устройстве) — 0.29 → 0.20 мс (100K), 0.23 → 0.15 мс (1M),
0.45 → 0.26 мс (16M).

На устройстве каждый work-item проходит свою часть итераций, группы по 256 work-item'ов складывают значения деревом в
local-памяти, хост сворачивает суммы групп. Число групп считается по границам цикла, если они — константа, параметр или
длина массива-параметра (в том числе через переменную до цикла), иначе берётся предел (16 групп на вычислительный блок).
Вызов ждёт результат: это одно блокирующее чтение маленького массива. Без устройства исполняется исходный цикл на JVM.
Порядок сложения на устройстве другой, поэтому сумма `float`/`double` может отличаться от последовательной в младших
битах; целые совпадают точно.

Свёртка заменяет пару «ядро пишет промежуточный массив, второе ядро его суммирует»: значения не пишутся в память, и
запуск один. На RTX 5070 (`FusionEffectDeviceTest`, проход «загрузить координаты, посчитать породу») `solidCount`
вместо пары `generateResident` + `countSolid`: 8 чанков DENSE — 0.20 → 0.15 мс, 64 чанка COARSE — 0.09 → 0.07 мс, на
больших порциях (64 чанка DENSE, вычисления шума доминируют) — около 2%.

### Автоматическое слияние «ядро → свёртка»

Если ядро только заполняет массив — `out.set(Gpu.getGlobalId(0), value)` на верхнем уровне тела, без других записей в
память, — и его выход затем читает `@Reduction`, свёртку можно не переписывать: рантайм сам подставит вычисление ядра в
свёртку, и массив не будет записан в память вовсе.

```java
TerrainNoise.generateResident(density, x, z, /* ... */);   // ядро откладывается
int solid = Stats.solid(density);                          // свёртка вычисляет плотности сама
```

Условия: вызов идёт через обычный вызов метода (фасад, а не `ctx.launch`), все массивы ядра — `GpuFloatArray` и т.п.,
размер запуска равен длине выхода, свёртка читает выход только как `a.get(i)` и `a.length()`. Отложенное ядро всё
равно исполняется, как только его результат может понадобиться: хост читает или меняет выход, выход передан другому
ядру, хост или ядро меняют вход ядра (маленькие входы до 64 КБ копируются при откладывании и этого не требуют),
контекст закрывается. Если выход целиком перезаписан (`fill`, новое такое же ядро), отложенный запуск отбрасывается.
Ошибка исполнения отложенного ядра проявляется в момент, когда оно исполняется.

То же работает с обычным ядром, которое читает выход поэлементно — `in.get(Gpu.getGlobalId(0))`: вычисление
отложенного ядра вставляется в него. Если и это ядро только заполняет свой массив, оно тоже откладывается, и цепочка
`generate → classify → count` исполняется одним ядром свёртки, без записи промежуточных массивов. Ядро, читающее
выход по другим индексам (`in.get(i - 1)`, цикл по массиву), не сливается: каждый элемент пришлось бы вычислять
несколько раз, поэтому отложенное ядро сначала исполняется.

На RTX 5070 (`AutoFusionDeviceTest`, проход «загрузить координаты, посчитать породу») — 8 чанков DENSE 0.25 → 0.18 мс
(явная свёртка `solidCount` — 0.16), 64 чанка COARSE 0.084 → 0.069 мс (0.066). Выключить — `GpuContext.builder()
.fusion(false)`, свойство `javatogpu.fusion=off` или переменная `JAVATOGPU_FUSION=off`.

## Деление ядра на стадии

Ядро, которому не хватает регистров, рантайм умеет исполнять несколькими запусками подряд (стадии `KernelSplitter`,
значения между стадиями — в промежуточных буферах, которые выделяет сам контекст); вызов ядра при этом не меняется.
Режим задаётся `GpuContext.builder().splitKernels(KernelSplitMode.X)` либо свойством `javatogpu.split` /
переменной `JAVATOGPU_SPLIT`: `off` (по умолчанию), `auto` (кандидат — ядро, которое по данным драйвера проливает
регистры; первые 10 запусков меряют оба варианта, остаётся более быстрый), `always` (для проверки). На RTX 5070 деление
во всех замерах медленнее целого ядра в 2.5–5 раз, поэтому по умолчанию выключено. `CompiledKernel.stageCount()` и
`stageDriverStats()` показывают, что выбрано.

## Числа и проверка результата

Целые операции следуют Java: переполнение с оборотом, маскирование счётчика сдвига, насыщающее float→int с NaN→0.
Деление целых на ноль и выход за границы на устройстве не имеют определённого результата; JVM бросает исключение,
а интерпретатор возвращает ошибку. Не используйте устройство для проверки результата такого запуска.

По умолчанию float strict: кодген запрещает слияние операций в FMA. Ослабить точность может только само ядро —
свойством `fp` (см. «Свойства компиляции ядра»); переключателя на весь контекст нет.
Побитовое равенство JVM и OpenCL для всех вещественных вычислений не гарантируется.

| Builtin | f32, ULP | f64, ULP |
|---|---:|---:|
| `sin`, `cos` | 4 | 4 |
| `sqrt` | 3 | 0 |
| `fma` | 0 | 0 |

Это табличные допуски **отдельных операций**. Автодопуск `GpuAssert` — эвристический максимум допусков
достижимых операций фактически выбранного варианта, с учётом f32/f64; для деления и остатка он не меньше 3 ULP.
Исключение: строгое ядро на устройстве с точным делением (см. ниже) делит и берёт `sqrt` побитово как JVM, и допуск
этих операций — 0.
Он не доказывает границу ошибки всего ядра: при вычитании близких чисел и длинных вычислениях ошибка результата
может быть больше. Для таких образцов задайте обоснованный `KernelSample.ulps(...)`.

Ядро с флагами `fp` (свойства компиляции, ниже) на устройстве по замыслу считает не то же, что JVM: `a*b+c` — одним
`fma`, `x/c` — как `x*(1/c)`. Оптимизатор делает эти замены явным кодом, поэтому `GpuAssert` сверяет устройство не с JVM,
а с интерпретатором по **скомпилированному** модулю (в сообщении — `COMPILED versus DEVICE`, в отчёте —
`compiledReference() == true`). Допуск остаётся прежним, и для `fma` это 0 ULP. Насколько «быстрое» ядро отличается от
JVM, не проверяется: это цена флагов, которые выбрали вы. Если откалиброванные `native_sin`/`native_cos` действительно
попали в ядро, к допуску добавляется абсолютный `2^-14` (`Report.absolute()`), для `native_sqrt` — 8 ULP. Флаг `native`
сам по себе код не переписывает, поэтому эталоном остаётся JVM.

```java
var sample = KernelSample.named("scale")
        .args(() -> new Object[]{new float[]{1, 2}, new float[2], 2f})
        .expected(null, new float[]{3, 5}, null)
        .build();
GpuAssert.sameResult(Kernels.class, "scale", sample);
```

Зависимость тестов — `io.github.deussixik:test-support:0.2.0-SNAPSHOT`, JUnit Jupiter и platform launcher;
полный пример находится в standalone-сборке. `Report` показывает выполненные и пропущенные ветви. Для
детерминированной проверки без устройства используйте `.without(KernelSample.Leg.DEVICE)`.
Для группового ядра задайте `expected`, независимо посчитанный на хосте.
При допуске 0 различается знак нуля; все NaN считаются равными. При ненулевом допуске ±0 совпадают,
а бесконечность по текущему правилу сравнения соседствует с максимальным конечным значением.

## Диагностика и отладка

Фронтенд выдаёт `GPU####` с позицией исходника и подсказкой, нарушение подмножества останавливает сборку.
Полная таблица — [`diagnostics.def`](../diagnostics/diagnostics.def).

| Код | Типичная причина |
|---|---|
| `GPU0113` / `GPU0114` | helper без `@DeviceFunction` / нет исходника device-функции |
| `GPU0301`–`GPU0306` | только `frontend = 'asm'`: нет `LocalVariableTable`, неподдерживаемая инструкция, класс вызова не найден, несводимый поток, непустой стек на стыке, нечитаемый class-файл |
| `GPU0112` | метод не поддержан в GPU-коде, в том числе `Math.sin` и другие неточные методы JDK |
| `GPU0122` | запись в constant-массив |
| `GPU0130` / `GPU0131` | потенциально расходящийся barrier; предупреждение / strict-ошибка |
| `GPU0193` | struct-значение может разделять ссылку с другим объектом |
| `GPU0310` | ядро `exact` использует приближённый builtin (`Gpu.sin`) или флаг `fp` |
| `RT-D01` / `RT-D02` | нет подходящего устройства / нет требуемых возможностей |
| `RT-A02` / `RT-L01` | неверный аргумент / несовместимые размеры запуска |
| `RT-F01` / `RT-F02` / `RT-F03` | fallback невозможен / отсутствует IR / отсутствует `$jvm` |

Для строгой проверки барьеров: `gpu { strictBarriers = true }`.
`Gpu.assumeUniform(x)` — утверждение автора ядра, а не синхронизация work-item.
Дамп исходника: `builder.dumpSources(path)`, `-Djavatogpu.dump=...` или `JAVATOGPU_DUMP`.

## Оптимизатор IR

Перед генерацией OpenCL C контекст прогоняет IR через `ir-optimizer`: свёртка констант и алгебра, удаление мёртвого
кода, протяжка значений по локалям, общие подвыражения и вынос инвариантов из циклов. По умолчанию
(`OptimizeOptions.DEFAULT`, уровень 2) все преобразования точные: результат ядра побитово тот же, что без оптимизатора.
В режиме `EmitOptions.DEBUG` оптимизатор не запускается, чтобы исходник совпадал с Java-кодом.

```java
GpuContext ctx = GpuContext.builder()
        .optimize(OptimizeOptions.DEFAULT.withRegisterBudget(48)) // бюджет регистров для CSE/LICM
        .build();
```

`OptimizeOptions.NONE` выключает оптимизатор; `-Djavatogpu.optimize=0..3|off` или `JAVATOGPU_OPTIMIZE` меняют уровень
без пересборки. Бюджет времени - 2 с на модуль (`withTimeBudget(Duration)`, `null` - без предела): не уложившийся
модуль оптимизируется заново на уровне 1, затем собирается как есть, а `EventListener` получает предупреждение
«compiled at opt=N». Преобразования, меняющие вещественный результат, разрешает не контекст, а ядро (`fp=...`). Если ядру не хватает регистров, контекст пишет предупреждение в `EventListener`: когда драйвер
сообщает ресурсы ядра (NVIDIA), — только если драйвер действительно проливает значения в память; иначе — если оценка
давления по IR выше бюджета. Такое ядро рантайм умеет исполнять по стадиям (см. «Деление ядра на стадии»).
`CompiledKernel.registers()` — регистры для решений рантайма: от драйвера, если известны, иначе откалиброванная
оценка; `registersMeasured()` говорит, что из двух. Данные драйвера сохраняются в дисковом кэше рядом с образом
программы, поэтому известны и после перезапуска (драйвер печатает их только при настоящей сборке).

### Свойства компиляции ядра

Настройки генерации задаются в самом ядре — без JVM-флагов и переменных окружения, поэтому работают и там, где
командной строкой не управляешь (моды, плагины, встраиваемые приложения):

```java
public final class Profiles {
    public static final String FAST = "fp=contract,native";
}

@Kernel(compilationProperties = Profiles.FAST + "; opt=3")
public static void terrain(@Global float[] out, int seed) { ... }
```

Формат — пары `ключ=значение` через `;`, списки через запятую, пробелы игнорируются. Строку проверяет annotation
processor: ошибка — это ошибка компиляции с подсказкой (`GPU0019` синтаксис, `GPU0020` неизвестный ключ, `GPU0021`
недопустимое значение, `GPU0022` повтор ключа).

| Ключ | Значения | Смысл |
|---|---|---|
| `fp` | `contract`, `reciprocal`, `finite`, `nsz`, `native`, `relaxed` | что можно менять в вещественной арифметике: слияние `a*b+c` в `fma`; `x/c → x*(1/c)`; NaN и бесконечностей нет; знак нуля не важен; аппаратные приближённые функции; `relaxed` — всё сразу. По умолчанию ничего: результат как на JVM |
| `opt` | `0..3` | уровень оптимизатора IR для ядра; важнее уровня контекста. Без ключа — уровень контекста |
| `inline` | `default`, `always`, `never` | политика встраивания device-функции: `always` — оптимизатор (`opt ≥ 1`) подставляет тело в место вызова, если это не меняет смысла; `never` — `__attribute__((noinline))` |
| `exact` | `true`, `false` | результат ядра побитово равен JVM: несовместимо с `fp`, разрешены только точные операции (ниже) |

Флаги `fp` записываются в IR ядра и входят в его хэш. Преобразования по ним выполняет оптимизатор библиотеки явным
кодом — опции сборки драйвера вроде `-cl-fast-relaxed-math` для этого не используются, поэтому результат не зависит от
того, как драйвер конкретного производителя понимает такие опции. JVM-реализация ядра всегда считает строго.
Сейчас по флагам работают правила оптимизатора: `contract` — `a*b+c → fma(a, b, c)`, в том числе когда произведение
записано в переменную (`float p = a[i] * b[i]; ... s = p + c` и накопление `s = s + p` в цикле), и только если
устройство выполняет FMA аппаратно (`CL_FP_FMA`; иначе явный `fma()` эмулировался бы программно и был бы медленнее); `reciprocal` — `x/c → x*(1/c)` для константы `c`; `nsz` — `x+0 → x`; `finite` — `x-x → 0`; `finite` и `nsz`
вместе — `x*0 → 0`; `native` — `Gpu.sin`, `Gpu.cos`, `Gpu.sqrt` для `float` печатаются как `native_sin`, `native_cos`,
`native_sqrt`, но только те, чья точность проверена на устройстве (ниже). Кроме того, кодоген по флагам ядра:
`finite` и `nsz` вместе — `Gpu.max`/`Gpu.min` для вещественных печатаются аппаратными `fmax`/`fmin` вместо обёрток,
повторяющих `Math.max` с NaN и `-0.0`; `reciprocal` — `1/sqrt(x)` печатается как `rsqrt(x)`. Device-функция получает пересечение флагов всех ядер,
из которых вызывается (общая функция строгого и «быстрого» ядра остаётся строгой); ядро после автоматического слияния —
пересечение флагов обоих ядер.

Строгое ядро делит как JVM. По умолчанию OpenCL C разрешает `float`-делению ошибку 2.5 ULP, а `sqrt` — 3 ULP, тогда
как Java округляет точно. Если устройство сообщает `CL_FP_CORRECTLY_ROUNDED_DIVIDE_SQRT` (NVIDIA сообщает), ядро с
`float`-делением или `sqrt` собирается с `-cl-fp32-correctly-rounded-divide-sqrt` (опция ужесточает математику, а не
ослабляет). Это не бесплатно: на RTX 5070 цикл из одних делений и `sqrt` стал медленнее в 1.5 раза. Ядро с `reciprocal`
или `native` опцию не получает — приближённое деление в нём разрешено.

**Точные ядра (`exact=true`).** Строгое ядро считает как JVM с точностью до допусков builtins (`Gpu.sin` — 4 ULP).
Ядро `exact` гарантирует побитовое равенство: фронтенд проверяет все достижимые из него функции, и приближённый builtin
(`Gpu.sin`, `Gpu.cos`) или флаг `fp` рядом с `exact` — ошибка `GPU0310` с именем операции. Функция, общая для строгого
и точного ядра, проверяется по каждому ядру отдельно. Ядру `exact` с `float`-делением или `sqrt(float)` нужно устройство
с `CL_FP_CORRECTLY_ROUNDED_DIVIDE_SQRT`; на другом устройстве рантайм отвечает `RT-D02`, а не считает приближённо.

**Методы JDK в GPU-коде.** Побитово точные методы JDK вызываются как обычно, без `Gpu.*`:
`Math.floor/ceil/rint/abs/sqrt/min/max/fma/copySign/nextUp/nextDown/nextAfter(double, double)/signum/floorDiv/
floorMod/multiplyHigh` (и те же методы `StrictMath`), `Double.doubleToRawLongBits/longBitsToDouble`,
`Float.floatToRawIntBits/intBitsToFloat`, `Integer` и `Long`: `rotateLeft/rotateRight/numberOfLeadingZeros/
numberOfTrailingZeros/bitCount/compareUnsigned`. Результат на устройстве равен JVM для любых аргументов (NaN, `-0.0`,
`MIN_VALUE`). Остальные методы JDK — `GPU0112`: `Math.sin`, `Math.exp` и подобные на устройстве не точны, поэтому их
нужно заменить явно на `Gpu.sin` и т.п.; `Math.round` и `Double.doubleToLongBits` тоже не входят (иное округление,
нормализация NaN).

Точность `native_*` стандарт OpenCL не задаёт, поэтому при первой сборке ядра с `fp=native` контекст калибрует
устройство: небольшое ядро считает функции на фиксированной выборке, результат сравнивается с эталоном в `double`.
Функция разрешается, если `sin`/`cos` ошибаются не больше чем на `2^-14 ≈ 6e-5` (абсолютно, на `[-32π, 32π]`), а `sqrt`
— не больше чем на `2^-20` (относительно, на `[2^-60, 2^61]`); NaN — отказ. Остальные функции ядра остаются точными.
Результат хранится в дисковом кэше по устройству и драйверу и доступен через `GpuContext.nativeMath()`; ядра без
`fp=native` калибровку не запускают. Например, на RTX 5070 проходят все три: ошибка `sin`/`cos` около `1e-5`,
`sqrt` — около `1e-7`. Ошибка `native_sin` растёт с аргументом, поэтому для больших углов `native` не подходит.

Элементы `@Kernel(inline = ..., optLevel = ...)` устарели: они учитываются, только если заданы явно, а задание одного
свойства и элементом, и строкой — ошибка `GPU0023`.

## Кэш и ограничения

Кэш в памяти хранит результат компиляции; дисковый кэш — бинарь драйвера. Учитываются IR без debug,
кодген, исходник, опции и устройство с версией драйвера. Повреждённый или отвергнутый образ пересобирается.
Дисковый предел по умолчанию — 512 МиБ. Каталоги:

- Windows: `%LOCALAPPDATA%\javatogpu`;
- Linux: `$XDG_CACHE_HOME/javatogpu` либо `~/.cache/javatogpu`;
- macOS: `~/Library/Caches/javatogpu`.

Управление: `builder.diskCache(path)`, `noDiskCache()`, `diskCacheLimit(bytes)`, свойство `javatogpu.cache`
или `JAVATOGPU_CACHE` (путь либо `off`). Явная настройка builder имеет приоритет.

### Прогрев

Первый вызов ядра ждёт его сборки драйвером: на RTX 5070 это 30–120 мс на ядро без кэшей, 10–30 мс из дискового
кэша. Чтобы первый вызов не ждал, ядра можно собрать заранее, в фоне:

```java
JavaToGpu.warmUp(TerrainNoise.class, Effects.class);    // при старте приложения, ждать не нужно
...
TerrainNoise.generate(...);                             // ядро уже собрано
```

`warmUp` собирает все `@Kernel`- и `@Reduction`-методы классов в том же контексте, что и обычный вызов из этого
потока (`JavaToGpu.use` либо по умолчанию), и возвращает `CompletableFuture<JavaToGpu.WarmUp>`: сколько ядер собрано и
диагностики тех, что не собрались. Вызов ядра во время прогрева ждёт только сборку своего ядра, если она уже идёт;
запуски остальных ядер не задерживаются. События `COMPILE` прогрева приходят в слушатель из потока прогрева.

В v1 одно активное устройство на контекст и синхронные запуски. Указатели и динамические `__local`-аргументы
в сигнатуре ядра не поддерживаются. Images, async API, AutoTune, multi-GPU, оптимизатор e-graph,
Rust и CUDA/SPIR-V — после v1.
